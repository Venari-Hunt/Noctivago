## Freesound import

Search/preview/import sounds from [Freesound.org](https://freesound.org) directly into the library. The search/browse UI itself lives in the **Browse Sounds plugin** (`plugins/browse-sounds/`, see below) as of v0.1.204 — everything in this section below the UI layer (auth, the main-process search/download/proxy code, the actual import) is core and unchanged by that move.

**Auth**: a single app-wide API token (`FREESOUND_API_KEY`, requested once at freesound.org/apiv2/apply), baked in at build time (`electron.vite.config.js`'s `__FREESOUND_API_KEY__`, main process only). This is Freesound's simplest auth shape and covers everything this feature needs — text search and downloading a sound's **preview** (compressed mp3, not the original file). OAuth2 (a per-user login flow) is only required for write actions (upload/rate) or for downloading a sound's full original-quality file, neither of which this feature does — importing a preview is plenty for a looping ambient sound and keeps the whole feature to one token instead of a login flow. It's baked into the one build `.github/workflows/release.yml` produces, which goes to both the GitHub release and itch.io unmodified — it's a free, re-issuable, read-only key rather than a real credential, so the owner accepted it being extractable from a public binary.

**Main process** (`src/main/freesound/`): `client.js` does the search call and builds an authorized (token-appended) preview URL; `download.js` reuses the bundled ffmpeg (`runFfmpegToFile`, same shape as `library.js`'s own direct-link download) to pull a preview down to a scratch FLAC (see `docs/playback.md`, Stored audio format); `protocol.js` registers a `freesound-preview://` privileged scheme (alongside `sound://`/`plugin://` in `src/main/index.js`) that proxies live preview *auditioning* through an authorized fetch — the renderer only ever sees the plain, unauthenticated preview URL Freesound's search response returned, and the API token never crosses into the sandboxed renderer. `authorizedPreviewUrl`'s hostname check doubles as an SSRF guard against a URL that isn't actually pointing at Freesound.

**Import** (`library.js`'s `addSoundFromFreesound`) downloads the preview and funnels it through the exact same `addSound(keepCopy: true)` path every other import already uses, plus one new field: `source: { type: 'freesound', freesoundId, username, license, pageUrl, importedAt }`, carrying the attribution a CC-BY (or similar) sound legally needs — surfaced as a small "Freesound" badge in the Mixer (`SoundRow.js`, reusing the Composite badge's styling) whose tooltip shows the author/license.

### The Browse Sounds plugin (`plugins/browse-sounds/`, tab titled "Browse Sounds")

A dedicated tab for internet-sourced sound discovery, split out of the old "Search Freesound…" add-sound-menu dialog in v0.1.204 per the owner's own direction: browsing/discovering sounds you don't yet know needs fundamentally more screen space and richer UI than importing a file you already have and know (which is exactly why the old dialog felt "underbaked" and "not a pleasant experience for browsing"). Local file/folder/watch-folder/record imports explicitly stayed in core's existing "+" menu, unchanged — only internet-sourced search moved here, and the old dialog (`src/renderer/core/FreesoundDialog.js`, its `#freesound-dialog` markup, its `.freesound-*` CSS, its "Search Freesound…" menu item) was deleted outright rather than kept as a second entry point.

- **Nothing new on the backend** — `window.noctivago.freesound`/`window.noctivago.library` (the same `search`/`isAvailable`/`addSoundFromFreesound` the old dialog called) is already the full API surface a plugin needs, handed through wholesale per the plugin architecture's own `app.noctivago = window.noctivago` rule. The only main-process change was adding `description` to `client.js`'s `SEARCH_FIELDS`/mapped result shape, since the richer cards needed it and the old dialog never had.
- **Card grid instead of a list** (`grid-template-columns: repeat(auto-fill, minmax(280px, 1fr))`) so the extra room actually gets used, and every field the search response already returns now shows: tags (capped at 6 + a "+N" overflow pill), a 2-line-clamped description, and a rating (`★4.3 (12)`) the old dialog silently discarded despite the API already sending it.
- **Infinite scroll**: an `IntersectionObserver` on a sentinel `<div>` after the results grid triggers `loadMore()` (guarded by `loading`/`hasMore`/an active query) instead of the old dialog's manual "Load more" button — replaces `runSearch({append: true})`'s trigger, not its logic, which is otherwise identical to before.
- **A sort picker** (best match / highest rated / most downloaded / longest / shortest / newest) the old dialog never exposed even though `searchSounds`'s own `sort` param already supported all of these — a real, if small, missed feature the redesign picked up along the way.
- **State persists across tab switches for free** — a tab's `mount()` only runs once (`TabHost.js`'s lazy-mount-once-then-show/hide lifecycle), so the current query/results/scroll position survive navigating away and back, unlike the old modal which reset every time it opened.
- **A source badge on every card** (`.browse-card-badge`, reusing the exact amber `.sound-row-composite-badge` color the Mixer's own Composite/Freesound badges already use) — built before a second source existed so the layout wouldn't need to change when one landed; it landed a day later (see below).
- Verified live via CDP against a real dev build: the tab registers and mounts correctly, the old menu item and dialog are confirmed gone, and — since no `FREESOUND_API_KEY` was available in this local dev environment to exercise a real search — `renderCard()` was verified directly against synthetic result data (long-name ellipsis, 8-tag truncation to 6+"+2", a populated vs. a zero-rating result, an empty description omitting the `<p>` entirely) plus the preview button's play/pause toggle. Full 64-test suite (unaffected - `client.js`'s existing search tests don't assert the full mapped shape) and a clean build (bundle size dropped, confirming the old dialog's code was actually removed, not just unreferenced).

**YouTube search added (v0.1.206)**, after a 2026-09-15 research pass (owner interview + Board) found the official YouTube Data API is a dead end for this app's one-app-wide-key model (the Freesound pattern): `search.list` costs 100 of a project's 10,000 daily quota units, so a single key would cap *every user of the app combined* at ~100 searches/day, and a quota increase needs a Google compliance audit (weeks to months, not guaranteed). Instead, `src/main/ytdlp/search.js` reuses the yt-dlp binary already bundled for "Add from link"'s video-site fallback (since v0.1.132) — it searches with no API key and no quota at all, the same way the site itself works rather than calling Google's API. `--flat-playlist --dump-json` against `ytsearch{page*pageSize}:<query> --playlist-start <n> --playlist-end <m>` returns one NDJSON line per result with everything a card needs (title, duration, channel, thumbnail, description, watch URL) already in one call — verified against the real bundled binary before writing this (2.2s for 20 results); no second per-video yt-dlp call needed. `--playlist-start`/`--playlist-end` against a larger `ytsearchN:` count works as a genuine page offset (also verified directly) — YouTube search has no cursor/token the way Freesound's API does, so each "page" re-runs the search up through its own end index rather than continuing a saved cursor, which is fine at the scale an interactive search realistically reaches. Reuses the same `ytDlpCookiesBrowser` setting "Add from link" already has for YouTube's bot-detection, rather than a second parallel cookie setting.

The owner's own direction building this: "do it in a way that won't break the sound browser... contained inside the plugin but if it doesn't work or breaks it doesn't stop the other half (freesound)." Freesound and YouTube are two fully independent sources in the plugin's own state (`this.sources.freesound`/`.youtube`, each its own `available`/`page`/`hasMore`/`loading`/`error`) - every YouTube-specific call (`isSearchAvailable`, `searchYouTube`, a card's own render) is wrapped in its own try/catch so a yt-dlp failure never blocks, clears, or otherwise touches Freesound's results, and vice versa; verified live by confirming a search with no `FREESOUND_API_KEY` locally still returned a full YouTube grid with the correct "Freesound isn't available... YouTube still works" banner and zero console errors. Results from both sources combine into one grid (owner's own settled answer from the day before: "search both sources at once, combined, tagged by source," not a *source-picker* toggle that only ever shows one source's results at a time — v0.1.207 below adds an *include/exclude* toggle per source, a different axis, see that entry) - `renderCard(sound, source)` branches only on rendering shape (Freesound's username/license/rating vs. YouTube's channel/thumbnail), everything else (grid, sentinel, infinite scroll) is shared. YouTube results get a thumbnail and a "Watch ↗" link (opens externally via the app's existing `setWindowOpenHandler` → `shell.openExternal`) instead of Freesound's in-app preview button, since there's no cheap streaming preview URL the way Freesound's `previews` field provides - importing is the only way to actually hear one. Import reuses `library:addSoundFromUrl` unchanged (the exact same yt-dlp-download pipeline `AddLinkDialog.js` already drives), capped at the same 10-minute default; since its progress channel is a single global stream with no per-request id, only one YouTube import can run at a time (every other YouTube card's Import button disables while one is in flight - the same constraint `AddLinkDialog`'s own single-download dialog already lives with), while Freesound imports are unaffected since they use a separate channel. A `seenYoutubeIds` Set filters cross-page duplicates - found live while testing infinite scroll (two consecutive `ytsearch` calls at different end-indices can rank a video differently between calls, producing an occasional repeat at a page boundary; Freesound's API has a stable cursor and doesn't have this issue). Verified live via CDP against a real dev build with real network access (no Freesound key needed for this half): a real search returned 12 YouTube cards with correct thumbnail/channel/duration/watch-link; scrolling to the sentinel loaded 12 more with the dedup fix confirmed (24 cards, 24 unique URLs); a real import of an actual search result through the unmodified `addSoundFromUrl` pipeline produced a real library entry (cleaned up after). Full 65-test suite and a clean build.

**Per-source enable/exclude toggles (v0.1.207)**, owner inbox follow-up the day after v0.1.206 shipped: "Youtube search as well as freesound search should be toggles." A checkbox per source (`#browse-source-freesound`/`#browse-source-youtube`, both checked by default) next to the search bar - unrelated to the combined-grid decision above (that's still in effect: both sources still render into one shared grid when both are on). Each source gained an `enabled` field alongside its existing `available`/`page`/`hasMore`/`loading`/`error` state; `search()`/`loadMore()` now gate on `available && enabled`. Unchecking a source removes its cards from the grid immediately (`toggleSource()` queries `[data-source="key"]` and removes them, same selector `fetchSource`'s own non-append path already uses) and marks it `hasMore = false`; re-checking it re-fetches page 1 fresh into the existing grid via the same `fetchSource(key, {append:false})` path `search()` uses, rather than requiring a whole new search. `checkAvailability()` also disables and force-unchecks a toggle for a source that isn't available at all, so you can't "enable" a source that can't work. **Bug caught live while verifying this**: re-enabling YouTube initially returned only 1 of 12 expected results - `toggleSource`'s re-enable path called `fetchSource` without clearing `seenYoutubeIds` (the cross-page dedup set added in v0.1.206), so every video from the *previous* search was still marked "already seen" and filtered out as a false duplicate. Fixed by clearing `seenYoutubeIds` on every toggle of the `youtube` key (both directions - off needs it cleared too, since its cards are gone from the grid either way). Verified live via CDP against a real dev build: toggling YouTube off correctly cleared the grid to 0 cards with a "turn on at least one source" status; toggling it back on correctly re-populated with no duplicates (11/11 unique URLs, confirmed after the dedup fix). Full 65-test suite and a clean build.

**Freesound name-as-link, and a sticky preview playback bar (v0.1.208)**, owner inbox 2026-09-16, three asks in one note: (1) a Freesound card's name should link out to the sound's real Freesound page, styled as a link with a small link icon; (2) a draggable progress bar so a preview can be scrubbed forward/back instead of only playing start-to-end; (3) "a topbar similar to the one on the remix tab but without the audio editing modules, just the ones that control playback and volume." All three are Freesound-specific (YouTube results already open externally via their own "Watch ↗" link and have no in-app preview to control). The card's name is now an `<a href={pageUrl} target="_blank">` wrapping a truncatable `.browse-card-name-text` span plus a small Feather-style external-link SVG icon, `target="_blank"` routed externally the same way as the YouTube "Watch ↗" link already is. `mountSticky()` (newly registered for this plugin, alongside the existing `mount()`) renders a stripped-down echo of the Remix plugin's own sticky bar — Play/Pause, a draggable progress-bar-with-thumb, a time readout, and a volume slider, all `browse-sticky-*`-prefixed duplicates of the same CSS shapes `plugins/editor/styles.css` already has (per this plugin's own self-contained-by-directory rule) — with none of Remix's editing modules. `togglePreview()` (the existing per-card ▶/⏸ button handler) now also updates the sticky bar's sound name and enables its Play button; a new `applyPreviewPlayState(playing)` keeps the card's own button and the sticky Play button in sync from every call site (card click, sticky Play click, `stopPreview()`); `wireStickyProgressDrag()` is a simplified copy of Remix's own mousedown/mousemove/mouseup seek handler (no loop-region math needed here, just plain 0..`audio.duration`); `updateStickyProgress()` reads `previewAudio.currentTime`/`.duration` on `timeupdate`/`loadedmetadata` events. Verified live via CDP against a real dev build (a temporary `window.__browseDebug = this` hook, removed before commit): a synthetic Freesound card's name rendered as a real `<a>` with the correct `href`/`target`/`rel` and the icon present; starting a preview correctly populated the sticky name and flipped both the card and sticky Play icons; a real `mousedown` dispatched at 75% along the progress bar's own bounding rect set `audio.currentTime` to within rounding of 75% of a (stubbed) duration, confirming the drag-to-seek wiring itself fires correctly, not just the underlying method; stopping reset every sticky element back to its idle state. Full 65-test suite and a clean build.

**BUG FIX (v0.1.209) — self-review pass over v0.1.204-208 (8 parallel finder agents, backlog was dry of anything owner-actionable) caught a real toggle-off race in the per-source enable/exclude toggles (v0.1.207).** `toggleSource(key, false)` clears a source's cards and sets `hasMore = false`, but a `fetchSource()` call already in flight for that key when the toggle fires has no way to know it's now stale — its only staleness guard was `requestId`, which only changes on a fresh `search()`, not a toggle. Three independent review agents converged on the same repro: search with both sources on, disable the slower one (YouTube, mid-`yt-dlp` search) before its response lands, and the late response would silently re-append its cards and flip `hasMore` back to `true` — undoing the toggle-off the user had just performed, with no error and no visible cause. A related, subtler case (also flagged independently): a rapid off-then-on toggle before the pre-toggle fetch resolves could start a second, concurrent `fetchSource()` for the same key, racing the first and risking duplicate/stale cards depending on resolution order. Fixed with a per-source `generation` counter (mirroring the existing global `requestId` pattern this file already uses for cross-search staleness) — `toggleSource(key, false)` bumps `sources[key].generation`, and `fetchSource()` captures it before its awaits and bails if it's changed by the time the response lands, regardless of the source's `enabled` state when it resolves (a fresh fetch from a subsequent re-enable already owns the current generation, so the stale one is correctly discarded even if the user turned the source back on in between). Also extracted two small pieces of logic that were independently duplicated in both `toggleSource()` and `fetchSource()` (the sentinel-visibility check, the per-source card-clear query) into `updateSentinelVisibility()`/`clearSourceCards()`, added a module-level `SOURCE_KEYS` constant replacing 5 repeated `Object.keys(this.sources)` calls, and dropped a dead `s.hasMore = true` write in the toggle re-enable path (unconditionally overwritten by the very next `fetchSource()` call before ever being read). Not live-verified via CDP — no existing Electron/CDP test harness in this repo, and building one from scratch was judged disproportionate to a self-review cleanup pass (the same call made in prior self-review passes, e.g. v0.1.205); instead verified directly against the real, unmodified `BrowseSoundsPlugin` class via a hand-rolled minimal-DOM Node harness with controllable delayed search promises — confirmed the harness genuinely reproduces the bug against the pre-fix code (stale card reappears, `hasMore` flips back on, sentinel un-hides) before confirming the fix resolves it, plus a second scenario for the rapid off→on double-fetch case (exactly one card survives, from the fresher call, no stuck `loading` state). A handful of lower-severity/theoretical findings from the same review pass (YouTube's `hasMore` computed after filtering out live-stream results, which could rarely end infinite scroll one page early; a confusing retry message if "Add folder" partially fails after files are already imported; minor cross-file pagination-clamp duplication between `client.js`/`search.js`) were not chased this pass — none were confirmed-reproducible regressions, matching the usual bar for what gets fixed immediately versus logged as a follow-up. Full 65-test suite and a clean build.

**Export credits + scene details (v0.1.224)**, owner inbox. The export's `info.txt` gains two sections, so a person or an AI can write a YouTube description with proper credits and an accurate picture of the mix.

**Credits.** `src/shared/credits.js` (Electron-free, `test/credits.test.js`; the Export plugin's copy, `src/domain/credits.js` in `noctivago-export`, is checked identical apart from its 2-line header by that repo's `test/coreParity.test.js`) provides:
- `parseFreesoundFileName`, which reads Freesound's download names `<id>__<username>__<title>`. Usernames may contain single underscores, and a trailing `_optimized` from the owner's re-encode step is dropped.
- `describeLicense`, which maps CC URLs and names to short labels plus whether attribution is required.
- `creditLine`.

Sources are recorded in `library.js`:
- `addSound` detects a Freesound source from the file name when none was given. It uses the title as the name when the caller passed the bare file name.
- `addSoundFromUrl` now records `source: { type: 'url', url }`.
- Freesound imports (Browse Sounds and community re-downloads) also keep `title`, a trimmed `description` and `tags`.
- `detectFreesoundSources()` runs once at startup (`freesoundSourcesDetected` store flag) to backfill existing entries from `originalPath`. That's 25 of the owner's 81 sounds.
- `resolveCredits(ids)` (IPC `library:resolveCredits`, preload `library.resolveCredits`) fills a Freesound source's missing license/title/description/tags via `freesound/client.js`'s new `getSoundCredits` and saves them. It returns null without a key or on any error, and the export still writes the file.

**Scene section.** `src/domain/sceneSummary.js` in `noctivago-export` (pure, `test/sceneSummary.test.js` there) has `buildSceneSection({ sounds: [{entry, volume}], groups, wholeMix })`:
- One line per sound: volume, play mode (loop, random interval with its gap, clock times or interval), and group.
- Then a detail line listing only non-neutral settings: speed/pitch/reverse/Doppler, drift ranges and timing (loop sounds) or per-play ranges (random interval/scheduled), filters, effects, and pan.
- Then the groups with their bus processing and drift ("each sound on its own"), and whole-mix processing.

`buildCreditsSection(credits)` adds the attribution reminder, a check-these list for unknown licenses, and the authors' own descriptions. `plugins/export/index.js` collects each sound's effective entry and volume, resolves credits before writing `info.txt`, and appends both sections. The AI prompt now asks for a plain-words scene description followed by the Credits section copied exactly.

**Editable prompt (v0.1.234).** The prompt text lives in `DEFAULT_INFO_PROMPT` (`plugins/export/index.js`) and credits Noctívago with its itch.io link.
