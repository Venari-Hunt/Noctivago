## Plugins

The app is designed for outside contributors to add functionality as plugins rather than editing core — modeled on Obsidian's plugin architecture, but **deliberately not** copying its trust model (Obsidian plugins get raw Node/Electron access; here that's split by process, see below), since this codebase is more sandboxed (`contextIsolation: true`, no `nodeIntegration`, everything served through custom protocols rather than raw file access).

**A plugin is a folder** containing `manifest.json` (`id`, `name`, `version`, `main` required; `mainProcess`, `styles`, `description`, `author`, `minAppVersion` optional) + a `main` entry file exporting a default class:
```js
export default class MyPlugin {
  constructor(app, manifest) { this.app = app }
  async onload() { this.unregister = this.app.tabs.register({ id, title, mount: (container) => {...} }) }
  async onunload() { this.unregister?.() }
}
```
**The contract is `types/plugin.d.ts`** (manifest shape, the plugin class, `TabDefinition`, the `app` object, every `window.noctivago` method). The app stays plain JS; the `.d.ts` is for plugin authors' editors (TypeScript import or JSDoc, see `hello-world/index.js`). Payload/result objects are typed loosely on purpose, since sound/preset records still change between releases; method names and arguments are the stable part. `test/pluginManifest.test.js` fails if a preload method is added without a matching line in the `.d.ts`. **The manifest is validated at runtime** by `src/shared/pluginManifest.js` (called from `registry.js`'s scan): required strings present, `id` a lowercase host label (`[a-z0-9-]`, it becomes the `plugin://` hostname; it need not match the folder name, e.g. `plugins/editor/` is `remix`), `version`/`minAppVersion` shaped like `1.2.3`, and `main`/`mainProcess`/`styles` relative paths with no `..`. That last one matters for `mainProcess`: `invoke.js` imports it straight from disk, outside the `plugin://` path-traversal guard. A failing plugin is skipped with every reason in one log line. `minAppVersion` is format-checked only for bundled plugins (every bundled manifest says `0.2.0` while the app is 0.1.x); store installs compare it with the app version (see the store section).

Two real examples exist in `plugins/`: `hello-world/` (minimal working plugin) and `broken-plugin-example/` (deliberately throws in `onload()` — a regression-test fixture proving one broken plugin can't take down the app or other plugins). Both stay in the repo for development but are excluded from release builds (v0.1.226, owner request) by a `filter` on `electron-builder.yml`'s `plugins` extraResources entry; before that every installed app showed a "Hello" tab. A new example or test-fixture plugin should be added to that filter too.

**Plugins written in React/JSX** (step 2 of the React plan): a plugin with `src/index.jsx` (or `.tsx`/`.js`) is bundled by `scripts/build-plugins.mjs` (Vite library mode, ES output) into `plugins/<id>/main.js`, which its manifest's `main` points at. React is bundled *into each plugin* (~360 KB unminified) rather than shared with the app — the contract stays framework-free (`mount(container)` hands over a plain DOM node; the plugin creates its own React root there and unmounts it in `onunload()`), so a community plugin can use any framework or none. Plain-JS plugins have no `src/index.*` and are left alone. `main.js` is build output (gitignored); `npm run dev`/`build`/`build:win`/`release:win` all run `build:plugins` first, and `npm run dev:plugins` rebuilds on save (reload the window to pick it up). The packaged app ships only `main.js` — `electron-builder.yml` filters out every plugin's `src/`. CSS imports from JSX aren't supported; ship a `styles.css` via the manifest. `plugins/hello-react/` is the minimal example (excluded from releases like `hello-world/`); `test/buildPlugins.test.js` checks the output has no bare `react` imports or `process.env` references, the two things that break in the renderer. Canvas-heavy UI (waveform, meters, EQ graph) stays imperative inside a React-owned container, per the React decision.

**JSX islands — moving part of a plain-JS plugin to React** (step 3 of the React plan, the pilot): every `plugins/<id>/src/islands/<Name>.jsx` is built to `plugins/<id>/islands/<Name>.js` (gitignored, wiped each build; all of one plugin's islands build together so they share one copy of React), which the plugin's plain-JS code imports like any module. The pilot is Remix's Sound-mode filter sliders (high/low-pass, gain, pan, gate, noise reduction, echo, reverb): `src/islands/FilterControls.jsx` exports `mountFilterControls(container, { onChange, onNoiseSampleFromLoop })` → `{ getValues, setValues, unmount }`, and `index.js` replaced ~16 `els.*` inputs, their listeners and `updateFilterLabels()` with that. Values live in a tiny external store read through `useSyncExternalStore`, not React state, because `index.js` reads them synchronously (`currentFilters()`) right after writing them (`setFilterSliders()`), before React has rendered. **Gotcha:** the app-wide double-click-resets-a-slider listener (`src/renderer/core/sliderReset.js`) doesn't work on React-controlled range inputs — React rewrites the input's native `defaultValue` on every render and ignores a programmatic `.value` + synthetic `input` event — so React sliders handle `onDoubleClick` themselves and `stopPropagation()`. Owner + Luis judge this pilot before any wider migration.

`register()` also accepts an optional `mountSticky: (container) => {...}` alongside `mount` — its own section in the shared sticky bar directly under the tab bar (`#tab-sticky-bar` in `index.html`, wired in `TabHost.js`), always visible regardless of how far the tab's own content is scrolled. This is a fixed-height flex sibling of `main` in `#app`'s layout, not `position: sticky` — deliberately simpler, no scroll-container edge cases to get wrong. Distinct from the toolbar above the tab bar (global mix Play all/master volume, app-wide): the sticky bar is per-tab, for controlling whatever's local to that specific tab (e.g. the Remix plugin's own trim preview, see below) — only the active tab's sticky section is shown, and the shared bar itself hides entirely for a tab that doesn't provide one (like the Mixer, which has no single "current preview" the way Remix does). Same lazy-mount-once-then-show/hide lifecycle `mount` already has, not remounted on every tab switch.

**Where plugins live**: `plugins/<id>/` at the repo root for bundled/official plugins (packaged into the app via `electron-builder.yml`'s `extraResources`), and `<userData>/plugins/<id>/` for user-installed ones (parallel to Obsidian's `.obsidian/plugins/`). `src/main/plugins/registry.js` scans both and merges them; on an id collision, bundled wins. Presence in either directory *is* enabled — there's no enable/disable toggle UI in v1 (disable by moving the folder out).

**How loading actually works**: `plugin://<id>/<path>` is a privileged `standard` Electron scheme (registered in `main/index.js`, handled in `src/main/plugins/protocol.js`) serving a plugin's own files as real ES modules — `PluginLoader.js` in the renderer does `await import(\`plugin://${id}/${manifest.main}\`)`, which resolves relative imports between a plugin's own files correctly and shows real filenames/breakpoints in DevTools. This directly extends the same pattern `sound://` already established for serving local files into the sandboxed renderer.

**Security posture — split by process**:
- Renderer-side plugin code (`manifest.main`) is exactly as sandboxed as core code — no `require`, no `ipcRenderer`, only the curated `app` object (`{ tabs, settings, noctivago, plugin }`) it's constructed with. `app.noctivago` is `window.noctivago` handed through wholesale (already curated/whitelisted) — no per-plugin capability scoping in v1, any enabled plugin can call any core API, matching Obsidian's own trust model closely enough not to need more yet.
- Main-process plugin code (`manifest.mainProcess`, opt-in) is ordinary trusted Node — same trust level `src/main/*.js` already has — loaded via `src/main/plugins/invoke.js`. This is the only place a plugin gets real power (spawn ffmpeg, touch disk), reached from the renderer via one generic `api.plugins.invoke(pluginId, method, ...args)` rather than each plugin needing its own hand-written IPC channel in `ipc.js`.
- This is not real code sandboxing — a `mainProcess` plugin still has full Node power once opted into, same as Obsidian's actual model. Trust boundary remains "the user reads/trusts plugin source before installing," just scoped to a smaller, more visible manifest field than "the whole plugin."

**Explicit non-goals for v1** (deferred, not designed): command palette, ribbon icons, per-plugin capability scoping, persistent per-plugin data storage. (The settings-page API and enable/disable UI arrived with the Settings window, below.)

### Settings window, enable/disable, Restricted mode

Step 1 of the Obsidian-style store rework (plan: the owner's `Plugin Store Plan.md` note). Settings is a React screen in `src/renderer/settings/` (`domain/` + `components/`), mounted into `#settings-modal` by `settings/index.jsx`. The core renderer builds JSX through electron-vite's esbuild (`esbuild: { jsx: 'automatic' }`), no `@vitejs/plugin-react`. Sidebar: **Options** (General, Library, Core plugins, Community plugins), then one page per loaded plugin that called `app.settings.addPage({ title, mount(container), unmount? })`, grouped under Core or Community plugins. `hello-world` adds one as the example.

- **Core plugins** = bundled (`source: 'bundled'`); **community plugins** = anything in `<userData>/plugins/`. Every plugin has a toggle, saved as the `disabledPlugins` setting.
- **Restricted mode** (`restrictedMode` setting, on by default) keeps third-party community plugins from loading or installing. **Official** plugins are exempt: a store install writes `<plugin>/.origin.json` (`{ repo }`), and a repo under the `Venari-Hunt` owner counts as official. A hand-dropped folder has no origin, so it's third-party. The rules are pure, in `src/shared/pluginEnablement.js` (`test/pluginEnablement.test.js`); `store.js`'s `install` enforces them too, not just the UI.
- **Applies on restart.** `registry.js` freezes the loaded set the first time the renderer calls `plugins:list`; `plugins:describe` reports each plugin's saved `state` and whether it's `loaded`, and the window shows a Restart banner when they differ. `invoke.js` refuses main-process calls to a plugin that isn't loaded.
- The Plugins tab is gone: its UI is now the **Browse** window on the Community plugins page (`components/BrowseModal.jsx`), which also shows an Official badge and blocks third-party installs while Restricted mode is on.

### The plugin store (Settings > Community plugins > Browse)

Step 4 of the React plan, modeled directly on Obsidian's community plugins. **The list** is `community-plugins.json` in the separate repo `Venari-Hunt/noctivago-plugins` — an array of `{ id, name, author, description, repo }`; a plugin gets listed by a reviewed PR there, and the app reads it from `raw.githubusercontent.com` on `main`. **The files** come from the plugin author's own repo: the latest GitHub Release must have `manifest.json` plus every file it names (`main`, optional `styles`, optional `mainProcess`) as release assets. Assets have no folders, so a store plugin's manifest must name plain top-level file names. Downloads use `github.com/<repo>/releases/latest/download/<file>`, which redirects straight to the asset without touching the rate-limited GitHub API (60 requests/hour unauthenticated).

Split like everything else: `src/main/plugins/store.js` does the network and disk work behind `window.noctivago.pluginStore` (`list`, `checkLatest`, `readme`, `install`, `uninstall`, `restartApp`); the pure checks (list-entry validation, stats validation, asset names, id match, version compare) are in `src/shared/pluginStore.js`, unit-tested in `test/pluginStore.test.js`. The UI is core, in `src/renderer/settings/components/`; it used to be the bundled `plugins/plugin-store` tab.

**Browse window (step 2 of the store rework).** Two panes, like Obsidian's: `BrowseModal.jsx` has search, sort (Most downloaded, Name, Recently updated) and Installed only over a list of `StoreListItem.jsx`; `PluginDetail.jsx` shows the chosen plugin's facts, Install / Update / Enable switch / Options / Uninstall, and its README. Below 640px wide it shows one pane at a time with a Back button. Sorting and filtering are in `domain/storeBrowse.js`.
- **Download counts** come from `community-plugin-stats.json` in `noctivago-plugins`, Obsidian's shape (`{ "<id>": { downloads, updated, "<version>": count } }`), read alongside the list. It's optional: a missing or bad file just shows 0 downloads. `.github/workflows/stats.yml` there runs `scripts/update-stats.mjs` daily: it sums each listed repo's release download counts (per release, the most-downloaded asset other than `manifest.json`, since update checks also fetch that) and commits the file if it changed. A repo that fails to load keeps its previous numbers.
- **README** is `raw.githubusercontent.com/<repo>/HEAD/README.md`, capped at 200 KB. Anyone can write a README, so it is never rendered as HTML: `domain/markdown.js` parses it into blocks and inline pieces that `components/Markdown.jsx` turns into React elements. Raw HTML tags are dropped (`<script>`/`<style>` with their contents), images become links, relative links resolve to the repo on GitHub, and only http(s) links survive (`safeHref`). Tests: `test/storeBrowse.test.js`.
- **Update all** appears on the Community plugins page after Check for updates finds any; it installs them one at a time.
- Dev testing: `NOCTIVAGO_PLUGIN_STATS_URL` overrides the stats file, and `NOCTIVAGO_PLUGIN_RELEASE_BASE` also serves `README.md` from `<base>/<repo>/README.md`.

- **Install** takes only an id from the renderer and looks the repo up in the list it fetched itself, so the renderer can't point an install at an arbitrary repo. The downloaded manifest must pass `validateManifest` and have the same id as its list entry. Files go into `<userData>/plugins/.staging-<id>/` and are renamed into `<userData>/plugins/<id>/` only when all of them arrived; `registry.js` skips dot-folders, so a leftover staging folder is never loaded. An id that a bundled plugin already uses can't be installed or removed (bundled wins in the registry anyway).
- **`mainProcess` warning**: the tab checks each listed plugin's latest manifest when it opens, and a plugin with a `mainProcess` module (or one whose manifest couldn't be checked) needs a second "Install anyway" click, since that code runs as trusted Node.
- **Updates**: the same check compares the latest release's `version` with the installed one (`compareVersions`, prereleases sort before their release) and offers "Update to vX". An update is a reinstall into the existing folder.
- **Restart, not hot-load**: plugins load once at startup and `invoke.js` caches a `mainProcess` module, so after any install/update/removal the tab shows "Restart Noctívago" (`app.relaunch()` + `app.quit()`). `registry.js`'s cache is invalidated right away so the list shows the new state. Under `npm run dev` the relaunched app comes up blank, because the Vite dev server exits with the old process — a dev-only artifact.
- **Testing locally**: in an unpackaged build, `NOCTIVAGO_PLUGIN_LIST_URL` replaces the list URL and `NOCTIVAGO_PLUGIN_RELEASE_BASE` replaces `https://github.com` (latest-release files, `README.md` and `versions.json` from `<base>/<repo>/<file>`, an older release's files from `<base>/<repo>/<tag>/<file>`), so any static file server works as a fake list + releases.
- **App version (step 3)**: `resolveRelease` in `store.js` installs the latest release when its `minAppVersion` is at most the running app's version (`supportsApp`). Otherwise it reads `versions.json` from the plugin repo's default branch (`{ "<plugin version>": "<minAppVersion>" }`, Obsidian's shape), picks the newest version this app can run (`pickCompatibleVersion`), and downloads that release by tag (`releases/download/<version>/<file>`; the tag must equal the version, no `v`). No compatible version, or no `versions.json`, fails with "needs Noctívago X or newer". `checkLatest` reports the same resolved release, so an old app never sees an update it can't run, and `install` refuses to downgrade.
- **Release pipeline (step 3)**: `noctivago-plugins` has a reusable workflow, `.github/workflows/plugin-release.yml`. A plugin repo calls it on a tag push; it runs `npm ci` + `npm run build` when there's a `package.json`, fails unless tag = manifest `version` and `versions.json` maps it to the manifest's `minAppVersion`, then publishes `manifest.json` plus every file the manifest names as release assets. `Venari-Hunt/noctivago-sample-plugin` (a GitHub template repo, the old `hello-react` as a standalone Vite build) is the reference and was verified end to end: tag `1.0.0` published a release the dev app installed from real GitHub. Each moved-out plugin gets the same setup in step 4, as `Venari-Hunt/noctivago-<id>`.

### The Remix plugin (`plugins/editor/`, tab titled "Remix")

The first real (non-toy) plugin, and the one that validated the plugin API against an actual feature. All per-sound editing — trim points *and* filters (highpass, lowpass, gain) — lives here.

- **Live preview without touching ffmpeg**: `audio/PreviewSource.js` streams the sound the same way `LocalFileSoundSource` does (`sound://<id>`, works for any file length) but inserts a `BiquadFilterNode` (highpass) → `BiquadFilterNode` (lowpass) → `GainNode` chain before the output gain. Dragging a filter slider calls `setTargetAtTime` on these nodes directly — instant, click-free, audible feedback with zero ffmpeg round-trips. ffmpeg only runs once, on Save.
- **Save bakes trim + filters in one ffmpeg pass**: reuses `loopClip.js`'s renderer (extended to accept a `filters` object and insert `-af highpass=f=…,lowpass=f=…,volume=…dB` into the ffmpeg args), rather than a second, parallel baking pipeline. The Mixer's buffer-mode eligibility check compares filters as well as loop points, so changing either without re-saving correctly falls back to streaming (still filtered — see Playback above — just with a small loop seam) instead of playing a stale baked clip.
- **Save never touches the original file**: trim points and filters are persisted as metadata (`library.js`, via `electron-store`) and applied live by both playback modes; the ffmpeg render is a disposable derived cache (`getUserData()/clips/<id>.wav`), regenerated on every Save, not an edit to the source audio. The Save button surfaces the outcome (baked / bake failed / skipped because the trim exceeds the buffer-mode cap) via a status line under the button.
- **BUG FIX, v0.1.193 — a baseline Save had no live-reconcile bridge to the Mixer.** `performSave` writes to one of two places: a preset override (`presets:updateSoundOverride`, when the open sound is a member of the preset the editing session is pinned to) or the shared baseline (`library:update*`, otherwise). Only the override branch dispatched a `noctivago:sound-override-changed` CustomEvent telling an already-mounted Mixer tab to patch its cache and `reconcileSource()` the live playing source (the same bridge `noctivago:sound-fluctuation-changed` uses for Fluctuation) — the baseline branch dispatched nothing at all, and `library:changed` (the IPC push channel `tabs/mixer/index.js` already listens for) is watch-folder-only, never fired by any of the `library:update*` handlers. So a baseline-path edit — trim, filters/EQ, crossfade, Speed/Pitch, play mode, scatter, or schedule — was correctly persisted to disk but a sound already playing in the Mixer kept its old in-memory settings until something else happened to rerun `refreshList()` (switching tabs away from Remix and back). Reported directly: disabling a scatter sound's per-shot pitch/speed range "still kept pitch randomized and also speed." Fixed by giving the baseline branch the same event bridge: it now dispatches `noctivago:sound-baseline-changed` with the full patch, and `tabs/mixer/index.js` patches `state.baselineById` (the raw cache `recomputeEffectiveLibrary()` rebuilds `state.library` from — mutating the derived `state.library` entry directly wouldn't survive the next recompute), then recomputes and reconciles, mirroring the override listener's own shape exactly. Verified live via CDP against a real dev build: seeded a live `BufferScatterSource` with a randomized scatter config, persisted a disabled config to disk (confirming the live source stayed stale, reproducing the bug), then fired the new event and confirmed the same live source instance picked up the disabled config immediately. In the same pass, corrected a stale doc claim just above (§ Playback mode: Loop vs. Random Interval) that still described pre-v0.1.105 behavior (pitch `0`/`0` "secretly" meaning fully random) — that was fixed by v0.1.105's explicit `pitchFullyRandom` checkbox and the doc had never been updated to say so.
- **BUG FIX, v0.1.194 — v0.1.193's own live-reconcile bridge fired too early and permanently downgraded the sound's playback quality.** `performSave`'s call order is: (1) persist the edited metadata + dispatch the `sound-override-changed`/`sound-baseline-changed` bridge event, (2) *then* call `this.api.audio.renderLoopClip(...)` to actually re-bake the clip (an async ffmpeg round-trip). v0.1.193 added the bridge dispatch at step 1, before the bake at step 2 had even started — so by the time the Mixer's listener ran `reconcileSource()`, `entry.speedPitch`/`entry.filters` already reflected the new edit but `entry.loopClipSpeedPitch`/`loopClipFilters` (the *previous* bake's own recorded settings) hadn't been touched yet. `loopClipEligible()` correctly saw a mismatch and concluded the existing bake was stale, so `desiredSourceKind()` flipped from `loop-buffer` to `loop-stream` — and nothing ever flipped it back, because the real bake finishing a moment later only updated the Remix plugin's own local `this.currentEntry.loopClip*` fields, never the Mixer's separate `state.baselineById` cache. Stream mode has no live pitch-shift primitive at all (`reconcileSource`'s `'loop-stream'` branch only applies filters/loop points/Speed/crossfade — see Playback above), so Pitch silently stopped applying, permanently, for any sound edited this way — along with anything else that only ever takes effect through the baked clip (Doppler, Reverse, Noise reduction), and the loop lost its sample-accurate seam. Reported directly, several ways at once: "I change audio settings like pitch and speed and it has no results on live playback on mixer tab," Noise reduction/EQ "seemingly aren't working," and exports sounding "dramatically different from live playback" (the export always re-bakes from the true current settings, so it was the Mixer's stuck fallback that was wrong, not the export). Fixed by moving the event dispatch to fire only once the bake has actually resolved (success, failure, or skipped for being over the buffer-mode cap or not bake-relevant), and by having its payload carry a `loopClip` sub-object (`ready`/`start`/`end`/`filters`/`crossfadeSeconds`/`speedPitch`) mirroring the just-updated `this.currentEntry.loopClip*` fields. Both Mixer listeners now route that through a shared `patchBaselineLoopClip()` helper that updates `state.baselineById`'s `loopClip*` fields regardless of which event fired — necessary because the baked clip file and its bookkeeping always live on the *shared* baseline record (`library.js`'s `setLoopClipReady`, called from the same `audio:renderLoopClip` IPC handler either way), never per-preset-override, even when the edit that triggered the bake came through the override branch. Verified live via CDP against a real dev build: reproduced the exact bug (a `loop-buffer` source visibly flipped to `loop-stream` immediately after simulating the old pre-fix event timing, and stayed there even after a real matching bake completed afterward with no further event); then confirmed the fix's actual flow (metadata write → real `audio.renderLoopClip` → the now-delayed, loopClip-carrying event) correctly returned the same sound to `loop-buffer` with `loopClipEligible()` true and the new pitch reflected in `loopClipSpeedPitch`. Full 51-test suite and a clean build pass.
- **BUG FIX, v0.1.196 — two data-integrity bugs in `performSave`/its Mixer listeners, caught by self-review before either was reported.** (1) **Cross-sound save race**: `performSave` read `this.currentEntry`/`this.editingPresetId`/`this.fluctuation` *after* its `await`s (the metadata IPC writes, the ffmpeg bake) — but nothing stopped the user from clicking a different sound in the Remix picker while a save/autosave was still in flight (`loadSound()` reassigns `this.currentEntry` synchronously with no lock against an in-flight save; `_saveInProgress` only guards two overlapping `save()` calls, not a save racing a sound switch). A bake that resolved after the switch wrote its results onto the *new* sound's `currentEntry` (corrupting it with the old sound's bake data) and dispatched a Mixer event mislabeling the old sound's id under the new sound's preset context. Fixed by capturing `entry`/`savingEditingPresetId`/`savingFluctuation` once at the top of `performSave`, before any `await`, and mutating/reading only those captured references from then on; a new `stillEditingThisEntry()` guard (`this.currentEntry === entry`) gates everything that's legitimately UI-instance-scoped instead (status text, `savedSnapshot`, the Save button, the `bakedPreview` swap) so those don't stomp on whatever sound the user has since switched to. Also wrapped the `renderLoopClip` call in try/catch (normalizing a thrown rejection into the same `{ok:false}` shape a failed render already produces) so a real IPC/ffmpeg exception can't skip `notifyLiveReconcile()` and leave the Save button stuck on "Saving…" forever - the same failure class as v0.1.194, just via an exception instead of a timing gap. (2) **Preset-mismatch skipped the baseline patch**: the `sound-override-changed` listener's `presetId !== state.activePresetId` early return sat *before* `patchBaselineLoopClip` (v0.1.194's own fix), so saving an override for a preset other than the one currently loaded in the Mixer never synced `state.baselineById`'s `loopClip*` bookkeeping — even though the physical clip file (`getUserData()/clips/<id>.wav`) is shared across every preset and gets overwritten regardless of which one is active. If the stale baseline values happened to still match whichever preset *was* active, `loopClipEligible()` would wrongly report the bake valid and buffer-mode would play a clip that now actually contained a *different* preset's baked audio, with no staleness indicator. Fixed by moving `patchBaselineLoopClip` before the preset check — it always runs now, since the physical file was overwritten unconditionally; only the live-reconcile (which only matters for whatever's actually audible right now) stays gated on the active preset. Also merged the `sound-baseline-changed` listener's two separate `state.baselineById` get→spread→set round-trips into one (`loopClipPatchFields()` now returns a plain object both listeners spread into their own single `.set()`), and moved 4 new `pickBiasedValue` unit tests (added in v0.1.195) out from under `describe('Modulator', ...)` into their own top-level block, matching this test file's one-describe-per-exported-function convention. Both data-integrity fixes verified live via CDP against a real dev build (fired a save on sound A without awaiting it, immediately switched to sound B, confirmed B's `currentEntry` stayed uncorrupted and A's own bake still completed correctly; dispatched a `sound-override-changed` event with a deliberately mismatched `presetId` and confirmed `state.baselineById` still updated). Full 55-test suite and a clean build pass.
- **BUG FIX, v0.1.197 — the "Saved audio" preview toggle looked available but usually failed to actually play.** Reported directly: "never works as it should," happening on essentially every sound, with the only known workaround being a small edit followed by a re-save. Root cause found live via CDP, not by re-reading the v0.1.142/193/194 diffs (which looked correct in isolation): the toggle's own client-side gate (`savedPreviewEligible()`) deliberately only checks `loopClipReady` + a `bakedPreview` instance existing — staleness (an edit since the last bake) was intentionally *not* disqualifying, per v0.1.142's own design ("the toggle is now sticky... shows a dashed 'stale' outline rather than auto-reverting"). But the actual audio bytes for both "Saved audio" (`BakedClipPreview.js`) and the Mixer's own buffer-mode fetch come from the same `sound://<id>?variant=clip` URL, and the main process's handler for it (`getLoopClipPathForId`) ran the *strict* staleness comparison — the same one used to decide whether the Mixer can trust the cached clip at all — and returned `null` (a 404) the instant *any* live field diverged from what was actually baked, regardless of who was asking or why. For the Mixer this is inert (it already runs the identical comparison client-side in `loopClipEligible()` *before* ever choosing to fetch the URL, so it simply never asks while stale) — but Remix's "Saved audio" toggle explicitly *wants* to keep playing the last real bake through staleness, and instead got a hard 404 → `<audio>` element stuck in `DEMUXER_ERROR_COULD_NOT_OPEN`/`NETWORK_NO_SOURCE`, indistinguishable from broken. ### The Remix tab: Sound / Preset / Group modes (`plugins/editor/`, tab titled "Remix")

The Remix plugin also covers preset- and group-level editing, alongside per-sound editing. One tab, a three-pill mode switch at the top:

- **Sound mode** — the full per-sound editor: waveform + trim, Doppler, Speed/Pitch/Reverse, scatter/schedule randomization, Fluctuation (slow random volume+pitch drift), Volume envelope (drag control points on the waveform to shape volume over time), Noise gate, Noise reduction, the parametric EQ, HP/LP/Gain/Echo/Reverb filters, effect presets, undo/redo, A/B compare, autosave, and a Live-edit / Saved-audio preview toggle. None of this applies to more than one sound, so none of it shows outside Sound mode.
- **Preset mode / Group mode** — only the filter + EQ modules: HP/LP/Gain/Echo/Reverb, volume Fluctuation, the *same* parametric EQ module Sound mode uses (`EqEditor.js`'s `createEqEditorController` — one shared implementation across all three modes), effect presets, Reset filters — plus the minimal picker/membership chrome each needs (a preset `<select>`; Group mode adds a group `<select>`, "+ New group", a Members checklist, a name field, Delete, and a "Copy to preset…" picker for duplicating a group's filters/EQ/membership into another preset).

**Bus processing** lives in `src/renderer/audio/WholeMixChain.js` (a preset's whole-mix) and `SoundGroupChain.js` (one Sound Group) — each a `highpass → lowpass → EQ → gain → [parallel echo tap] → [parallel reverb tap] → fluctuation gain → brick-wall limiter` chain, installed by `AudioEngine` when a preset loads or groups change. A **Sound Group** is a named subset of one preset's sounds (`presets.js` `groups: [{id, name, soundIds, filters}]`, one group per sound max) routed through that shared chain instead of straight to `masterGain`. The Mixer's right-click menu toggles group membership without leaving the Mixer; both entry points write via `presets:updateGroups` and stay in sync through the `noctivago:sound-groups-changed` CustomEvent. A group's `filters` also supports an `occlusion` (0..1) field — `applyOcclusionToFilters` (`src/shared/constants.js`) log-interpolates the lowpass cutoff down and pushes reverb wet/size up together as occlusion increases (muffled *and* echoey reads as "behind a wall"; muffled alone just reads as quieter), combined with a manual Lowpass by taking whichever is more occluded. **BUG FIX (v0.1.215)**: reverb used to combine the same way (`max(manual, occlusion)`), which silently deadened the manual Mix/Size sliders anywhere below occlusion's own amount (at occlusion 1: Mix < 0.4, Size < 900ms) in both the live `SoundGroupChain` and the export (both call the one shared function). Reported as "reverb controls ain't working properly... something is impeding new changes from applying"; the owner's real active preset ("Rain Inside") had group "Thunda" at occlusion 1 with Mix 0.25, below the 0.4 floor, so every Mix edit from 0 to 0.4 was inaudible. The Remix-to-Mixer event bridge (`noctivago:sound-group-preview`) was checked and was fine. Reverb now uses `pushToward(manual, sliderMax, amount)` (`manual + (max - manual) * amount`, where amount is `0.4 * occlusion` for Mix and `900/4000 * occlusion` for Size; `REVERB_SIZE_MAX_MS = 4000` mirrors the Remix slider's max). That gives the same result as before when manual is 0, and output rises strictly with the manual value at any occlusion. The tradeoff: existing groups with both occlusion and manual reverb sound wetter than before. Lowpass kept `min()` (not reported; at occlusion 1 any manual cutoff above 700Hz is still dead - a known remaining dead zone). Unit-tested, including a regression test; 73-test suite and a clean build.

**Live spectrogram / status in Preset/Group mode**: a plugin has no reference to the Mixer's real `AudioEngine`, so the plugin dispatches a *synchronous* `noctivago:request-analyser` (or `request-mixer-status`) CustomEvent with a mutable `detail` object and reads it back the instant `dispatchEvent()` returns — the Mixer's listener sets `detail.node = engine.wholeMix.analyser` / `engine.groupChains.get(id)?.analyser` before returning. Safe because plugin and core renderer code share one JS realm (only the main-process boundary is actually sandboxed here).

**Export baking mirrors all of this**: `exportMix.js`'s `buildWholeMixPostChain` / `buildGroupFilterChain` / `renderGroupBuses` / `finalizeWholeMix` apply the same HP/LP/EQ/Gain/Echo/Reverb/volume-Fluctuation/occlusion a group or whole-mix carries. Reverb (`afir` convolution) and volume-Fluctuation (a baked `amultiply` gain envelope) each need their own separate ffmpeg pass; the rest is one linear `-af` chain. A per-sound loop sound's own volume **and** pitch Fluctuation bake too (`pitchEnvelope.js` → an `asendcmd` file stepping `rubberband`'s `pitch`, capped at a maximum command-file line count to stay well clear of a real ffmpeg bug in its own `asendcmd` parser on very large command files — see the ffmpeg version pinned in `package.json` before assuming this is fixed upstream), applied to its tiled full-duration track alongside the volume-Fluctuation `amultiply`; pitch-Fluctuation is per-sound only (a bus has nothing single to detune). A sound's Volume envelope bakes via the same WAV+`amultiply` machinery as volume-Fluctuation (`src/main/ffmpeg/volumeEnvelope.js`, `gainEnvelope.js`'s shared `writeWav`/`GEN_RATE`) rather than `asendcmd`, since it needs no continuous re-sampling loop — it rides along for free with every export since it bakes directly into the same short loop-clip WAV every other bake-only filter already uses.

**Export progress reporting must be wired into every real ffmpeg pass, not just the "big" ones** — `exportMix.js`'s `makeReporter` weights the Export tab's progress bar by audio-seconds of work (`step()`/`tick()`/`completePhase()`), and any pass long enough to matter that skips this looks indistinguishable from a hang: this exact bug has been hit and fixed three separate times for three different passes (v0.1.150 for the video re-encode and for Sound Group bus rendering, and again 2026-09-14 for `combineTracks`/`reduceTrackCount`'s "Merging N track groups…" pre-combine step, reported directly as a "fail log" after an export sat frozen on it for 37 real minutes). When adding a new ffmpeg-backed export phase, budget its expected seconds into `totalWorkSeconds` up front and wire its `onProgress` into `reporter.tick`/`completePhase` from the start rather than assuming a short pass — `combineTracks` had gone unwired since the pre-combine rounds were first added because each individual chunk combine had seemed cheap, until a dense enough export (243 tracks in one Sound Group) made it the single longest phase.

**BUG FIX (v0.1.210) — the "Merging N track groups…" pre-combine step wasn't just slow to *report* (v0.1.150/2026-09-14's fixes above), it was doing genuinely far more ffmpeg work than it needed to.** Root-caused from a direct owner report ("there's no way an export to audio should take this long"), not a live debugging session — the installed app wasn't running at the time, but the per-step `export-log.txt` this pipeline already writes (v0.1.154) turned out to be exactly the evidence needed: a real recent export spent 33m35s of its ~49-minute total on a single "Merging 245 track groups…" line, dwarfing every other phase combined. `reduceTrackCount` chunked `combineTracks`' input tracks by raw array position, with zero regard for each track's `.offset` (its absolute position in the export timeline) — and that array has no time locality at all, since Phase 2's `batchJobs` pool runs across every event sound's batches at once to keep concurrency saturated, so array order is really *completion* order. A ~120-track chunk drawn that way, when the export has several Random Interval/Scheduled sounds with batches spread across the whole timeline, ends up containing tracks whose offsets span nearly the *entire* export — so `combineTracks`' own `amix=duration=longest` had to render an output nearly as long as the whole export just to hold a scattering of a few seconds of real audio each, on every single combine pass. That's the exact "N × full duration" cost the v0.1.99 pipeline rewrite was built to eliminate in the first place, silently reintroduced one level up by this later pre-combine step. Made worse by `combineTracks` always hardcoding its result's `.offset` back to `0` regardless of where the chunk's content actually started, baking in leading silence from t=0 even when every track in the chunk started, say, 40 minutes in. Fixed two ways together: `combineTracks` now delays each track relative to the chunk's own *minimum* offset and returns that minimum as the result's real offset (rather than always `0`) — every consumer of `.offset` (the final mixdown, a later merge round, `renderGroupBuses`) already `adelay`s by whatever `.offset` says, so a track that's honestly positioned was already handled correctly, it just never used to *be* honest. `reduceTrackCount` now sorts a copy of its input by `.offset` before chunking, and chunks into groups of a new, much smaller `MERGE_CHUNK_SIZE` (32) rather than reusing `MAX_INPUTS_PER_PASS` (128, which stays exactly as-is for its own real job — capping the *final* pass's input count under the Windows command-line length limit, unrelated to this). Smaller, time-sorted chunks mean each combine pass only has to span its own narrow slice of the timeline instead of nearly the whole thing — more, far cheaper passes instead of few, enormous ones — and this benefit is unconditional (helps even with "Faster export" off, since it cuts total CPU work, not just wall time; concurrency on top of that is pure upside). Verified against the real bundled ffmpeg binary via two Node harnesses (no Electron needed — `resolveFfmpegPath()` just returns the raw `ffmpeg-static` path in dev): (1) a correctness pass — 48 short synthetic tracks scattered across a synthetic 900s timeline, reduced to one final track through multiple real merge rounds under the new logic, then `volumedetect`-probed at every original track's true offset (real signal, confirming the offset math threads correctly across rounds) and at known gaps between tracks (near-silence) — passed cleanly; (2) a scale pass matching the real bug's shape — one 128-track combine spanning a full synthetic hour (matching `MAX_INPUTS_PER_PASS` exactly, mirroring the real 245-track case's own first chunk) took 25.6s real ffmpeg time, versus the same 128 tracks split into 4 time-sorted 32-track chunks (`MERGE_CHUNK_SIZE`) taking 5.9s total *sequentially* (a 4.3x cut in real CPU work) — and since the real pipeline runs those 4 chunks concurrently under "Faster export" (up to `FASTER_EXPORT_CONCURRENCY_CAP`), real wall-clock for that round would drop to roughly the slowest single chunk (~1.7s), a ~15x wall-clock win on this synthetic case alone. Full 65-test suite and a clean build; not verified against a real multi-hour export end-to-end (would take hours to confirm 1:1) — the owner's next real slow export producing a new `export-log.txt` is the natural confirmation this actually lands as expected in practice.

**Export pipeline optimization pass (v0.1.211)** — owner asked for the export to be "the absolute fastest it can possibly be"; everything below was **benchmarked against the real bundled ffmpeg over repeated runs before changing anything**, and two hypotheses were measured and *rejected* rather than shipped on intuition. Rejected: (a) the FLAC `INTERMEDIATE_CODEC` is already right — `-compression_level 0` made no difference at all, and raw `pcm_s16le` is a wash overall (faster encode, but ~3x the bytes makes it *slower* to read back, and a merge pass reads 32+ inputs), so FLAC's smaller files genuinely win; (b) splitting the final mixdown into parallel time segments + concat measured only 1.73x even at 8 segments (I/O-bound, serial concat), which doesn't justify the seam/phase-alignment risk on stateful filters — the existing doc comment's skepticism about time-chunking holds up. What actually shipped, in order of measured impact: **(1) The concurrency cap.** `FASTER_EXPORT_CONCURRENCY_CAP = 4` was a fixed number justified by "a single 20-event rubberband batch was measured at ~500 MB" — a figure predating the v0.1.99 rewrite that made every batch graph `apad` only to its own span (the `EVENT_BATCH_SIZE` comment already conceded peak memory was now "meaningfully lower than even that measurement", but the cap was never revisited). Measured on the current shape: 12 concurrent 20-event rubberband batches peaked at **~1.6 GB of ffmpeg RSS in total** (~130 MB each, not 500), while a fixed 12-batch workload went from 15675ms at concurrency 4 to 7966ms at concurrency 12 — **1.97x** being left on the floor on any machine with more than 4 cores. Replaced with `resolveConcurrency()`: bounded by cores-1, by `MEMORY_BUDGET_FRACTION` (0.5) of total RAM at `PER_PASS_MEMORY_BUDGET_MB` (512) each, and by a `CONCURRENCY_HARD_CEILING` of 12 — yields 11 on a 12-core/16 GB box, and stays at 1-2 on a small machine, i.e. at or below the old behavior there. The v0.1.85 "took all my RAM" failure mode is still real, so this is still bounded, just by what the machine can take rather than a fixed guess. **(2) BUG: `pitchq=speed` was a ~38% slowdown, not a speedup.** Applied only under "Faster export" and documented as "rubberband's fast (slightly lower quality) mode", it measured *consistently slower* on this ffmpeg build across every repetition and both graph shapes this pipeline uses (20-event batch: 3250ms plain vs 4485ms with it; whole-clip speedPitch: 4900ms vs 5167ms). So the toggle meant to make exports faster was paying a real time penalty *and* requesting lower pitch quality — no tradeoff to weigh, removing it is strictly better on both axes. Removed from `exportMix.js`'s `eventBranchChain` and from `pitchEnvelope.js`'s `pitchCommandFilter` (that one runs over the whole export duration, so it's not a small saving); the now-unused `speedMode` parameter was deleted rather than left dangling. **(3) `channels=together` added to every rubberband call site** (`exportMix.js`'s new shared `RUBBERBAND_OPTS`, `loopClip.js`'s speedPitch bake, `pitchEnvelope.js`) — ~1.12x faster, and it fixes the exact defect already fixed on the live-playback side in **v0.1.112**: shifting L and R independently decorrelates them into stereo smear / comb filtering when summed to mono (`pitchStretch.js`'s own fix note describes the identical mechanism). The ffmpeg path never got that fix; this is it, and it makes export match live. Net on the hot per-event batch path vs what "Faster export" used to run: **~1.55x, at strictly better quality**. **(4) Mono sources stop being upconverted before the expensive stage.** `renderSlicedBatch`'s graph did `[0:a]aformat=channel_layouts=stereo,asplit=…`, so a mono source file — very common for one-shot SFX, and shot clips preserve source channel count since `renderClipToPath` passes no `-ac` — ran every branch's rubberband/volume/fade/adelay at 2x the samples for nothing. Moving the conversion to after the `amix` (safe: every amix input comes from that one `asplit`, so they always share a layout) measured **~1.5x** on a 20-event mono batch (2991ms → 2000ms), and is an exact no-op for an already-stereo source. Combined, the batch-placing phase — the dominant remaining cost after v0.1.210 fixed the merge phase — should land around **3x faster**, more for mono-sourced libraries. Verified against real ffmpeg: `asendcmd` + `rubberband:channels=together` still genuinely steps pitch over time (measured 440Hz early → 329Hz late on a real render, so the command file is still being honored), and the mono-passthrough batch graph produces correct stereo output at the right length with real audio at each event position and silence in the gaps. Full 65-test suite and a clean build. Not verified end-to-end on a real multi-hour export — the next real export's own `export-log.txt` is the natural confirmation.

**Fluctuation-baking optimization (v0.1.212)** — the direct follow-up to v0.1.211, driven by a real before/after `export-log.txt` pair the owner produced. v0.1.211 landed as predicted (batch-placing phase **1m48s → 34s, 3.2x**; whole export 14m01s → 8m54s, 1.57x; the log's own `up to 11 passes at once` header confirming `resolveConcurrency()`), but the same logs showed the remaining cost had moved somewhere v0.1.210/211 barely touched: **"Baking drift into a loop sound" was 57% of the export** (two sounds, 4m17s + 3m46s) with Sound Group processing another 28% — together 85%, while the newly-optimized batch phase was down to 13%. Two independent problems, both fixed here. **(1) Three full-duration passes per drifting loop sound, fused into one.** `tileLoopShotFull` wrote a full-duration tiled track, `applyPitchEnvelopeToTrack` read it back and wrote another, `applyEnvelopeToTrack` read *that* back and wrote a third - three encode/decode round-trips of a multi-GB intermediate for what is one linear chain over one stream. New `tileAndDriftLoopShot` does the whole thing in a single invocation: `-stream_loop` feeding `volume → [asendcmd+rubberband pitch drift] → [amultiply volume envelope]`, preserving the live chain's pitch-then-volume order. Verified against the real bundled ffmpeg as output-identical to the three-pass version (same length, same measured level at the same moment, pitch genuinely stepping 440→547Hz via the command file, volume genuinely drifting 9dB peak-to-trough) at 1.12x - deliberately noted as *modest*, because rubberband dominates the cost rather than the I/O, but it also stops writing two full-duration intermediates per drifting sound, real temp-disk and write-bandwidth savings on a multi-hour export. `applyLoopFluctuation`/`applyPitchEnvelopeToTrack` are deleted as dead rather than left dangling; `applyEnvelopeToTrack` stays live since a Sound Group's *bus* drift genuinely is a separate pass over an already-combined submix. **(2) The bigger win: both drift loops were sequential `for` loops.** Ungrouped drifting loop sounds baked strictly one after another (hence 4m17s *then* 3m46s for two independent renders), and inside `renderGroupBuses` each group's member loop sounds tiled one after another too - the only phases in this pipeline that never went through `mapPool`. Both now do, results written *by index* rather than pushed so mix/submix input order stays deterministic regardless of completion order. The nested case needed care: `renderGroupBuses` already runs groups concurrently, so naively giving the inner loop the full concurrency would allow concurrency² processes (121 on an 11-wide machine) - exactly the unbounded fan-out the old hard cap existed to prevent - so `perGroupConcurrency` divides the budget by group count (verified across a table of group/concurrency combinations that worst-case total stays ≈ concurrency, never squared). Progress accounting was kept honest through the fusion: the reporter budgets one tile plus one pass per active axis for a drifting sound (`fluctuationWorkSeconds`, plus the tile via `groupedLoopSoundCount` for a grouped one), so the fused pass banks `durationSeconds * (1 + activeAxes)` in one `completePhase` rather than leaving the bar permanently short of 100%. Also in this release, owner-requested after comparing two logs by hand: **`export-log.txt` now opens with a `Noctívago vX.Y.Z — export log — <ISO date>` header**, stamped in `ipc.js`'s `export:writeLogFile` from `app.getVersion()` so it reflects the real running build and can't drift from it. Full 65-test suite and a clean build; the next real export's log is the confirmation.

**Tape-style pitch-drift baking + a Sound Group timing regression fix (v0.1.213)** — driven by the first version-stamped log (`v0.1.212`, 1-hour "Rain Inside" export, 7m28s total: Sound Group processing 3m26s = 46%, "Baking drift into 2 loop sounds" 3m22s = 45%). The owner picked both follow-ups offered: (A) Sound Group processing, no sound change, and (B) switch export pitch drift to tape-style. **(B) Varispeed pitch drift.** The live Mixer applies a buffer-mode loop sound's pitch Fluctuation through `AudioBufferSourceNode.detune`, which the Web Audio spec folds into the node's computed playback rate (the codebase already says so in `pitchStretch.js`'s header) — so live drift is tape-style (pitch and speed together), while exports baked it with `asendcmd`+`rubberband` (pitch only). That mismatch was also ~all of the drift phase's cost. New `src/main/ffmpeg/varispeedCore.js` (Electron-free so `test/varispeedCore.test.js` — 6 tests — can run it: rate-1 reproduces the tiled clip sample-for-sample, rate-2 doubles the heard frequency, the rate follows the curve over time, the loop seam wraps without a jump, gain + cross-block state are exact, bad input throws) reads the short decoded loop clip at a time-varying, linearly-interpolated rate (matching Chromium's own `AudioBufferSourceNode` interpolation), fed by `pitchEnvelope.js`'s new `samplePitchRatios` (same walk as before, expressed as rate multipliers). `exportMix.js`'s `tileAndDriftLoopShot` decodes the clip once (`decodeClipToFloat32`, streaming, abandoned early past `MAX_BUFFER_CLIP_SECONDS`), then `renderVarispeedDrift` pipes one-second Float32 blocks into ffmpeg via the new `runFfmpegWithStdin` (in `runFfmpeg.js`; honors stdin backpressure, rejects writes once ffmpeg has exited, kills ffmpeg if generation throws), yielding to the event loop between blocks so the main process stays responsive; ffmpeg only applies the volume envelope (if any) and encodes. This replaces **both** the full-duration tile pass and the rubberband pass. Measured on a real 1-hour bake: **180.1s → 8.2s (21.9x)**, identical length. A clip longer than `MAX_BUFFER_CLIP_SECONDS` (which live can't buffer either) falls back to the previous fused rubberband pass, so `renderPitchCommandFile`/`pitchCommandFilter` stay live as that fallback. Known and deliberately left alone here: **stream-mode** live pitch drift (`SoundSource.js`, loop regions over 600s) rode `playbackRate` with the browser's default `preservesPitch=true`, so it was a tempo wobble with no pitch change. Fixed in v0.1.225 (see § Playback). **(A) Sound Group processing — and a real regression from v0.1.210.** Reading the owner's actual preset (read-only, `%APPDATA%\noctivago\presets.json`/`library.json`) showed the 3m26s wasn't the bus passes at all: group "outside" contains "acampamento sons", a 75s loop with pitch drift, baked *inside* the group step with rubberband (~3 min) — now covered by (B). The bus passes themselves are cheap: a synthetic 1-hour bus with 24 members + filters + a 1.2s reverb + volume drift took 24.3s sequential, and fusing all four passes into one graph measured only **1.34x** — not worth duplicating `applyReverbPass`'s graph inline, so that fusion was deliberately *not* done. While tracing that path, found that **v0.1.210's `combineTracks` change broke Sound Groups**: v0.1.210's entry above claims every `.offset` consumer already honored it, but `renderGroupBuses` passed the combined track to `applyGroupFilters`, which read it as starting at 0 and returned offset 0 — so a group made only of Random Interval/Scheduled sounds was pulled earlier by its first event's time (any loop-sound member, being offset 0, masked it, which is why v0.1.210's harness and v0.1.212's grouped-drift check never caught it). Reproduced first against the real `exportMix()` (shots scheduled at 30s/60s came out at 0s/30s, with and without group reverb and group volume drift), then fixed: `applyGroupFilters` folds `track.offset` in as a leading `adelay` inside the pass it already runs at full length (no extra ffmpeg work), and `renderGroupBuses` now skips the combine for any lone member rather than only an offset-0 one. **Verification harness worth reusing:** the real `exportMix()` runs under plain Node with Electron stubbed via a module resolve hook (`node --import ./register.mjs`, where the hook maps `'electron'` to a stub exporting `app` with `getPath`/`isPackaged`/`getVersion` — every module in the export's dependency tree imports only `app`). Passed: ungrouped drift (varispeed), grouped drift (varispeed via the group bus), a 610s clip (rubberband fallback) — each exactly 120s long, progress reaching 100%, pitch measurably moving, no temp files left behind — plus the group-timing regression in all three group configurations. Full 71-test suite and a clean build. Expected on the owner's preset: the two ~3.5-minute phases drop to seconds each.

**Export destination filename** (v0.1.192): `ipc.js`'s `export:pickDestination` still auto-creates a per-preset subfolder named after the preset alone (so re-exporting the same preset lands in the same place), but the *file* inside it now carries more than just the preset's name — the Export plugin appends the video kind (when exporting video at all) and a compact export length, e.g. `Rainy Night - Black screen - 9h.wav` (inbox request). `fileName` is a new, separate param from `defaultName` (still the bare preset name, used only for the folder) on that same IPC call; the video's own filename automatically follows since `exportMix.js` derives it by swapping the audio path's extension for `.mkv`.

**`plugins/editor/` is self-contained** by the `plugin://` path-traversal guard — it carries its own bundled copies of `AudioEngine.js`, the waveform-drawing code, `LoopEditor.js`, `Modulator.js`, `NoiseGate.js`, `util/time.js`, and `MAX_BUFFER_CLIP_SECONDS` — duplicated from core, not shared. Keep the copies in sync if core's change.

## Plugin ecosystem note

`plugins/export/` (mix export/rendering to a file) and other first-party plugins follow the same self-contained, `plugin://`-loaded pattern described above. See each plugin's own `manifest.json` and `index.js` for specifics — the patterns described for the Remix plugin (self-contained copies of shared logic, live-preview-vs-bake split, staleness checks reusing the `filters` object) generalize to any plugin doing similar work.
