## Watch folders

`src/main/watchFolders.js` auto-imports any audio file dropped into a folder the user has registered (`library.js`'s `addWatchedFolder`/`listWatchedFolders`), via `fs.watch` while running and a rescan (`library.js`'s `scanWatchedFolder`) on every startup to catch anything that arrived while the app was closed (`fs.watch` only reports live changes). A newly-seen file waits for its size to stop changing across two spaced checks before importing (`checkStable`), so a large file still mid-copy-in isn't imported truncated.

**Subfolders are watched recursively and interpreted as tags (v0.1.198)**, owner-requested to mirror the existing manual "Add folder as tag" dialog but automatically and per subfolder level rather than one flat tag the user types for a whole flat root: `<watched root>/Rain/Heavy/thunder.wav` gets tagged both `Rain` and `Heavy`; a file dropped directly into the watched root itself gets no tag (nothing to derive, matching the manual dialog's own requirement that the user supply one). `src/main/watchFolderTags.js`'s `tagsForWatchedFile(rootPath, containingDir)` is the one small pure function this rule lives in — split out of `library.js` specifically because `library.js` constructs a real `electron-store` `Store` at module load, which can't be imported by a plain `node:test` run outside Electron; keeping the actual path logic in its own dependency-free module is what makes it unit-testable at all (`test/watchFolderTags.test.js`). The live watcher passes `{ recursive: true }` to `fs.watch` (well-supported on Windows, the only platform this app targets) and derives tags from the relative path Windows hands back in the callback. Only ever tags a file at import time — an existing sound already in the library keeps whatever tags it has and is never retroactively re-tagged if later moved between subfolders, matching how a watched folder never touches a sound it's already imported (`importIfNew`'s own dedup-by-path check). Verified live via CDP against a real dev build with a real nested folder (root file, one level, two levels) — the initial scan tagged all three correctly, and a file dropped into a subfolder while the app was already running was picked up by the live recursive watcher with the correct tag, matching the initial-scan behavior exactly. Full 60-test suite (5 new) and a clean build.

**Hardened initial-scan walk against a folder cycle and against blocking the main process (v0.1.201)**: the initial scan (`scanWatchedFolder`, run both when a folder is first added and, via `startWatching()`, on every app startup) originally walked the whole subtree in one `fs.readdirSync(path, { recursive: true, withFileTypes: true })` call — flagged in a self-review (not a reported bug) as having two latent weaknesses on a large or unusual real folder: (1) `{ recursive: true }` has no cycle protection, so a Windows directory junction or a OneDrive "placeholder" reparse point pointing back at one of its own ancestors would make it walk forever; (2) it's fully synchronous, so a very large or deep folder would block the main process's event loop (and every pending IPC call) for the whole scan. `src/main/folderWalk.js`'s `walkFilesRecursive(rootPath, onFile)` replaces it: an async, `fs.promises`-based depth-first walker that resolves each directory's real (symlink/junction-resolved) path via `fs.realpath` and skips one it's already visited, and yields to the event loop (`await new Promise(setImmediate)`) between directories so a big scan is chunked rather than one long freeze. Its own dependency-free module (same reasoning as `watchFolderTags.js`) so `test/folderWalk.test.js` can unit-test it directly against a real filesystem, including a real Windows junction cycle (`fs.symlinkSync(..., 'junction')`, which doesn't require admin rights) — confirms the walk terminates and doesn't double-count files rather than just trusting the logic by inspection. `scanWatchedFolder` and `addWatchedFolder` are now both `async` as a result.

**Manual "Add folder as tag/preset" import now matches watch-folder import too (v0.1.203)**: `addFolderSounds` (`library.js`) used to be a flat, single-level `readdirSync` with no tag derivation at all - it now reuses the same `walkFilesRecursive` + `tagsForWatchedFile` treatment `scanWatchedFolder` already has, so both the "Add folder as tag" and "Add folder as preset" dialogs (`tabs/mixer/index.js`) pick up nested files and per-subfolder tags automatically, the same way a watched folder does. Resolved the one open design question this left behind: whether the dialogs' own explicit typed tag should apply on top of the new auto-derived subfolder tags or replace them - both call sites already applied their tag *additively* (`updateTags(id, [...entry.tags, tag])`, pre-dating this change), so the answer was already implicit in the existing code rather than a real toss-up: a folder named "Rain" containing a "Heavy" subfolder now ends up tagged "Rain" (typed) *and* "Heavy" (derived), never a forced choice between them. `addFolderSounds` is `async` now for the same reason `scanWatchedFolder` is. Verified live via CDP against a real dev build with a genuine nested test folder (root file, one level, two levels) - `addFolderSounds` alone produced the correct per-file tags, and simulating the dialog's own additive `updateTags` call on top confirmed the explicit tag layers correctly rather than overwriting. Full 64-test suite (unaffected - this path has no existing unit coverage, mirrors `scanWatchedFolder`'s own already-tested logic) and a clean build.

**BUG FIX, v0.1.205 — self-review pass over v0.1.201-204 (8 parallel finder agents) caught a real data-integrity bug in v0.1.203's own `addFolderSounds` change, plus two smaller robustness gaps, none reported.** (1) `addFolderSounds` re-inlined `importIfNew`'s own filter/`addSound`/`updateTags` steps line-for-line instead of calling it, which silently dropped `importIfNew`'s `hasSoundForPath` dedup check that `scanWatchedFolder` already relies on for exactly this reason (a watched-folder rescan needs to be a no-op on files it's already imported). Re-running "Add folder as tag" or "Add folder as preset" on an already-imported folder created a full duplicate set of library entries instead of skipping them. Fixed by having `addFolderSounds` call `importIfNew(filePath, keepCopy, tagsForWatchedFile(...))` directly, the same way `scanWatchedFolder` already does — one line replaces four, and the dedup comes back for free. (2) `folderWalk.js`'s `walkFilesRecursive` called `onFile(dirent, dirPath)` with no try/catch — a single file throwing synchronously inside it (a permission error, a file deleted mid-scan, disk full mid-copy) propagated up through every pending recursive `walk()` frame and aborted the *entire* remaining tree, not just that one file, silently dropping every file after it — for both a manual folder import and a watched-folder background rescan. Wrapped in a quiet catch matching the file's own existing `realpath`/`readdir` failure handling, plus a new regression test (`test/folderWalk.test.js`) proving one throwing file doesn't stop the rest of the walk. (3) The two "Add folder" dialogs (`tabs/mixer/index.js`) had no try/catch around the `addFolderSounds` IPC call — an unexpected rejection left the Confirm button disabled and the status stuck on "Adding sounds…" forever, with no way out but Cancel; now caught, the button re-enables, and a plain error message shows. Also fixed the stale "No audio files found directly inside that folder" copy in both dialogs (accurate for the old flat scan, wrong since v0.1.203 made it recursive). Two smaller bugs in the new Browse Sounds plugin from the same review: a failed search wiped whatever results were already on screen instead of preserving them (a real regression from the old dialog's own behavior, introduced when the clear-results call moved earlier in the new plugin's `search()`); and `loadMore()`'s auto-triggered infinite-scroll request had no staleness guard against a fresh search starting before it resolved, which could append a stale query's cards onto a new query's grid — fixed with a monotonic request-id counter, the same shape a debounce/cancellation guard elsewhere in the app already uses. Also hardened an unguarded `sound.avgRating.toFixed(1)` (only checked `numRatings > 0`, not that `avgRating` itself was non-null) found in the same pass. `addFolderSounds`'s dedup fix relies on `importIfNew`, which is already proven via `scanWatchedFolder`'s real production usage — not independently re-verified live via CDP this pass (would have needed a from-scratch Electron-stub test harness this repo doesn't have yet), verified instead via the full 65-test suite (1 new) and a clean build.
