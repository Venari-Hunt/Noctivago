# Noctívago

Windows desktop ambient sound mixer, inspired by the Linux app [Blanket](https://github.com/rafaelmardojai/blanket) (not a port — Blanket is GTK/Linux-only). Electron + vanilla JS/DOM (no UI framework). Original MVP spec: `C:\Users\jluca\.claude\plans\ok-i-m-fine-with-hidden-lemur.md`.

The user (owner of this project) is not a developer — explain setup steps explicitly, don't assume familiarity with the toolchain.

## Running it

```
npm install
npm run dev
```

Two environment quirks that show up in fresh shells on this machine (both needed before `npm`/`node`/Electron will work):
- `node`/`npm` aren't reliably on `PATH` in every shell — `$env:Path += ";C:\Program Files\nodejs"` if `node -v` fails.
- If launching Electron produces `Cannot read properties of undefined (reading 'whenReady')`, an inherited `ELECTRON_RUN_AS_NODE=1` env var is forcing Electron to run as plain Node. Clear it: `Remove-Item Env:\ELECTRON_RUN_AS_NODE`.

`ffmpeg-static`'s postinstall (which downloads the actual ffmpeg binary) sometimes gets skipped by npm's script-allowlist prompt — if ffmpeg-dependent features (waveform, loop clips) fail, check `node_modules/ffmpeg-static/ffmpeg.exe` exists; if not, run `node node_modules/ffmpeg-static/install.js`.

Under `npm run dev` with more than one display connected, `src/main/index.js`'s `devWindowPosition()` opens the window directly on the highest-numbered display rather than the default (primary, centered) position — the owner keeps working there (gaming, etc.) while a dev session runs and doesn't want a window popping up over whatever's already on screen. Computed *before* window creation (passed as `x`/`y` to the `BrowserWindow` constructor), not moved after the fact — an after-the-fact move still means the window visibly flashes on the primary display first. Gated on `!app.isPackaged`, so a real installed build is never affected.

## Architecture

- `src/main/` — Electron main process.
  - `index.js` — window creation, custom `sound://` protocol (serves either the original file or a rendered loop clip, see below) and `plugin://` protocol (serves plugin files, see Plugins below).
  - `ipc.js` — IPC handlers.
  - `library.js` — registered sound files, persisted via `electron-store`.
  - `presets.js` — saved mixes.
  - `ffmpeg/` — ffmpeg integration (see below). `runFfmpeg.js` is the reusable spawn wrapper; `ffmpegPath.js` resolves the bundled binary; `loopClip.js` and `waveformPeaks.js` are its two current consumers.
  - `plugins/` — `registry.js` (scans + caches bundled/user plugin manifests), `protocol.js` (`plugin://` handler + path-traversal guard), `invoke.js` (dispatches `plugin:invoke` IPC to a plugin's own main-process module).
- `src/preload/index.js` — contextBridge API exposed to the renderer as `window.noctivago` (namespaces: `library`, `presets`, `audio`, `plugins`).
- `src/shared/constants.js` — plain constants imported by both main and renderer (e.g. `MAX_BUFFER_CLIP_SECONDS`).
- `src/renderer/` — plain JS/DOM UI, no framework.
  - `core/TabHost.js` — tab bar + lazily-mounted `<section>` per tab.
  - `core/PluginLoader.js` — discovers plugins via IPC, dynamically `import()`s each one, registers its tab(s).
  - `tabs/mixer/index.js` — the entire sound mixer (was `main.js` before the plugin-architecture rework), registered as the first tab via `mount(container)`.
  - `audio/AudioEngine.js`, `audio/SoundSource.js` (streaming playback), `audio/BufferSoundSource.js` (buffer/gapless playback).
  - `ui/*.js` — SoundList, SoundRow, PresetsModal (mixer-specific, used only by `tabs/mixer/`). Trimming/filtering UI (`LoopEditor.js`, waveform drawing) used to live here but moved to the Remix plugin — see below.
  - `main.js` — now a tiny bootstrap: creates the `TabHost`, registers the Mixer tab synchronously, then calls `loadPlugins()`.

### Playback: two modes, chosen automatically per sound

**Stream mode** (`LocalFileSoundSource`, the default): each sound plays through **two** `<audio>` elements of the same file (`src="sound://<id>"`), one active and one standby, each piped through its own crossfade `GainNode` and then summed into the shared chain `→ highpass BiquadFilterNode → lowpass BiquadFilterNode → EQ chain → filter GainNode → per-sound GainNode → master GainNode` (echo taps off filter GainNode as before). The filter nodes apply the sound's saved highpass/lowpass/gain/EQ settings (same chain shape as the Remix plugin's live preview) — this is what makes filters audible even for sounds that never qualify for a baked buffer clip (see below). The `sound://` protocol hand-rolls HTTP Range support via `fs.createReadStream` (Electron's `net.fetch` on `file://` URLs was found to silently ignore Range headers in this Electron version — don't assume it works, verify). This is what makes arbitrarily long files (hours) playable at all without loading them into memory.

Looping is a two-element crossfade at the seam (`v0.1.101`): a `requestAnimationFrame` `_tick` boundary-check watches the active element's `currentTime`; when it reaches `loopEnd - fade*speed` (the `*speed` since `fade` is wall-clock — added `v0.1.102`), the standby element (pre-seeked to `loopStart`) starts playing and the two crossfade GainNodes ramp in opposite directions over `fade` seconds, then a `setTimeout` (`fade*1000 + 40`) swaps their roles — the retired element is paused and rewound to `loopStart` to become the next standby. `fade` = `entry.crossfadeSeconds` (the *same* per-sound Remix "Loop crossfade" slider that drives the baked-clip crossfade; `null` → a local `DEFAULT_STREAM_CROSSFADE_SECONDS = 0.2` mirroring `loopClip.js`'s `DEFAULT_CROSSFADE_SECONDS`), clamped to a quarter of the loop region. **An explicit `crossfadeSeconds: 0` falls back to the pre-`v0.1.101` behavior**: a plain `currentTime = loopStart` hard seek-back on the single active element (not sample-accurate, audible click/gap on non-self-looping content — which is exactly why this crossfade was added). The seam trigger is still rAF-polled `currentTime` (documented imprecise), but a ~200ms crossfade masks that jitter far better than the hard seek did — this is the streaming counterpart of buffer mode's baked tail/head crossfade, minus the sample-accuracy. This was the ranked backlog's "hybrid bridge-clip seamless loop" item; the owner picked this simpler dual-element approach over a pre-baked ffmpeg bridge segment when it was surfaced (no ffmpeg round-trip, no disk cache / staleness tracking, filters stay live, loop region stays exact, and it's automatic rather than opt-in). `pause()` mid-crossfade finalizes the swap synchronously so resume continues cleanly from just past the loop point; `dispose()` tears down both elements + both source nodes + both crossfade gains. Cost: two `<audio>` elements (and two `MediaElementAudioSourceNode`s) per stream-mode loop sound — negligible in practice since most sounds get baked into buffer mode anyway and only a genuinely long *loop region* (>600s) keeps a sound in stream mode for real.

**Buffer mode** (`BufferSoundSource`): whenever the user trims + sets filters and hits Save in the Remix plugin (see below), ffmpeg renders *just that loop region*, with any highpass/lowpass/gain filters baked in via `-af`, out to a small WAV (`src/main/ffmpeg/loopClip.js`, `getUserData()/clips/<id>.wav`) — but only if the region is ≤ `MAX_BUFFER_CLIP_SECONDS` (600s/10min, in `src/shared/constants.js`). Since the clip is now short regardless of how long the source file was, it's fully decoded client-side (`decodeAudioData`) into a native `AudioBufferSourceNode` with true `loop=true`/`loopStart`/`loopEnd` — sample-accurate, click-free. `tabs/mixer/index.js`'s `loopClipEligible(entry)` checks `entry.loopClipReady` + that the clip's recorded loop points *and* filters still match the entry's live ones (4-way staleness check, since either changing without re-saving should fall back to streaming) before trying buffer mode, and falls back to stream mode on *any* failure (missing ffmpeg, corrupt clip, decode error) — buffer mode is strictly additive and only ever affects loop-seam smoothness, never whether filters apply, never required for the app to work.

`BufferSoundSource.pause()` tracks elapsed offset manually (`AudioBufferSourceNode` is one-shot — can't be pause/resumed like `<audio>` can) so resuming continues from the same position rather than restarting, matching stream mode's behavior.

**Getting a sound into buffer mode**: the default is lazy — `tabs/mixer/index.js`'s `maybeAutoBake` bakes a full-file clip the first time an eligible, never-baked sound actually plays. A Settings toggle (`eagerlyBakeOnImport`, off by default) makes this eager instead: `library.js`'s `maybeEagerBakeOnImport`, fired fire-and-forget from `addSound()` — the single choke point every import path (single file, folder-as-preset, folder-as-tag, watch-folder) already funnels through — probes the file's real duration via ffmpeg directly (`loopClip.js`'s `probeDurationSeconds`, since a fresh import has no `durationSeconds` yet; that's normally only learned lazily via the `<audio>` element's own `loadedmetadata`) and bakes immediately, before the sound is ever played. Same `MAX_BUFFER_CLIP_SECONDS` cap and bake call as the lazy path — this only changes *when* the first bake happens, not how.

### Playback mode: Loop vs. Random Interval ("scatter")

Every sound's `playMode` (`'loop'` default, or `'scatter'`, in `library.js`) picks between the two source families above (continuous loop) and a second pair — `BufferScatterSource`/`StreamScatterSource` (`src/renderer/audio/ScatterSoundSource.js`) — that instead replay the trimmed clip as one-shots on a randomized gap (`entry.scatter.minGapSeconds`/`maxGapSeconds`) with a randomized pitch each time (`entry.scatter.minPitchSemitones`/`maxPitchSemitones`; both left at 0 means *fully* random pitch per replay, not "no shift" — an explicit, deliberate special case). This is the game-engine "scattered ambience emitter" pattern (Wwise Random Container, FMOD's Scatterer Instrument, Unity's Audio Random Container) — researched before implementing, per the standing instruction in [[feedback_research_before_complex_tasks]] — for a short, event-like sound (a creak, a bird call) inside a longer ambient mix, rather than looping it back-to-back. `tabs/mixer/index.js`'s `desiredSourceKind(entry)` crosses `playMode` with buffer eligibility into four kinds (`loop-buffer`/`loop-stream`/`scatter-buffer`/`scatter-stream`); `reconcileSource` swaps the live source whenever the desired kind or the bake itself changes, same pattern the original loop/stream swap already used.

`BufferScatterSource` uses the decoded clip's native `AudioBufferSourceNode.detune` (cents) for pitch — true independent pitch shift with zero effect on shot duration or the gap timer, a nicer primitive than the playbackRate-linked pitch/tempo coupling most non-web engines settle for. `StreamScatterSource` (the fallback for a trim too long to bake) has no such primitive on `<audio>`, so it reuses `playbackRate` the same way Speed does elsewhere in this app — a pitch shift there also changes shot tempo, a documented, accepted limitation.

Scatter-mode clips reuse `renderLoopClip` unchanged rather than a second bake pipeline: both `library.js` and `tabs/mixer/index.js` have an `effectiveCrossfadeSeconds(entry)` helper that forces the crossfade to `0` whenever `playMode === 'scatter'` (crossfade+rotation, which permanently reorders the clip's own audio to hide a *looping* wrap point, would be actively wrong for a clip that's never looped back-to-back) — `0` already means "plain trim, no rotation" in `loopClip.js`'s `doRender`, so this is a pure input-shaping trick, not new ffmpeg logic. Switching a sound between Loop and Random Interval in the Remix plugin (which owns this control, alongside trim/filters/crossfade/speed-pitch — the same "shape a sound" editor as everything else that affects the bake) naturally invalidates the old bake via the same staleness check every other trim/filter edit already goes through.

### Waveform

`src/main/ffmpeg/waveformPeaks.js` streams the *whole* original file through ffmpeg as downsampled mono float32 PCM and reduces it into `[min,max]` peaks per pixel column with O(1) memory (never buffers the decoded audio) — works for files of any length/format. This replaced an earlier renderer-side `decodeAudioData`-based approach that was capped at 30 minutes and fell back to a bare time-ruler beyond that.

**BUG FIX (canvas stretch/blur)**: the Remix trim waveform (`#editor-canvas`, drawn by `plugins/editor/audio/waveform.js`) had its internal bitmap resolution (fixed `640x160` HTML attributes) out of sync with its actual rendered CSS size (styled `width: 100%`, so it stretches to fill the panel on any normal window width) — the browser scaled the smaller bitmap up non-uniformly to fill the box, which is exactly what a user-reported "totally stretched and blurry" waveform looks like. Same root cause and same fix as the Remix EQ graph's own identical bug (see below) — `waveform.js` gained its own `resizeCanvasForDisplay()`, resizing the canvas's real bitmap resolution to its rendered CSS size × `devicePixelRatio` before every draw and scaling the context so the rest of the drawing code keeps working in plain CSS-pixel coordinates. `LoopEditor.js`'s own interaction math (drag, wheel, hit-testing) was never affected — it already worked in `rect.width`/`rect.height` (CSS-pixel space) throughout, only the *drawing* function had the bug.

**Live spectrum analyzer**: `PreviewSource.js` taps an `AnalyserNode` (never connected onward — a pure read tap) off `outputGainNode`, the single point both crossfading voices' signals combine into, so it reflects whichever voice is actually audible regardless of crossfade state. `EqEditor.js`'s `tickSpectrum(analyserNode)` is called once per frame from the same `tickPreviewPlayhead()` rAF loop that already drives the waveform playhead and sticky progress bar (no separate loop) — reads `getByteFrequencyData()` (already dB-scaled 0-255 by the Web Audio API itself, no extra scaling needed) and redraws a filled area in pink (`rgba(247, 118, 142, ...)`, matching the FL Studio "Fruity Parametric EQ 2" reference this was modeled on) connecting each linearly-spaced FFT bin's point via the graph's own log-frequency `freqToX`. Takes over from the static band-energy backdrop (above) whenever playing; `clearSpectrum()` (called on pause/stop/dispose) falls back to the static backdrop rather than freezing on the last live frame.

**Per-band filter types**: 7 bands (matches the real FL Studio reference, researched directly rather than assumed — see `noctivago_task_list` memory for the full research and the deliberate cut-list of reference features judged not worth cloning, e.g. Mid/Side processing, Linear Phase mode, phase rotation display, none of which map onto Noctívago's single-independent-sound signal flow). Each band independently one of 8 types via a `type` field on the band object (`'off' | 'lowpass' | 'highpass' | 'bandpass' | 'notch' | 'lowshelf' | 'highshelf' | 'peaking'`), selected via a `<select>` next to the Freq/Gain/Q precision fields. A lucky architecture fit: Web Audio's native `BiquadFilterNode.type` already covers 7 of the 8 shapes directly — only `'off'` is a pseudo-type (not a real biquad shape), mapped to `'allpass'` at the node level (`eqNodeType()` in both `SoundSource.js` and `PreviewSource.js`) since allpass leaves the amplitude spectrum completely unchanged, a true no-op without needing to dynamically rewire the fixed per-band node chain. `.type` isn't an AudioParam (a plain property, can't be smoothed like frequency/Q/gain) — only reassigned when it actually changes, to avoid resetting the filter's internal state on every unrelated update. Baking dispatches per band to the matching ffmpeg filter (`loopClip.js`'s `buildEqBandFilter`: `lowpass`/`highpass`/`bandpass`/`bandreject`(notch)/`bass`(lowshelf)/`treble`(highshelf)/`equalizer`(peaking), `'off'` simply omitted from the chain) — all six real filter names verified chained together in one real ffmpeg invocation before writing any app code. Only peaking/lowshelf/highshelf are true no-ops at `gainDb: 0` (their whole effect is proportional to gain); lowpass/highpass/bandpass/notch have no gain parameter at all and always shape the signal whenever selected, so they're never skipped just for looking "neutral."

### Why ffmpeg, not more JS

Both the loop-seam click and the waveform-for-long-files problems trace back to the same root cause: `decodeAudioData` on a whole multi-hour file either throws `EncodingError` or uses gigabytes of RAM (this is *why* stream mode exists at all — see git history around the original long-file rewrite). ffmpeg (bundled via `ffmpeg-static`, spawned via `child_process`, never a shell) processes files without holding them fully in memory, sidestepping that limit entirely. `runFfmpeg.js` is deliberately generic/domain-agnostic so ffmpeg-based features reuse it rather than each rolling their own spawn logic — the Remix plugin's filter baking (see below) is the first consumer beyond loop clips/waveforms.

**Packaging note:** `electron-builder.yml` has `asarUnpack: [node_modules/ffmpeg-static/**]` — required because binaries can't execute from inside an asar archive. Verified working since `v0.1.0` (real install, see Status) and re-confirmed structurally on every local `npm run build:win` run since.

### App icon

`resources/icon.ico` is not a plain PNG electron-builder auto-converts — it's hand-built by `resources/icon-src/build-ico.mjs` (run `node resources/icon-src/build-ico.mjs` from the repo root to regenerate after editing `resources/icon-src/render.html`'s SVG and re-rendering `icon-master.png`). **Why this matters**: electron-builder's own PNG→ICO conversion PNG-compresses every embedded size, but Windows only honors PNG compression for the 256px entry — sizes below that (16/24/32/48/64, exactly what the taskbar and Windows Search use) silently fall back to a generic icon if they're PNG-compressed instead of classic uncompressed BMP/DIB data. Discovered the hard way: `v0.1.13` shipped with an auto-converted icon that looked fine in most places but showed a generic icon on the taskbar and in Windows Search; confirmed via low-level PE resource inspection (`LoadLibraryEx`/`EnumResourceNames`/`FindResource` on the built `.exe`) that every size, not just 256, had been PNG-compressed. The build script now generates real BMP/DIB data (with a proper 1bpp AND mask derived from the alpha channel) for every size below 256, PNG-compressing only the 256 entry — verified by loading the result back through .NET's `System.Drawing.Icon` (Windows' own icon parser), not just by trusting the script's own logic. `src/main/tray.js` (system tray) and `src/main/index.js` (`BrowserWindow`'s `icon` option) both read the same design; the tray one stays a plain PNG since `nativeImage`-based tray icons don't have this multi-size ICO requirement.

## Plugins

The app is meant to be open-sourced with outside contributors adding functionality as plugins rather than editing core — modeled on Obsidian's plugin architecture, but **deliberately not** copying its trust model (Obsidian plugins get raw Node/Electron access; here that's split by process, see below), since this codebase has been consistently more sandboxed (`contextIsolation: true`, no `nodeIntegration`, everything served through custom protocols rather than raw file access).

**A plugin is a folder** containing `manifest.json` (`id`, `name`, `version`, `main` required; `mainProcess` optional) + a `main` entry file exporting a default class:
```js
export default class MyPlugin {
  constructor(app, manifest) { this.app = app }
  async onload() { this.unregister = this.app.tabs.register({ id, title, mount: (container) => {...} }) }
  async onunload() { this.unregister?.() }
}
```
Two real examples exist in `plugins/`: `hello-world/` (minimal working plugin) and `broken-plugin-example/` (deliberately throws in `onload()` — a regression-test fixture proving one broken plugin can't take down the app or other plugins).

`register()` also accepts an optional `mountSticky: (container) => {...}` alongside `mount` — its own section in the shared sticky bar directly under the tab bar (`#tab-sticky-bar` in `index.html`, wired in `TabHost.js`), always visible regardless of how far the tab's own content is scrolled. This is a fixed-height flex sibling of `main` in `#app`'s layout, not `position: sticky` — deliberately simpler, no scroll-container edge cases to get wrong. Distinct from the toolbar above the tab bar (global mix Play all/master volume, app-wide): the sticky bar is per-tab, for controlling whatever's local to that specific tab (e.g. the Remix plugin's own trim preview, see below) — only the active tab's sticky section is shown, and the shared bar itself hides entirely for a tab that doesn't provide one (like the Mixer, which has no single "current preview" the way Remix does). Same lazy-mount-once-then-show/hide lifecycle `mount` already has, not remounted on every tab switch.

**Where plugins live**: `plugins/<id>/` at the repo root for bundled/official plugins (packaged into the app via `electron-builder.yml`'s `extraResources`), and `<userData>/plugins/<id>/` for user-installed ones (parallel to Obsidian's `.obsidian/plugins/`). `src/main/plugins/registry.js` scans both and merges them; on an id collision, bundled wins. Presence in either directory *is* enabled — there's no enable/disable toggle UI in v1 (disable by moving the folder out).

**How loading actually works**: `plugin://<id>/<path>` is a privileged `standard` Electron scheme (registered in `main/index.js`, handled in `src/main/plugins/protocol.js`) serving a plugin's own files as real ES modules — `PluginLoader.js` in the renderer does `await import(\`plugin://${id}/${manifest.main}\`)`, which resolves relative imports between a plugin's own files correctly and shows real filenames/breakpoints in DevTools. This directly extends the same pattern `sound://` already established for serving local files into the sandboxed renderer. Verified working (including relative cross-file imports) via a throwaway spike before any of the rest was built.

**Security posture — split by process**:
- Renderer-side plugin code (`manifest.main`) is exactly as sandboxed as core code — no `require`, no `ipcRenderer`, only the curated `app` object (`{ tabs, noctivago, plugin }`) it's constructed with. `app.noctivago` is `window.noctivago` handed through wholesale (already curated/whitelisted) — no per-plugin capability scoping in v1, any enabled plugin can call any core API, matching Obsidian's own trust model closely enough not to need more yet.
- Main-process plugin code (`manifest.mainProcess`, opt-in) is ordinary trusted Node — same trust level `src/main/*.js` already has — loaded via `src/main/plugins/invoke.js`. This is the only place a plugin gets real power (spawn ffmpeg, touch disk), reached from the renderer via one generic `api.plugins.invoke(pluginId, method, ...args)` rather than each plugin needing its own hand-written IPC channel in `ipc.js`.
- This is not real code sandboxing — a `mainProcess` plugin still has full Node power once opted into, same as Obsidian's actual model. Trust boundary remains "the user reads/trusts plugin source before installing," just scoped to a smaller, more visible manifest field than "the whole plugin."

**Explicit non-goals for v1** (deferred, not designed): plugin marketplace/browser, hot-reload dev tooling, settings-tab API, command palette, ribbon icons, enable/disable UI, per-plugin capability scoping, persistent per-plugin data storage.

**Full design rationale** (alternatives considered and rejected, e.g. `executeJavaScript` injection vs. dynamic `import()`, why core doesn't route through the plugin loader itself) is in the plan file this was built from: `C:\Users\jluca\.claude\plans\snoopy-booping-sky.md`.

### The Remix plugin (`plugins/editor/`, tab titled "Remix")

The first real (non-toy) plugin, and the one that validated the plugin API against an actual feature. All per-sound editing — trim points *and* filters (highpass, lowpass, gain) — lives here now; it moved out of the core Mixer tab entirely (the old in-mixer Loop Editor modal, its canvas/waveform code, and the "Trim" button are gone from `src/renderer/` — deleted, not just unused, once nothing else referenced them).

- **Live preview without touching ffmpeg**: `audio/PreviewSource.js` streams the sound the same way `LocalFileSoundSource` does (`sound://<id>`, works for any file length) but inserts a `BiquadFilterNode` (highpass) → `BiquadFilterNode` (lowpass) → `GainNode` chain before the output gain. Dragging a filter slider calls `setTargetAtTime` on these nodes directly — instant, click-free, audible feedback with zero ffmpeg round-trips. ffmpeg only runs once, on Save.
- **Save bakes trim + filters in one ffmpeg pass**: reuses `loopClip.js`'s renderer (extended to accept a `filters` object and insert `-af highpass=f=…,lowpass=f=…,volume=…dB` into the ffmpeg args), rather than building a second, parallel baking pipeline. The Mixer's buffer-mode eligibility check compares filters as well as loop points, so changing either without re-saving correctly falls back to streaming (still filtered — see Playback above — just with a small loop seam) instead of playing a stale baked clip.
- **Save never touches the original file**: trim points and filters are persisted as metadata (`library.js`, via `electron-store`) and applied live by both playback modes; the ffmpeg render is a disposable derived cache (`getUserData()/clips/<id>.wav`), regenerated on every Save, not an edit to the source audio. The Remix plugin's Save button surfaces this outcome directly (baked / bake failed / skipped because the trim exceeds the buffer-mode cap) via a status line under the button — added after user feedback that a silent Save was confusing.
- **Self-contained by design, not by accident**: a plugin can't import files outside its own directory (enforced by the `plugin://` path-traversal guard), so `plugins/editor/` has its own copies of `AudioEngine.js`, the waveform-drawing code, `LoopEditor.js` (the drag/scrub/snap canvas controller), and `util/time.js` — duplicated from core rather than shared. This is a deliberate tradeoff matching Obsidian's "bundle your own dependencies" plugin model, not an oversight; keep it in mind if core's copies of these change and the plugin's need the same fix.
- `MAX_BUFFER_CLIP_SECONDS` (600s) is duplicated as a local constant in `plugins/editor/index.js` for the same cross-directory-import reason — keep it in sync with `src/shared/constants.js` if that value ever changes.
- **Parametric EQ**: a fixed 6-band peaking EQ, folded into the *existing* `filters` object as `filters.eq: [{freqHz, gainDb, q}, ...]` (`library.js`'s `defaultEqBands()`) rather than a new top-level field — reuses every bit of existing filters plumbing (staleness comparison, `updateFilters`, live-update paths) with zero new schema/IPC code. A scoped-down take on FL Studio's "Fruity Parametric EQ 2" (the reference screenshot this was designed from, see `noctivago_remix_eq_future` memory): fixed band count, no add/remove-node UI, and the connecting line drawn between nodes is a straight polyline through each band's own point, not the true composite biquad response curve — both deliberate cuts to keep it buildable in one pass. `plugins/editor/ui/EqEditor.js` is the draggable-node canvas (X = log-frequency, Y = gain, mouse wheel over a node = Q — no third drag axis available); `index.js` also exposes precision numeric fields (Freq/Gain/Q) for the selected band, mirroring the Start/End/Length text-input pattern next to the trim handles. Presets (Muffled/Phone/etc.) deliberately never touch `.eq` — only "Reset filters" (via `NEUTRAL_FILTERS.eq`) or a per-sound "Reset EQ" button do. Live preview inserts a chain of 6 `BiquadFilterNode`s (`type: 'peaking'`) between the lowpass and filter-gain nodes in both `PreviewSource.js` and core's `LocalFileSoundSource` (`src/renderer/audio/SoundSource.js`), same position ffmpeg's bake applies them (`equalizer=f=…:width_type=q:w=…:g=…` in `loopClip.js`'s `buildFilterChain`, verified against the real bundled binary before shipping) so preview and the real Mixer agree. **Real bug caught during verification**: the canvas's interaction math (hit-testing, drag) initially used `canvas.width`/`canvas.height` (the internal 640×140 bitmap resolution) instead of `canvas.getBoundingClientRect()` (the actual rendered CSS size, ~1319px wide here since the canvas is styled `width: 100%`) — this silently broke all dragging, since mouse coordinates and node positions were computed in two different, mismatched coordinate spaces. Fixed by following `LoopEditor.js`'s already-established split exactly: interaction math uses `rect.width`/`rect.height`, drawing uses `canvas.width`/`canvas.height` — caught by an actual CDP drag test coming back with no-op results, not by code review.
- **Sticky playback bar**: Play/Pause, a loop toggle, a progress bar/time readout, and a preview-volume slider live in `mountSticky()` (see the Plugins section above), not the scrollable panel body — always visible under the tab bar regardless of scroll position. Progress is relative to the *trimmed loop region* (`loopStart`..`loopEnd`), not the whole original file, matching what's actually being previewed/looped. The loop toggle is an icon button (`.editor-loop-icon-btn`/`-active`, an inline SVG repeat glyph recolored via `currentColor`), not the checkbox it used to be — same underlying `this.looping` boolean and `previewSource.setLooping()` call, purely a restyle plus relocation. The volume slider drives `PreviewSource.setVolume()` directly (that method already existed — nothing previously exposed it in the UI, the preview was always hardcoded to 0.7); `this.previewVolume` persists across sound switches within the tab session, same pattern `this.looping` already established, distinct from the Mixer's own per-sound saved volume. `mount()` and `mountSticky()` populate the same shared `this.els` object; ordering matters (`mount` then `mountSticky`, both synchronous, see `TabHost.js`) since `wireControls()` (called from `mount()`) no longer wires the Play/Pause or loop-toggle listeners itself — those move to `mountSticky()`'s own wiring, run immediately after.
- **EQ graph backdrop**: translucent bars behind the EQ curve showing roughly how much energy the sound actually has around six fixed reference frequencies (`library.js`'s `defaultEqBands()` frequencies, independent of wherever the user later drags a node) — a deliberately scoped-down alternative to a literal live spectrum analyzer (which would need real-time `AnalyserNode` playback + a continuous rAF redraw loop, meaningfully more scope) or a literal waveform (which wouldn't make sense on this graph's *frequency*-domain X-axis — a time-domain plot doesn't belong there, an early framing mistake caught before implementing). `src/main/ffmpeg/bandEnergy.js`'s `computeBandEnergy` runs one `bandpass`-filtered ffmpeg pass per frequency (in parallel — wall-clock cost is roughly the slowest single pass, not the sum), computing RMS in JS from the piped PCM, verified against the real bundled binary before writing any app code. Static, load-time-only analysis (`plugins/editor/index.js`'s `loadSound()`, fire-and-forget) — not tied to playback, not recomputed as the user drags EQ nodes. **Two real bugs caught during verification, not by code review**: (1) the output PCM sample rate was originally 11025Hz (Nyquist 5512.5Hz) — comfortably below the 6000Hz and 14000Hz bands, so ffmpeg's own anti-aliasing filter during the final resample was silently discarding real signal at those frequencies for *every* file, not just an edge case (confirmed: a genuinely loud real 14kHz tone measured as near-silence at 11025Hz output vs. correctly strong at 32000Hz); (2) a bandpass filter centered at or above the *source* file's own Nyquist is a degenerate configuration, not just imprecise — confirmed a low-sample-rate (22050Hz) test file spuriously reported its 14000Hz band as the *loudest* of all six for a pure 100Hz tone. Fixed by raising the output rate to 32000Hz and probing the source's real sample rate first (parsed straight out of ffmpeg's own stderr stream-info line), skipping any band at or past that file's Nyquist entirely rather than trusting a degenerate filter's output.

### The merged Remix tab (Sound / Preset / Group modes, v0.1.147)

**Preset Remix and the Mixer's Sound-Groups-management UI no longer exist as separate surfaces** — `plugins/preset-remix/` is deleted outright; everything it did now lives inside `plugins/editor/` (still id `remix`, title "Remix") behind a three-pill mode switch (Sound / Preset / Group) at the top of the tab, per the owner's own direction above. **What's genuinely shared vs. mode-specific, matching the owner's own scoping**: Sound mode is the untouched original Remix — waveform, trim, Doppler, Speed/Pitch/Reverse, scatter/schedule randomization controls, undo/redo, A/B compare, autosave, the Live-edit/Saved-audio toggle — none of that applies to more than one sound at once, so none of it appears outside Sound mode. **Live spectrogram now works in Preset/Group mode too**, closing the one piece the owner explicitly called out as more than cosmetic parity. The hard part: Sound mode's spectrum analyzer taps an `AnalyserNode` off `PreviewSource.js`'s own private preview engine (a parallel playback path that exists only for auditioning one file) — Preset/Group modes have no such thing, since there's no single file to preview; the only real signal is whatever's actually coming out of the live `WholeMixChain`/`SoundGroupChain` in the Mixer's real `AudioEngine`, which a plugin has no reference to (only the curated `window.noctivago` IPC surface + window-CustomEvent bridges, per this app's plugin trust model). Solved with a **synchronous request/response CustomEvent** (`noctivago:request-analyser`, `tabs/mixer/index.js`): the plugin dispatches with a mutable `detail` object and reads `detail.node` immediately after `dispatchEvent()` returns (listeners run synchronously in the same tick), and the Mixer's listener sets `detail.node = engine.wholeMix.analyser` or `engine.groupChains.get(groupId)?.analyser` before returning — a real live `AnalyserNode` reference handed across, safe specifically because plugin code and core code run in the same JS realm (only the main-process/Node boundary is actually sandboxed in this app, not core-vs-plugin renderer code). `WholeMixChain`/`SoundGroupChain` (`src/renderer/audio/`) each gained their own read-only analyser tap (a dedicated fixed-gain feed node off the post-limiter output, never connected onward — the exact same "decoupled from anything downstream" shape `PreviewSource.js`'s own tap already uses, learned the hard way there once before at v0.1.51 when a volume slider was shrinking the visual). A new `plugins/editor/ui/WholeMixEqEditor.js` (the old preset-remix `EqEditor.js`'s scoped-down EQ canvas, now living here) gained `tickSpectrum()`/`clearSpectrum()` copied faithfully from the main `EqEditor.js`'s own pink-fill drawing code. A separate rAF loop (`tickWholeMixSpectrum()`, distinct from Sound mode's own `tickPreviewPlayhead()`) polls the bridge every frame while Preset/Group mode is active and draws whatever comes back — `null` (the preset/group being edited isn't the one actually loaded/playing right now) correctly clears to a flat graph rather than freezing.

1. Rewiring `SoundList.js` to read `playbackState.groups` for the Mixer's own group badge (already shipped as v0.1.146) exposed a latent gap: the `noctivago:sound-groups-changed` listener updated `state.groups` but never called `render()` — previously invisible since nothing rendered off that state before, now a real "badge doesn't update after toggling membership" bug. ## Releasing and auto-update

`npm run release:win` (`electron-vite build && electron-builder --win --publish always`) builds the Windows installer and publishes it as a GitHub Release, via `electron-builder.yml`'s `publish: {provider: github, owner: joaovenari, repo: Noctivago, private: true}`. `.github/workflows/release.yml` runs this automatically on any pushed tag matching `v*` (or manually via workflow_dispatch), on `windows-latest`, using GitHub Actions' own auto-provided `GITHUB_TOKEN` (scoped read/write to just this repo via the workflow's `permissions: contents: write`) to create the release and upload the installer — no manual setup needed for this half.

**In-app update checking** (`src/main/autoUpdate.js`, `electron-updater`) checks GitHub Releases on every startup of a *packaged* build (`app.isPackaged` gate — never runs under `npm run dev`), and only ever prompts before acting: a "Download?" dialog on `update-available`, then a separate "Restart now?" dialog on `update-downloaded`. `autoUpdater.autoDownload`/`autoInstallOnAppQuit` are both `false` for exactly this reason — nothing happens silently.

**The one piece of manual setup this needs, because the repo is private:** `electron-updater`'s GitHub provider has to authenticate to read releases, and there's no config field for a token — it reads it from the `GH_TOKEN` environment variable at runtime. Baking the CI-publish token (`secrets.GITHUB_TOKEN`, broad repo-write access) into the *shipped app* would be a real credential-leak risk, so a **second, separate, narrowly-scoped token** is used instead: create a fine-grained PAT at github.com/settings/personal-access-tokens/new, scoped to only the `Noctivago` repo with read-only `Contents` permission, and add it as a repo secret named `NOCTIVAGO_UPDATE_TOKEN` (Settings → Secrets and variables → Actions). The release workflow passes it through as a build-time env var, and `electron.vite.config.js`'s `define: { __UPDATE_TOKEN__: ... }` bakes it into the compiled main-process bundle (empty string for any local/dev build, so nothing leaks into a build the user runs themselves). **Accepted risk, explicitly discussed:** this token still ships inside every installed copy of the app and could in principle be extracted by anyone who has it — acceptable per the user for now since distribution is limited to trusted people while the repo stays private ahead of a future public release.

### The Preset Remix plugin (`plugins/preset-remix/`, tab titled "Preset Remix")

**Whole-mix processing saved on a preset and heard live whenever that preset is loaded** — the long-standing `#future` "Preset Remix / whole-mix editing tab" item, built after the owner picked its shape from a two-question fork: processing set = "HP/LP/Gain now, EQ same session" (both shipped here in one release), and when-applied = "per-preset, applied on load" (not an always-on master bus). It's the *live-playback* counterpart of the Export plugin's "Whole-mix processing" section — Export bakes HP/LP/Gain+fade into a file; this applies HP/LP/Gain+fade-in **+ a parametric EQ** to everything playing.

**Data model**: a new `wholeMix` field on a preset (`presets.js`), `{ highpassHz, lowpassHz, gainDb, fadeInSeconds, eq: [...] }` or `null` when fully neutral (`normalizeWholeMix` collapses a neutral config to `null` so the "does this preset have whole-mix settings" check stays a truthiness test). `eq` is a variable-length band array in the *exact* same shape as a sound's own `filters.eq` (`{ freqHz, gainDb, q, type, slope, muted }`). New `presets.updatePresetWholeMix(id, wholeMix)` + `presets:updateWholeMix` IPC + `api.presets.updateWholeMix` preload. The portable preset export (`presetPortable.js`) does **not** carry `wholeMix` yet — deferred, noted in the inbox.

**Live chain** (`src/renderer/audio/WholeMixChain.js`): a master chain `masterGain → input → highpass → lowpass → [eq bands…] → gain → fadeGain → destination`, owned by `AudioEngine` (`engine.wholeMix`), sitting between `masterGain` (the global volume slider) and `context.destination`. The one structural change to `AudioEngine` is `masterGain.connect(this.wholeMix.input)` instead of `masterGain.connect(destination)`. The EQ sub-chain is built by the *same* `eqNodeType` / `eqBandStageCount` helpers a sound's own chain uses — now `export`ed from `SoundSource.js` (core-to-core, unlike the plugin-side duplicates) — with the identical "rebuild only when the per-band topology fingerprint changes, in-place param updates otherwise" logic copied from `SoundSource.setFilters`. `fadeGain` handles the on-load fade-in (kept separate from the user's `gain` dB node so a fade never fights a gain change). Neutral by default: nodes exist but pass audio through, `set(null)` resets them.

**How it takes effect**: `tabs/mixer/index.js`'s `loadPreset` sets `state.activePresetId = preset.id` and calls `engine.wholeMix.set(preset.wholeMix ?? null, { fadeInSeconds })` — the fade-in only ever runs on an actual load. Loading another preset swaps the chain (or resets it to neutral). `state.activePresetId` is *not* cleared when the user then deviates from the preset by hand — it just tracks "what did we last load."

**Live preview** across the plugin/core boundary: the plugin only has the curated `window.noctivago` IPC surface, no line to the engine — so it dispatches a `noctivago:whole-mix-preview` window `CustomEvent` `{ presetId, wholeMix }` on every control/EQ change (and once more with the *saved* values on `onHide`, reverting any unsaved preview). The Mixer listens and applies it **only if `e.detail.presetId === state.activePresetId`** — editing preset A while preset B is the live mix changes nothing audible. Same window-CustomEvent bridge the Solo button (`noctivago:solo`) and sleep timer (`noctivago:stop-all-playback`) already use.

**The plugin UI** (`plugins/preset-remix/index.js` + `ui/EqEditor.js`): a preset `<select>`, HP/LP/Gain sliders + a fade-in field (mirroring the Export tab's controls), then a scoped-down draggable-node EQ canvas — `WholeMixEqEditor`, a fresh ~280-line editor, *not* a copy of the core Remix `EqEditor` (which is 800+ lines of spectrum analyzer / A-B / mute-solo / cut-overlay that don't apply to a whole mix with no single preview source). Kept: draggable nodes, the real composite response curve (`OfflineAudioContext` `BiquadFilterNode.getFrequencyResponse` summed in dB, same technique as core), click-empty-to-add, wheel-for-Q, right-click-to-remove, double-click-to-flatten, per-band Freq/Gain/Q precision fields + a type `<select>`. No slope UI (bands are always `gentle`). Save via `api.presets.updateWholeMix`; a `canonicalMix()` order-insensitive compare drives the dirty check (the editor and the store build band objects with different key orders). `plugins/preset-remix/` uses only `app.noctivago` + its own tiny EQ math — no copies of `AudioEngine.js` etc. needed.

**BUG FIX: big exports failing with `spawn ENAMETOOLONG` (v0.1.116)** — reported directly ("Export failed: spawn ENAMETOOLONG"). Windows caps a process command line at ~32,767 chars. `exportMix.js`'s `renderFinalMixdown` passes ffmpeg one `-i <temp path>` per piece it merges — the filter *graph* goes to a `-filter_complex_script` file (off the command line), but the input list doesn't, and each `-i <userData>/export-tmp/<uuid>.flac` is ~95 chars. A multi-hour export, or one with a Random Interval / Scheduled sound firing often, produces one sliced-batch track per `EVENT_BATCH_SIZE` (20) events; ~350 of them (≈7000 events — a few scatter sounds over 3h at default gaps, or the v0.1.112 `MAX_EVENTS` cap of 200k in the pathological case) overflows the limit and `child_process.spawn` throws `ENAMETOOLONG` before ffmpeg ever runs. The export gets all the way through rendering every piece, then dies assembling them. **Fix**: `exportMix.js` gained `combineTracks` (adelay each track to its absolute offset → `amix` normalize=0 → one track, graph via `-filter_complex_script`) and `reduceTrackCount` (combine in fixed `MAX_INPUTS_PER_PASS = 32` chunks, repeatedly, until few enough remain). Before the final mixdown, if `batchTracks.length` exceeds the budget (`32 − loopShots.length`, floored at 4 — loop shots each take an input too and can't be pre-combined since they're `-stream_loop` tiled), the batch tracks are reduced first. A combine pass is just `adelay`+`amix` (no rubberband), so a wide one stays cheap and can't hit the v0.1.85 memory blowup; 32 inputs ≈ 3 KB of command line, well clear. Cheap no-op when the export is small enough that everything already fits. Combined intermediates are pushed onto the same cleanup array as the batch tracks. **Verified against the real bundled ffmpeg** via a Node harness importing the actual `exportMix.js` (electron stubbed through a `module.register` resolve hook, so `loopClip.js`/`runFfmpeg.js`/`ffmpegPath.js` run unmodified): a 40-min export with a scatter sound simulating 2000 plays → 100 batch tracks → one "Merging 100 track groups…" round → `ok`, output exactly 2400.00s, zero leftover temp files; the same at 800 pitch-varied events (40 batches, rubberband + reduction together) → `ok`, 2400.00s, mean −25 dB / max −15.5 dB (honest sum, no clipping), zero leftovers; a small 120-event export (6 batches, under budget) skips the reduction entirely and is byte-path-identical to before. New `.volume-slider-wrap` span (in `index.html` around the global input, built in `SoundRow.js` around each per-sound one) draws a faint 2px centre tick via `::after` (`pointer-events: none`, so it never blocks a drag) — makes "neutral" eyeball-able on the wider bar. Double-click-to-reset (`sliderReset.js`) is unaffected — it still reads the input's native `defaultValue` (now `gainToSlider(1)` = "50"). **Verified via CDP against the real dev app** (temp `NOCTIVAGO_CDP` switch + `window.__mixerDebug` engine hook, both removed): global slider at 100/50/0 → `masterGain.gain` 2.0/1.0/0.0; per-sound drag to 75 → `state.volumes` 1.5, the live source's `gainNode.gain` 1.5, and the store persisted 1.5; a pre-existing sound stored at 0.7 renders its thumb at 35 (left of centre); both sliders wrapped with the tick present; screenshot confirmed the wider bars.

**Real convolution reverb, replacing the old delay-based approximation (v0.1.122)** — owner's own inbox note: "think of a way to better the echo/reverb experience... if you need to write a better way to work with echo and delay you should absolutely do it." "Reverb" used to just be Echo's delay/decay knobs dialed to a short-delay/high-decay preset — never a real algorithm, since this ffmpeg build has no dedicated reverb filter. **Researched first**: exponentially-decaying noise as a synthetic impulse response is a legitimate, well-documented technique (Moorer 1979; MDN's own `ConvolverNode` example and the small `reverbGen` library both do exactly this instead of a bundled recorded IR — zero licensing/install-size cost). Confirmed the bundled ffmpeg has `afir` (arbitrary FIR/convolution filter, up to 60s) via `-filters`. **A real gotcha caught by testing directly against the bundled binary before writing app code**: `afir`'s own `dry`/`wet` options are NOT a dry/wet mix despite the name — both are just two gain stages multiplied into the same always-fully-convolved output (`dry=1:wet=0` produced total silence, not a passthrough; level scaled with the dry×wet product, confirmed by measuring `dry=10:wet=1` landing at the identical level as `dry=1:wet=10`). A real mix had to be built by hand: `asplit` the input into a dry branch and a to-be-convolved branch, run only the wet branch through `afir` at unity (`dry=1:wet=1`), scale each branch's own `volume`, then `amix`+`alimiter` (brick-wall ceiling, same `alimiter=limit=0.95:level=disabled` Composite's bake already uses — a continuous ambient sound's reverb tail genuinely can build real level, confirmed clipping-adjacent before the limiter). **Three touch points, mirroring exactly how Echo already works in each**: (1) *Bake* (`loopClip.js`) — reverb can't join `buildFilterChain`'s plain `-af` fragment (afir needs a second ffmpeg input, the IR file), so it's a new isolated pass (`applyReverbPass`, using a new `src/main/ffmpeg/reverbIR.js` that generates+caches the IR via `anoisesrc=color=pink`+`afade curve=exp`, one file per rounded size under userData) — `doRender`'s branch condition generalized from `!speedPitchChain` to `!speedPitchChain && !reverbActive`, reusing the exact "pre-process then crossfade last" pre-pass mechanism the v0.1.32 speed/pitch/reverse fix already established (crossfade-rotation itself was never touched). (2) *Live preview* — a `ConvolverNode` fed a synthetic IR (noise × exponential decay, `src/renderer/audio/reverbIR.js` + a Remix-plugin duplicate), wired as a third parallel send off `filterGainNode` (same pattern as `echoSendGain` — Echo and Reverb are independent, stackable effects, not chained) in both `SoundSource.js` and `PreviewSource.js`, regenerated only when `reverbSizeMs` changes. (3) *Data/UI* — `reverbSizeMs`/`reverbMix` added to `library.js`'s defaults, `NEUTRAL_FILTERS`, the Reverb preset (now `reverbSizeMs:1500, reverbMix:0.35`, echo fields zeroed), two new Remix sliders, and — caught proactively, the exact kind of miss v0.1.91's Doppler bug warned about — `plugins/editor/index.js`'s `snapshotOf()` (a flattened field list, not a generic spread) needed the two new fields added by hand or a reverb-only change would silently not mark the sound dirty. **Verified twice**: (a) a Node harness (electron stubbed via a `module.register` resolve hook, real `loopClip.js`/`reverbIR.js` unmodified) — reverb-off byte-path-identical; reverb-on (1500ms/0.4 mix) on a 3s tone still trimmed to exactly 3s despite the IR's own length, IR cache file created once and reused, the full combo (echo+reverb+speedPitch) completed without error, mix=0 with a nonzero size took the fast no-op path, peak level -0.4dB (no clipping), zero leftover temp files; (b) CDP against the real dev app — dragging the sliders live-updated both preview voices' `ConvolverNode.buffer` and `reverbSendGain` (settling at the target after the smoothing ramp — reading too early shows the pre-ramp value, a real gotcha hit during this same check), turning reverb off cleared the buffer to `null`, the Reverb preset button set the new fields and zeroed the old echo ones, Save persisted and baked a real clip whose actual file on disk measured exactly 1.00s with real non-silent, non-clipping content. **Un-feel-tested, flagged to the owner**: the exponential decay shape/rate, the Reverb preset's own 1.5s/35% starting point, and whether procedural noise reverb sounds convincing enough on real ambient content.

**"Sound Groups" — a non-destructive, per-preset submix bus with shared EQ (v0.1.143)** — the owner's own inbox idea: "create a Remix group... assign audio files to it and it'll show up on the remix tab as a single audio... EQ crickets or toads... to sound as if they're outside a house... accessible on a right click context menu, on the mixer tab... preset specific... copy it over to another preset." No `#next` item was ready on the Board (the whole Export wishlist had just shipped), so this was picked up the same session it was written rather than left to sit. **Architecture**: a group is a named subset of one preset's own sounds, routed through one shared `highpass → lowpass → [eq bands] → gain → limiter` chain (`src/renderer/audio/SoundGroupChain.js`, structurally identical to `WholeMixChain.js` minus the on-load fade-in, which only makes sense for a whole preset being *loaded*, not a group whose membership can change at any time) instead of straight to `masterGain`. `AudioEngine` gained `groupChains` (Map, keyed by group id) + `_soundGroupMembership` (soundId → groupId) + `setSoundGroups(groups)` (installs a preset's groups, reusing an existing chain object in place when its id survives so a live edit doesn't glitch) + `routeSound(soundId, source)` — the actual mechanism is a plain `source.gainNode.disconnect(); source.gainNode.connect(destination)` called from *outside* each Source class after construction, since every one of the four Source families (`SoundSource.js`, `BufferSoundSource.js`, `ScatterSoundSource.js`, `ScheduledSoundSource.js`) already exposes `this.gainNode` and connects it to `engine.masterGain` exactly once at construction — this sidesteps having to touch any of those already-complex classes at all. A sound belongs to at most one group (joining a new one silently leaves the old one) - a deliberate simplification over letting a sound fan out into multiple overlapping buses, which the ask never actually required. **Data model** (`presets.js`): new `groups: [{id, name, soundIds, filters}]` field per preset (`filters` = the same shape as whole-mix's, minus `fadeInSeconds`, always a real object rather than collapsed to `null` on neutral - a group's *existence* is the meaningful part even before it's tuned); `normalizeGroups`/`updatePresetGroups` mirror `normalizeWholeMix`/`updatePresetWholeMix` exactly; new `presets:updateGroups` IPC + preload, mirroring `updateSounds`. **Two UI entry points, one underlying write path**: (1) a sound row's right-click menu in the Mixer (`src/renderer/core/ContextMenu.js`, a new small generic floating-menu primitive - position/dismiss-on-outside-click/Escape, first real use case) lists the active preset's groups with a checkmark on the sound's current one, toggles membership on click, and offers "New group with this sound…" (a small name-only dialog, `#group-create-dialog` in `index.html`) — disabled with an explanatory item if no preset is loaded, since groups are preset-scoped; (2) the Preset Remix tab (`plugins/preset-remix/index.js`) gained a full "Sound Groups" section below its existing whole-mix controls - a list of the selected preset's groups, a create row with a "Copy filters from…" dropdown (any group on any preset, copies `filters` only, never membership), and an editor for the selected group: a membership checklist (checkboxes over the preset's own sound list, cross-referenced with the library for names), HP/LP/Gain sliders, and a second `WholeMixEqEditor` instance for the group's own parametric EQ — its own independent dirty-check/Save button, deliberately decoupled from the whole-mix controls' save state above it. Both entry points call the same `presets:updateGroups` and broadcast the same `noctivago:sound-groups-changed` window CustomEvent (mirroring the existing `noctivago:whole-mix-preview` bridge pattern) so a membership change from either place is instantly reflected everywhere; live filter/EQ dragging uses a second, cheaper `noctivago:sound-group-preview` event (`{presetId, groupId, filters}`) that the Mixer forwards straight to the already-installed chain via `engine.previewGroup()`, no re-fetch needed. `loadPreset` installs the new preset's groups and re-routes every already-live source in one pass; switching away from a preset (or deleting a group) correctly tears down its `SoundGroupChain` and returns every member sound to `masterGain`. **A real bug caught during CDP verification, not by code review**: `saveGroup()` persisted a renamed group correctly but never refreshed the "Copy filters from…" dropdown, so it kept showing the group's *pre-rename* name until the next full preset reselect - fixed by calling `renderGroupCopyFromOptions()` in the same place `renderGroupList()` already gets called after a save. **Verified via CDP against the real dev app** (temp `NOCTIVAGO_CDP` switch + a temp `window.__mixerDebug` hook, both removed after): built a real 3-sound preset, confirmed all three sources start routed to `masterGain`; created a group with two of them via a direct `updateGroups` call + the `sound-groups-changed` broadcast and confirmed exactly those two rerouted to the new chain's `input` node (the third untouched) with the chain's real `BiquadFilterNode`/`GainNode` values matching what was saved (300 Hz highpass, 4000 Hz lowpass, -3 dB gain → measured `0.708` linear gain); removing one sound from the group rerouted it back to `masterGain` while its groupmate stayed; deleting the group rerouted everyone back and dropped the chain (`groupChains.size` → 0); switching to a *different* preset with no groups at all correctly tore down the previous preset's chain and rerouted everyone. Drove the real Mixer right-click menu end-to-end with synthetic `contextmenu`/`click` DOM events (checkmark rendered correctly on the sound's current group; "Remove from group" and "New group with this sound…" both worked and were screenshot-confirmed legible against the app's dark theme); drove the real Preset Remix "Sound Groups" section end-to-end too (group list, membership checkboxes correctly moving a sound between groups live - including the actual audio reroute - EQ-canvas click-to-add via synthetic `pointerdown`/`pointerup` events, live gain preview landing on the real `BiquadFilterNode`, rename+Save persisting, "Copy filters from" correctly seeding a new group's filters with empty membership, and deleting a group both from the list and from inside its own open editor); screenshot-confirmed the new Preset Remix section reads on-brand. **Un-feel-tested, flagged to the owner**: whether shaping several sounds through one shared bus like this sounds as convincing in practice as the motivating "crickets + toads sound like they're outside" example, and the group-EQ's own gain/Q ranges (kept identical to Preset Remix's existing whole-mix EQ rather than re-tuned).

**Export tab: audio-reactive visualization video (v0.1.144)** — the last open item on the Board's Export wishlist, previously staged `#future` pending a research pass ("needs research first, speed/optimization is a hard requirement per the owner's own note"). That research pass ran first, against the real bundled ffmpeg, before any app code was written (per [[feedback_research_before_complex_tasks]]): ffmpeg ships three real audio-visualization filters (A→V) — `showwaves`, `showspectrum`, `avectorscope` — no external tool needed. Benchmarked on a real 5-minute synthetic file (pink noise + tone) at 1920×1080/15fps: `showwaves` ran ~5x realtime, `avectorscope` ~15x, `showspectrum` (a real STFT, the heaviest of the three) ~7x — all comfortably faster than the audio DSP phases already in this export pipeline, de-risking the owner's speed concern well enough to build rather than just report back. A custom (non-black) **background** color needed real investigation since none of the three filters take a background option (only `showwaves` takes a foreground `colors` list): a `format=yuva420p,colorkey,overlay` alpha composite measured close to 1x realtime and one real test run of it failed outright — rejected, never shipped; a `blend=all_mode=screen` composite (two opaque RGB frames, no alpha channel at all) measured ~2x realtime at 1080p — real, but meaningfully slower than plain black. Given the owner's own hard speed requirement, **black stays the fast default** (skips compositing entirely) and a custom background is opt-in, with the Export tab saying plainly that it renders slower. `src/main/ffmpeg/visualizationVideo.js`'s `renderVisualizationVideo()` builds one of the three filter graphs (`buildVizFilter`) at a fixed, un-exposed 15fps (this app already has a precedent for a fixed fps choice not worth a UI knob — the black-screen video's own fixed 1fps) and one of three size presets (854×480/1280×720/1920×1080), muxes the result with the just-finished audio stream-copied (`-c:a copy`, same shape as `renderBlackScreenVideo`/`renderLoopedVideoFromFile`) into one `.mkv`. `exportMix.js`'s `renderVideoOutput()` dispatcher grew a third branch (`videoBackground: 'black' | 'file' | 'visualization'`) alongside the two it already had, ahead of the existing `videoMode`/`loopVideoPath` params — `videoBackground` is the new, explicit setting that decides *which* of the three actually runs; `loopVideoPath`'s own nullability is no longer what selects 'file' mode (a `resolveExportVideoBackground()` one-time migration in `settings.js`, mirroring `resolveExportVideoMode()`, promotes anyone who'd already picked a loop-video file to `'file'` explicitly so that choice doesn't silently revert to black). New settings: `exportVideoBackground` + `exportVisualizationType`/`Color`/`BgColor`/`Palette`/`Size`, one combined `setExportVisualizationOptions(options)` setter (merges whichever fields the Export tab's individual controls send, ignoring invalid ones per-field rather than resetting the whole group) instead of five near-identical setters. Export tab UI: the old binary "Choose video to loop… / Use black screen instead" row became a 3-way `<select>` (`#export-video-background`) with two conditionally-shown subsections — file-picker controls (unchanged) and a new visualization panel (style/color/palette/background/size), the palette dropdown swapping in for the raw color picker specifically for Spectrum (`showspectrum`'s own `color` option is a named palette, not an arbitrary hex, so there's nothing for a color picker to drive there). The optional info.txt (v0.1.140) now names which of the three backgrounds was used, including the visualization's own type+size. **Verified against the real bundled ffmpeg** via a Node harness (electron stubbed via `module.register`, real `visualizationVideo.js`/`exportMix.js` unmodified): all three visualization types render correctly at the fast (black) default with both video+audio streams and exact duration; the custom-background blend-composite path renders correctly (just slower, as expected); an invalid/garbage options object (bad type, bad size, non-hex color) falls back cleanly to the waveform/medium/black defaults rather than throwing; a full `exportMix()` run with `videoBackground: 'visualization'` end-to-end (dispatcher wiring, not just the isolated render function) produced a correct `.mkv` with both streams at the exact requested duration alongside the retained standalone audio file (`videoMode: 'both'`) — 18/18 harness assertions passed. UI wiring (the `<select>`/subsection show-hide logic and the settings round-trip) was cross-checked for id/selector mismatches (all 29 element ids referenced via `querySelector` resolved to a real id in the markup, zero mismatches — the exact class of bug that silently killed the whole Export tab in the v0.1.130 incident) but **not driven live via CDP** this round, matching how the last several small, pattern-mirroring Export-tab UI changes (v0.1.138 onward) were verified — the new code here is structurally identical to the already-shipped, already-proven `exportVideoMode`/`exportLoopVideoPath` plumbing. **Un-verified, flagged to the owner**: how any of the three visualization styles actually looks/feels on a real export, and whether 15fps reads as smooth enough in practice; a genuine multi-hour export was not run (the harness used short synthetic audio) so the benchmarked speed multipliers are extrapolated, not measured at real scale.

**Self-review pass over v0.1.135–v0.1.144, five real fixes (v0.1.145)** — the Board and the Obsidian inbox both came up empty (the two open Board items are each explicitly gated on the owner - the Export mixdown-phase optimization on a real slow-export log, the app icon on the owner's own design pass - and everything else open is research-gated or deprioritized), so per this project's own established "dry backlog" precedent (the v0.1.102/v0.1.112 self-review passes), ran a multi-angle `/code-review` over the diff since the last such pass (`ebd2003..HEAD`, the ten releases from the per-shot Speed range through the visualization video) instead of sitting idle. Eight parallel review angles (line-by-line diff scan, removed-behavior audit, cross-file tracing, reuse, simplification, altitude/abstraction, efficiency, CLAUDE.md convention-adherence) surfaced candidates; each correctness/efficiency claim below was independently re-verified by reading the actual current source before being fixed, not taken on the sub-agent's word alone. **Fixed:**
- `plugins/editor/index.js`'s `performSave()` updated `savedSnapshot` unconditionally but only invalidated a stale bake's `loopClipReady`/`loopClip*` metadata on the *render-failed* branch, never on the *trim-now-exceeds-the-600s-cap* branch — extending an already-baked sound's trim past the cap and saving left the old bake looking fully valid (no dirty flag, no stale-dashed-border) while "Saved audio" would keep silently playing the previous, now-unrelated clip. Fixed by clearing the same fields in that branch too.
- The Mixer's right-click Sound Groups menu (`openSoundContextMenu`/`toggleGroupMembership`/`openCreateGroupDialog`) did a full `api.presets.list()` IPC round-trip on every single open, directly contradicting its own doc comment ("`state.groups` ... kept here purely so the right-click context menu can list them without an extra IPC round-trip on every open") — the cache existed but was never actually read. Fixed to read `state.groups`/`state.activePresetId` directly; in fixing this, also closed a real gap it would have reintroduced: `deletePreset()` never cleared `state.activePresetId`/`state.groups` when the deleted preset was the active one (the old code's IPC re-fetch had silently papered over this every time), so it now resets both and re-routes every live source back to `masterGain`, mirroring `loadPreset`'s own reset for "switching to a preset with no groups."
- `getOrCreateSource()` (Mixer) returned an already-cached source before ever reaching the new `engine.routeSound()` call added for Sound Groups — currently harmless only because every actual group-membership change already re-routes every live source in a separate full pass (`loadPreset`, the `sound-groups-changed` listener), but a real trap for the next caller that assumes a fetched source is always correctly routed. Since `routeSound` is already documented as idempotent (a no-op once correctly routed), made `getOrCreateSource` call it unconditionally, including on the cached-source path, so routing self-heals on every access rather than depending on side-channel resyncs.
- `visualizationVideo.js`'s custom-background composite (`blend=all_mode=screen`) built its `color` background source with no explicit framerate, defaulting to ffmpeg's standard 25fps against the visualization stream's fixed 15fps — mismatched-framerate inputs into a frame-matched blend risked visible judder between the moving waveform/spectrum and its background. Fixed by pinning the color source to the same `VIZ_FPS` (15) explicitly.
- The Export tab's "Clear" button (for a chosen loop-video file) cleared the stored path and updated the status line, but left the `#export-video-background` `<select>` still showing "Loop a video file" (and its file-picker subsection visible) — cosmetic only (the actual render already falls back to black correctly when `loopVideoPath` is null), but misleading until a reload re-read settings. Fixed to also flip the select back to `'black'`, persist it, and re-run the subsection-visibility update.
- `exportMix.js`'s `eventBranchChain` hardcoded a literal `0.005` for the speed-identity threshold instead of using the `IDENTITY_SPEED_EPSILON` constant declared for exactly this purpose 200 lines earlier (and already used by `eventsNeedRubberband`) — no behavior change today, but a real drift risk if the epsilon is ever tuned (the two checks are meant to agree, or a shot could get batched as "light" while still individually triggering rubberband). Fixed to reference the constant.

**Flagged, not fixed** (real but lower-priority or riskier to change unsupervised): a scatter/schedule Speed(min) > Speed(max) silently collapses to a fixed value with zero randomization and no UI warning — confirmed real, but it's the exact same `Math.max(min, max)` shape `randomVolumeScale` already has for the volume range, so it's a pre-existing app-wide pattern, not a new regression, and fixing it in isolation for Speed alone (without touching Pitch/Volume too) would be inconsistent; left for a follow-up that treats all three uniformly. Several structural-duplication findings (a near-identical `SoundGroupChain.js`/`WholeMixChain.js` pair; `scatter`/`schedule` defaults and Remix's `snapshotOf()` hand-copying the same fields twice per new per-shot control; three independent hand-rolled debounce timers in `plugins/editor/index.js`; a `probeVideoDurationSeconds`/`probeSourceSampleRate` pair that scrape the same ffmpeg-stderr pattern twice; a `resolveExportVideoMode`/`resolveExportVideoBackground` pair of near-identical one-time settings migrations) are real reuse opportunities but are refactors, not bugs — each would need to touch working, already-verified code across multiple files for a cleanliness win with no user-visible effect, so they're left as noted follow-up material rather than done unsupervised in this pass. Two more candidates were investigated and found *not* to be real bugs: a `reduceTrackCount` failure under `parallelMixdown`'s new concurrent merge could in principle leave a sibling `combineTracks` call still writing a temp file after the first rejection surfaces (speculative, `mapPool`'s own error-aggregation behavior wasn't independently re-derived); and `MAX_INPUTS_PER_PASS`'s doc comment describes only the merge-round chunk size, not the true worst-case final-mixdown input count once uncapped loop-shot tracks are added back on top (a preset with 100+ loop-mode sounds could exceed the "128 inputs" comfort margin the comment implies) — not an actual crash risk given the OS's real ~32,767-char command-line limit, just a comment that overstates the bound. Verified via `node --input-type=module --check` on every changed file (the real check for this codebase's plain-`.js`-but-ESM plugin/main files, per the v0.1.130 lesson) plus a full `electron-vite build`, both clean; not re-verified live via CDP this pass.
