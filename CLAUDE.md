# Noctívago

Windows desktop ambient sound mixer, inspired by the Linux app [Blanket](https://github.com/rafaelmardojai/blanket) (not a port — Blanket is GTK/Linux-only). Electron + vanilla JS/DOM (no UI framework).

See `CONTRIBUTING.md` for build/run instructions and code conventions if you're working on the codebase.

## Architecture

- `src/main/` — Electron main process.
  - `index.js` — window creation, custom `sound://` protocol (serves either the original file or a rendered loop clip, see below) and `plugin://` protocol (serves plugin files, see Plugins below). Under `npm run dev` with more than one display connected, `devWindowPosition()` opens the dev window on the highest-numbered display rather than the default (primary, centered) position, so a dev session doesn't pop a window over whatever's already in use on the primary display — computed *before* window creation (passed as `x`/`y` to the `BrowserWindow` constructor) rather than moved after the fact, to avoid a visible flash on the primary display first. Gated on `!app.isPackaged`, so a real installed build is never affected.
  - `ipc.js` — IPC handlers.
  - `library.js` — registered sound files, persisted via `electron-store`.
  - `presets.js` — saved mixes.
  - `ffmpeg/` — ffmpeg integration (see below). `runFfmpeg.js` is the reusable spawn wrapper; `ffmpegPath.js` resolves the bundled binary; `loopClip.js` and `waveformPeaks.js` are its two current consumers.
  - `plugins/` — `registry.js` (scans + caches bundled/user plugin manifests), `protocol.js` (`plugin://` handler + path-traversal guard), `invoke.js` (dispatches `plugin:invoke` IPC to a plugin's own main-process module).
- `src/preload/index.js` — contextBridge API exposed to the renderer as `window.noctivago` (namespaces: `library`, `presets`, `audio`, `plugins`).
- `src/shared/constants.js` — plain constants imported by both main and renderer (e.g. `MAX_BUFFER_CLIP_SECONDS`).
- `src/renderer/` — plain JS/DOM UI, no framework.
  - `core/TabHost.js` — tab bar + lazily-mounted `<section>` per tab.
  - `core/PluginLoader.js` — discovers plugins via IPC, dynamically `import()`s each one, registers its tab(s).
  - `tabs/mixer/index.js` — the entire sound mixer, registered as the first tab via `mount(container)`.
  - `audio/AudioEngine.js`, `audio/SoundSource.js` (streaming playback), `audio/BufferSoundSource.js` (buffer/gapless playback).
  - `ui/*.js` — SoundList, SoundRow, PresetsModal (mixer-specific, used only by `tabs/mixer/`).
  - `main.js` — a tiny bootstrap: creates the `TabHost`, registers the Mixer tab synchronously, then calls `loadPlugins()`.

### Playback: two modes, chosen automatically per sound

**Stream mode** (`LocalFileSoundSource`, the default): each sound plays through **two** `<audio>` elements of the same file (`src="sound://<id>"`), one active and one standby, each piped through its own crossfade `GainNode` and then summed into the shared chain `→ highpass BiquadFilterNode → lowpass BiquadFilterNode → EQ chain → filter GainNode → per-sound GainNode → master GainNode` (echo taps off filter GainNode as before). The filter nodes apply the sound's saved highpass/lowpass/gain/EQ settings (same chain shape as the Remix plugin's live preview) — this is what makes filters audible even for sounds that never qualify for a baked buffer clip (see below). The `sound://` protocol hand-rolls HTTP Range support via `fs.createReadStream` (Electron's `net.fetch` on `file://` URLs was found to silently ignore Range headers in the Electron version this was built against — don't assume it works without verifying against the version in use). This is what makes arbitrarily long files (hours) playable at all without loading them into memory.

Looping is a two-element crossfade at the seam: a `requestAnimationFrame` `_tick` boundary-check watches the active element's `currentTime`; when it reaches `loopEnd - fade*speed` (the `*speed` since `fade` is wall-clock), the standby element (pre-seeked to `loopStart`) starts playing and the two crossfade GainNodes ramp in opposite directions over `fade` seconds, then a `setTimeout` (`fade*1000 + 40`) swaps their roles — the retired element is paused and rewound to `loopStart` to become the next standby. `fade` = `entry.crossfadeSeconds` (the *same* per-sound Remix "Loop crossfade" slider that drives the baked-clip crossfade; `null` → a local `DEFAULT_STREAM_CROSSFADE_SECONDS = 0.2` mirroring `loopClip.js`'s `DEFAULT_CROSSFADE_SECONDS`), clamped to a quarter of the loop region. **An explicit `crossfadeSeconds: 0` falls back to a plain `currentTime = loopStart` hard seek-back** on the single active element (not sample-accurate, audible click/gap on non-self-looping content — which is exactly why the crossfade exists). The seam trigger is still rAF-polled `currentTime` (imprecise by nature), but a ~200ms crossfade masks that jitter far better than a hard seek would — this is the streaming counterpart of buffer mode's baked tail/head crossfade, minus the sample-accuracy. This dual-element approach was chosen over a pre-baked ffmpeg bridge segment (no ffmpeg round-trip, no disk cache/staleness tracking, filters stay live, loop region stays exact, and it's automatic rather than opt-in). `pause()` mid-crossfade finalizes the swap synchronously so resume continues cleanly from just past the loop point; `dispose()` tears down both elements + both source nodes + both crossfade gains. Cost: two `<audio>` elements (and two `MediaElementAudioSourceNode`s) per stream-mode loop sound — negligible in practice since most sounds get baked into buffer mode anyway and only a genuinely long *loop region* (>600s) keeps a sound in stream mode for real.

**Buffer mode** (`BufferSoundSource`): whenever the user trims + sets filters and hits Save in the Remix plugin (see below), ffmpeg renders *just that loop region*, with any highpass/lowpass/gain filters baked in via `-af`, out to a small WAV (`src/main/ffmpeg/loopClip.js`, `getUserData()/clips/<id>.wav`) — but only if the region is ≤ `MAX_BUFFER_CLIP_SECONDS` (600s/10min, in `src/shared/constants.js`). Since the clip is now short regardless of how long the source file was, it's fully decoded client-side (`decodeAudioData`) into a native `AudioBufferSourceNode` with true `loop=true`/`loopStart`/`loopEnd` — sample-accurate, click-free. `tabs/mixer/index.js`'s `loopClipEligible(entry)` checks `entry.loopClipReady` + that the clip's recorded loop points *and* filters still match the entry's live ones (a staleness check, since either changing without re-saving should fall back to streaming) before trying buffer mode, and falls back to stream mode on *any* failure (missing ffmpeg, corrupt clip, decode error) — buffer mode is strictly additive and only ever affects loop-seam smoothness, never whether filters apply, never required for the app to work.

`BufferSoundSource.pause()` tracks elapsed offset manually (`AudioBufferSourceNode` is one-shot — can't be pause/resumed like `<audio>` can) so resuming continues from the same position rather than restarting, matching stream mode's behavior.

**Getting a sound into buffer mode**: the default is lazy — `tabs/mixer/index.js`'s `maybeAutoBake` bakes a full-file clip the first time an eligible, never-baked sound actually plays. A Settings toggle (`eagerlyBakeOnImport`, off by default) makes this eager instead: `library.js`'s `maybeEagerBakeOnImport`, fired fire-and-forget from `addSound()` — the single choke point every import path (single file, folder-as-preset, folder-as-tag, watch-folder) already funnels through — probes the file's real duration via ffmpeg directly (`loopClip.js`'s `probeDurationSeconds`, since a fresh import has no `durationSeconds` yet) and bakes immediately, before the sound is ever played. Same `MAX_BUFFER_CLIP_SECONDS` cap and bake call as the lazy path — this only changes *when* the first bake happens, not how.

### Playback mode: Loop vs. Random Interval ("scatter")

Every sound's `playMode` (`'loop'` default, or `'scatter'`, in `library.js`) picks between the two source families above (continuous loop) and a second pair — `BufferScatterSource`/`StreamScatterSource` (`src/renderer/audio/ScatterSoundSource.js`) — that instead replay the trimmed clip as one-shots on a randomized gap (`entry.scatter.minGapSeconds`/`maxGapSeconds`) with a randomized pitch each time (`entry.scatter.minPitchSemitones`/`maxPitchSemitones`; both left at 0 means *fully* random pitch per replay, not "no shift" — an explicit, deliberate special case). This mirrors the game-engine "scattered ambience emitter" pattern (Wwise Random Container, FMOD's Scatterer Instrument, Unity's Audio Random Container) for a short, event-like sound (a creak, a bird call) inside a longer ambient mix, rather than looping it back-to-back. `tabs/mixer/index.js`'s `desiredSourceKind(entry)` crosses `playMode` with buffer eligibility into four kinds (`loop-buffer`/`loop-stream`/`scatter-buffer`/`scatter-stream`); `reconcileSource` swaps the live source whenever the desired kind or the bake itself changes, same pattern the original loop/stream swap already used.

`BufferScatterSource` uses the decoded clip's native `AudioBufferSourceNode.detune` (cents) for pitch — true independent pitch shift with zero effect on shot duration or the gap timer, a nicer primitive than the playbackRate-linked pitch/tempo coupling most non-web engines settle for. `StreamScatterSource` (the fallback for a trim too long to bake) has no such primitive on `<audio>`, so it reuses `playbackRate` the same way Speed does elsewhere in this app — a pitch shift there also changes shot tempo, a documented, accepted limitation.

Scatter-mode clips reuse `renderLoopClip` unchanged rather than a second bake pipeline: both `library.js` and `tabs/mixer/index.js` have an `effectiveCrossfadeSeconds(entry)` helper that forces the crossfade to `0` whenever `playMode === 'scatter'` (crossfade+rotation, which permanently reorders the clip's own audio to hide a *looping* wrap point, would be actively wrong for a clip that's never looped back-to-back) — `0` already means "plain trim, no rotation" in `loopClip.js`'s `doRender`, so this is a pure input-shaping trick, not new ffmpeg logic. Switching a sound between Loop and Random Interval in the Remix plugin (which owns this control, alongside trim/filters/crossfade/speed-pitch — the same "shape a sound" editor as everything else that affects the bake) naturally invalidates the old bake via the same staleness check every other trim/filter edit already goes through.

### Waveform

`src/main/ffmpeg/waveformPeaks.js` streams the *whole* original file through ffmpeg as downsampled mono float32 PCM and reduces it into `[min,max]` peaks per pixel column with O(1) memory (never buffers the decoded audio) — works for files of any length/format. This replaced an earlier renderer-side `decodeAudioData`-based approach that was capped at 30 minutes and fell back to a bare time-ruler beyond that.

**Canvas resolution**: any canvas whose bitmap resolution (`width`/`height` HTML attributes) doesn't match its rendered CSS size stretches/blurs when the browser scales it up. `waveform.js`'s and `EqEditor.js`'s `resizeCanvasForDisplay()` resize the canvas's real bitmap resolution to its rendered CSS size × `devicePixelRatio` before every draw and scale the context so the rest of the drawing code keeps working in plain CSS-pixel coordinates. Interaction math (drag, wheel, hit-testing) works in `rect.width`/`rect.height` (CSS-pixel space) throughout — only the *drawing* functions needed the resize fix, a distinction worth keeping in mind when adding a new canvas-based control (see the EQ editor note below).

**Live spectrum analyzer**: `PreviewSource.js` taps an `AnalyserNode` (never connected onward — a pure read tap) off `outputGainNode`, the single point both crossfading voices' signals combine into, so it reflects whichever voice is actually audible regardless of crossfade state. `EqEditor.js`'s `tickSpectrum(analyserNode)` is called once per frame from the same `tickPreviewPlayhead()` rAF loop that already drives the waveform playhead and sticky progress bar (no separate loop) — reads `getByteFrequencyData()` (already dB-scaled 0-255 by the Web Audio API itself) and redraws a filled area connecting each linearly-spaced FFT bin's point via the graph's own log-frequency `freqToX`. Takes over from a static band-energy backdrop (below) whenever playing; `clearSpectrum()` (called on pause/stop/dispose) falls back to the static backdrop rather than freezing on the last live frame.

**Per-band filter types**: 7 EQ bands, each independently one of 8 types via a `type` field on the band object (`'off' | 'lowpass' | 'highpass' | 'bandpass' | 'notch' | 'lowshelf' | 'highshelf' | 'peaking'`), selected via a `<select>` next to the Freq/Gain/Q precision fields. Web Audio's native `BiquadFilterNode.type` covers 7 of the 8 shapes directly — only `'off'` is a pseudo-type (not a real biquad shape), mapped to `'allpass'` at the node level (`eqNodeType()` in both `SoundSource.js` and `PreviewSource.js`) since allpass leaves the amplitude spectrum completely unchanged, a true no-op without needing to dynamically rewire the fixed per-band node chain. `.type` isn't an AudioParam (a plain property, can't be smoothed like frequency/Q/gain) — only reassigned when it actually changes, to avoid resetting the filter's internal state on every unrelated update. Baking dispatches per band to the matching ffmpeg filter (`loopClip.js`'s `buildEqBandFilter`: `lowpass`/`highpass`/`bandpass`/`bandreject`(notch)/`bass`(lowshelf)/`treble`(highshelf)/`equalizer`(peaking), `'off'` simply omitted from the chain). Only peaking/lowshelf/highshelf are true no-ops at `gainDb: 0` (their whole effect is proportional to gain); lowpass/highpass/bandpass/notch have no gain parameter at all and always shape the signal whenever selected, so they're never skipped just for looking "neutral."

### Why ffmpeg, not more JS

Both the loop-seam click and the waveform-for-long-files problems trace back to the same root cause: `decodeAudioData` on a whole multi-hour file either throws `EncodingError` or uses gigabytes of RAM (this is *why* stream mode exists at all). ffmpeg (bundled via `ffmpeg-static`, spawned via `child_process`, never a shell) processes files without holding them fully in memory, sidestepping that limit entirely. `runFfmpeg.js` is deliberately generic/domain-agnostic so ffmpeg-based features reuse it rather than each rolling their own spawn logic.

**Packaging note:** `electron-builder.yml` has `asarUnpack: [node_modules/ffmpeg-static/**]` — required because binaries can't execute from inside an asar archive.

**ffmpeg binary license note**: the bundled ffmpeg binary (fetched via `ffmpeg-static`) is GPLv3, not the more permissive LGPL — confirmed via the binary's own accompanying license file (`node_modules/ffmpeg-static/ffmpeg.exe.LICENSE`/`.README`, which `ffmpeg-static` itself started shipping after [eugeneware/ffmpeg-static#8](https://github.com/eugeneware/ffmpeg-static/issues/8)). See `THIRD_PARTY_NOTICES.md` for the full attribution, exact version/source-commit link, and why bundling a GPLv3 binary doesn't require Noctívago's own Apache-2.0 code to relicense (it's always invoked as a separate subprocess via `runFfmpeg.js`, never linked).

### App icon

`resources/icon.ico` is hand-built by `resources/icon-src/build-ico.mjs` (run `node resources/icon-src/build-ico.mjs` from the repo root to regenerate after editing `resources/icon-src/render.html`'s SVG and re-rendering `icon-master.png`) rather than a plain PNG electron-builder auto-converts. **Why this matters**: electron-builder's own PNG→ICO conversion PNG-compresses every embedded size, but Windows only honors PNG compression for the 256px entry — sizes below that (16/24/32/48/64, exactly what the taskbar and Windows Search use) silently fall back to a generic icon if they're PNG-compressed instead of classic uncompressed BMP/DIB data. The build script generates real BMP/DIB data (with a proper 1bpp AND mask derived from the alpha channel) for every size below 256, PNG-compressing only the 256 entry. `src/main/tray.js` (system tray) and `src/main/index.js` (`BrowserWindow`'s `icon` option) both read the same design; the tray one stays a plain PNG since `nativeImage`-based tray icons don't have this multi-size ICO requirement.

## Plugins

The app is designed for outside contributors to add functionality as plugins rather than editing core — modeled on Obsidian's plugin architecture, but **deliberately not** copying its trust model (Obsidian plugins get raw Node/Electron access; here that's split by process, see below), since this codebase is more sandboxed (`contextIsolation: true`, no `nodeIntegration`, everything served through custom protocols rather than raw file access).

**A plugin is a folder** containing `manifest.json` (`id`, `name`, `version`, `main` required; `mainProcess` optional) + a `main` entry file exporting a default class:
```js
export default class MyPlugin {
  constructor(app, manifest) { this.app = app }
  async onload() { this.unregister = this.app.tabs.register({ id, title, mount: (container) => {...} }) }
  async onunload() { this.unregister?.() }
}
```
Two real examples exist in `plugins/`: `hello-world/` (minimal working plugin) and `broken-plugin-example/` (deliberately throws in `onload()` — a regression-test fixture proving one broken plugin can't take down the app or other plugins).

`register()` also accepts an optional `mountSticky: (container) => {...}` alongside `mount` — its own section in the shared sticky bar directly under the tab bar (`#tab-sticky-bar` in `index.html`, wired in `TabHost.js`), always visible regardless of how far the tab's own content is scrolled. This is a fixed-height flex sibling of `main` in `#app`'s layout, not `position: sticky` — deliberately simpler, no scroll-container edge cases to get wrong. Distinct from the toolbar above the tab bar (global mix Play all/master volume, app-wide): the sticky bar is per-tab, for controlling whatever's local to that specific tab (e.g. the Remix plugin's own trim preview, see below) — only the active tab's sticky section is shown, and the shared bar itself hides entirely for a tab that doesn't provide one (like the Mixer, which has no single "current preview" the way Remix does). Same lazy-mount-once-then-show/hide lifecycle `mount` already has, not remounted on every tab switch.

**Where plugins live**: `plugins/<id>/` at the repo root for bundled/official plugins (packaged into the app via `electron-builder.yml`'s `extraResources`), and `<userData>/plugins/<id>/` for user-installed ones (parallel to Obsidian's `.obsidian/plugins/`). `src/main/plugins/registry.js` scans both and merges them; on an id collision, bundled wins. Presence in either directory *is* enabled — there's no enable/disable toggle UI in v1 (disable by moving the folder out).

**How loading actually works**: `plugin://<id>/<path>` is a privileged `standard` Electron scheme (registered in `main/index.js`, handled in `src/main/plugins/protocol.js`) serving a plugin's own files as real ES modules — `PluginLoader.js` in the renderer does `await import(\`plugin://${id}/${manifest.main}\`)`, which resolves relative imports between a plugin's own files correctly and shows real filenames/breakpoints in DevTools. This directly extends the same pattern `sound://` already established for serving local files into the sandboxed renderer.

**Security posture — split by process**:
- Renderer-side plugin code (`manifest.main`) is exactly as sandboxed as core code — no `require`, no `ipcRenderer`, only the curated `app` object (`{ tabs, noctivago, plugin }`) it's constructed with. `app.noctivago` is `window.noctivago` handed through wholesale (already curated/whitelisted) — no per-plugin capability scoping in v1, any enabled plugin can call any core API, matching Obsidian's own trust model closely enough not to need more yet.
- Main-process plugin code (`manifest.mainProcess`, opt-in) is ordinary trusted Node — same trust level `src/main/*.js` already has — loaded via `src/main/plugins/invoke.js`. This is the only place a plugin gets real power (spawn ffmpeg, touch disk), reached from the renderer via one generic `api.plugins.invoke(pluginId, method, ...args)` rather than each plugin needing its own hand-written IPC channel in `ipc.js`.
- This is not real code sandboxing — a `mainProcess` plugin still has full Node power once opted into, same as Obsidian's actual model. Trust boundary remains "the user reads/trusts plugin source before installing," just scoped to a smaller, more visible manifest field than "the whole plugin."

**Explicit non-goals for v1** (deferred, not designed): plugin marketplace/browser, hot-reload dev tooling, settings-tab API, command palette, ribbon icons, enable/disable UI, per-plugin capability scoping, persistent per-plugin data storage.

### The Remix plugin (`plugins/editor/`, tab titled "Remix")

The first real (non-toy) plugin, and the one that validated the plugin API against an actual feature. All per-sound editing — trim points *and* filters (highpass, lowpass, gain) — lives here.

- **Live preview without touching ffmpeg**: `audio/PreviewSource.js` streams the sound the same way `LocalFileSoundSource` does (`sound://<id>`, works for any file length) but inserts a `BiquadFilterNode` (highpass) → `BiquadFilterNode` (lowpass) → `GainNode` chain before the output gain. Dragging a filter slider calls `setTargetAtTime` on these nodes directly — instant, click-free, audible feedback with zero ffmpeg round-trips. ffmpeg only runs once, on Save.
- **Save bakes trim + filters in one ffmpeg pass**: reuses `loopClip.js`'s renderer (extended to accept a `filters` object and insert `-af highpass=f=…,lowpass=f=…,volume=…dB` into the ffmpeg args), rather than a second, parallel baking pipeline. The Mixer's buffer-mode eligibility check compares filters as well as loop points, so changing either without re-saving correctly falls back to streaming (still filtered — see Playback above — just with a small loop seam) instead of playing a stale baked clip.
- **Save never touches the original file**: trim points and filters are persisted as metadata (`library.js`, via `electron-store`) and applied live by both playback modes; the ffmpeg render is a disposable derived cache (`getUserData()/clips/<id>.wav`), regenerated on every Save, not an edit to the source audio. The Save button surfaces the outcome (baked / bake failed / skipped because the trim exceeds the buffer-mode cap) via a status line under the button.
- **Self-contained by design, not by accident**: a plugin can't import files outside its own directory (enforced by the `plugin://` path-traversal guard), so `plugins/editor/` has its own copies of `AudioEngine.js`, the waveform-drawing code, `LoopEditor.js` (the drag/scrub/snap canvas controller), and `util/time.js` — duplicated from core rather than shared. This matches Obsidian's "bundle your own dependencies" plugin model; keep it in mind if core's copies of these change and the plugin's need the same fix.
- `MAX_BUFFER_CLIP_SECONDS` (600s) is duplicated as a local constant in `plugins/editor/index.js` for the same cross-directory-import reason — keep it in sync with `src/shared/constants.js` if that value ever changes.
- **Parametric EQ**: a fixed 7-band peaking-style EQ, folded into the *existing* `filters` object as `filters.eq: [{freqHz, gainDb, q, type}, ...]` (`library.js`'s `defaultEqBands()`) rather than a new top-level field — reuses every bit of existing filters plumbing (staleness comparison, `updateFilters`, live-update paths) with zero new schema/IPC code. `plugins/editor/ui/EqEditor.js` is the draggable-node canvas (X = log-frequency, Y = gain, mouse wheel over a node = Q); `index.js` also exposes precision numeric fields (Freq/Gain/Q) for the selected band. Presets (Muffled/Phone/etc.) never touch `.eq` — only "Reset filters" or a per-sound "Reset EQ" button do. Live preview inserts a chain of `BiquadFilterNode`s between the lowpass and filter-gain nodes in both `PreviewSource.js` and core's `LocalFileSoundSource` (`src/renderer/audio/SoundSource.js`), same position ffmpeg's bake applies them (`equalizer=f=…:width_type=q:w=…:g=…` in `loopClip.js`'s `buildFilterChain`) so preview and the real Mixer agree.
- **Sticky playback bar**: Play/Pause, a loop toggle, a progress bar/time readout, and a preview-volume slider live in `mountSticky()` (see the Plugins section above), not the scrollable panel body — always visible under the tab bar regardless of scroll position. Progress is relative to the *trimmed loop region* (`loopStart`..`loopEnd`), not the whole original file. `mount()` and `mountSticky()` populate the same shared `this.els` object; ordering matters (`mount` then `mountSticky`, both synchronous, see `TabHost.js`) since `wireControls()` (called from `mount()`) doesn't wire the Play/Pause or loop-toggle listeners itself — those are wired in `mountSticky()`.
- **EQ graph backdrop**: translucent bars behind the EQ curve showing roughly how much energy the sound actually has around the EQ's reference frequencies, independent of wherever the user later drags a node — a scoped-down alternative to a literal live spectrum analyzer or waveform overlay (a time-domain plot doesn't belong on this graph's *frequency*-domain X-axis). `src/main/ffmpeg/bandEnergy.js`'s `computeBandEnergy` runs one `bandpass`-filtered ffmpeg pass per frequency (in parallel — wall-clock cost is roughly the slowest single pass, not the sum), computing RMS in JS from the piped PCM. Static, load-time-only analysis (`plugins/editor/index.js`'s `loadSound()`, fire-and-forget) — not tied to playback, not recomputed as the user drags EQ nodes. Two things worth knowing if you touch this: the output PCM sample rate needs to be well above twice the highest reference frequency (a prior version used 11025Hz, which silently discarded real signal at higher bands via ffmpeg's own anti-aliasing filter during resample — now 32000Hz), and a bandpass filter centered at or above the *source* file's own Nyquist frequency is a degenerate configuration that produces meaningless output — probe the source's real sample rate first and skip any band at or past that file's Nyquist entirely.

### The Remix tab: Sound / Preset / Group modes (`plugins/editor/`, tab titled "Remix")

The Remix plugin also covers preset- and group-level editing, alongside per-sound editing. One tab, a three-pill mode switch at the top:

- **Sound mode** — the full per-sound editor: waveform + trim, Doppler, Speed/Pitch/Reverse, scatter/schedule randomization, Fluctuation (slow random volume+pitch drift), Volume envelope (drag control points on the waveform to shape volume over time), Noise gate, Noise reduction, the parametric EQ, HP/LP/Gain/Echo/Reverb filters, effect presets, undo/redo, A/B compare, autosave, and a Live-edit / Saved-audio preview toggle. None of this applies to more than one sound, so none of it shows outside Sound mode.
- **Preset mode / Group mode** — only the filter + EQ modules: HP/LP/Gain/Echo/Reverb, volume Fluctuation, the *same* parametric EQ module Sound mode uses (`EqEditor.js`'s `createEqEditorController` — one shared implementation across all three modes), effect presets, Reset filters — plus the minimal picker/membership chrome each needs (a preset `<select>`; Group mode adds a group `<select>`, "+ New group", a Members checklist, a name field, Delete, and a "Copy to preset…" picker for duplicating a group's filters/EQ/membership into another preset).

**Bus processing** lives in `src/renderer/audio/WholeMixChain.js` (a preset's whole-mix) and `SoundGroupChain.js` (one Sound Group) — each a `highpass → lowpass → EQ → gain → [parallel echo tap] → [parallel reverb tap] → fluctuation gain → brick-wall limiter` chain, installed by `AudioEngine` when a preset loads or groups change. A **Sound Group** is a named subset of one preset's sounds (`presets.js` `groups: [{id, name, soundIds, filters}]`, one group per sound max) routed through that shared chain instead of straight to `masterGain`. The Mixer's right-click menu toggles group membership without leaving the Mixer; both entry points write via `presets:updateGroups` and stay in sync through the `noctivago:sound-groups-changed` CustomEvent. A group's `filters` also supports an `occlusion` (0..1) field — `applyOcclusionToFilters` (`src/shared/constants.js`) log-interpolates the lowpass cutoff down and pushes reverb wet/size up together as occlusion increases (muffled *and* echoey reads as "behind a wall"; muffled alone just reads as quieter), combined with any manual Lowpass/Reverb settings by taking whichever is more occluded.

**Live spectrogram / status in Preset/Group mode**: a plugin has no reference to the Mixer's real `AudioEngine`, so the plugin dispatches a *synchronous* `noctivago:request-analyser` (or `request-mixer-status`) CustomEvent with a mutable `detail` object and reads it back the instant `dispatchEvent()` returns — the Mixer's listener sets `detail.node = engine.wholeMix.analyser` / `engine.groupChains.get(id)?.analyser` before returning. Safe because plugin and core renderer code share one JS realm (only the main-process boundary is actually sandboxed here).

**Export baking mirrors all of this**: `exportMix.js`'s `buildWholeMixPostChain` / `buildGroupFilterChain` / `renderGroupBuses` / `finalizeWholeMix` apply the same HP/LP/EQ/Gain/Echo/Reverb/volume-Fluctuation/occlusion a group or whole-mix carries. Reverb (`afir` convolution) and volume-Fluctuation (a baked `amultiply` gain envelope) each need their own separate ffmpeg pass; the rest is one linear `-af` chain. A per-sound loop sound's own volume **and** pitch Fluctuation bake too (`pitchEnvelope.js` → an `asendcmd` file stepping `rubberband`'s `pitch`, capped at a maximum command-file line count to stay well clear of a real ffmpeg bug in its own `asendcmd` parser on very large command files — see the ffmpeg version pinned in `package.json` before assuming this is fixed upstream), applied to its tiled full-duration track alongside the volume-Fluctuation `amultiply`; pitch-Fluctuation is per-sound only (a bus has nothing single to detune). A sound's Volume envelope bakes via the same WAV+`amultiply` machinery as volume-Fluctuation (`src/main/ffmpeg/volumeEnvelope.js`, `gainEnvelope.js`'s shared `writeWav`/`GEN_RATE`) rather than `asendcmd`, since it needs no continuous re-sampling loop — it rides along for free with every export since it bakes directly into the same short loop-clip WAV every other bake-only filter already uses.

**Export progress reporting must be wired into every real ffmpeg pass, not just the "big" ones** — `exportMix.js`'s `makeReporter` weights the Export tab's progress bar by audio-seconds of work (`step()`/`tick()`/`completePhase()`), and any pass long enough to matter that skips this looks indistinguishable from a hang: this exact bug has been hit and fixed three separate times for three different passes (v0.1.150 for the video re-encode and for Sound Group bus rendering, and again 2026-09-14 for `combineTracks`/`reduceTrackCount`'s "Merging N track groups…" pre-combine step, reported directly as a "fail log" after an export sat frozen on it for 37 real minutes). When adding a new ffmpeg-backed export phase, budget its expected seconds into `totalWorkSeconds` up front and wire its `onProgress` into `reporter.tick`/`completePhase` from the start rather than assuming a short pass — `combineTracks` had gone unwired since the pre-combine rounds were first added because each individual chunk combine had seemed cheap, until a dense enough export (243 tracks in one Sound Group) made it the single longest phase.

**`plugins/editor/` is self-contained** by the `plugin://` path-traversal guard — it carries its own bundled copies of `AudioEngine.js`, the waveform-drawing code, `LoopEditor.js`, `Modulator.js`, `NoiseGate.js`, `util/time.js`, and `MAX_BUFFER_CLIP_SECONDS` — duplicated from core, not shared. Keep the copies in sync if core's change.

### Presets as primary context: per-preset sound overrides

A preset's `sounds[]` items are `{soundId, volume, overrides}`, where `overrides` is `null` (pure inheritance from the sound's shared baseline) or a bag of the overridable keys named in `src/shared/constants.js`'s `OVERRIDABLE_SOUND_KEYS` (trim, filters/EQ, crossfade, Speed/Pitch, play mode, scatter/schedule config). Editing a shared sound while one preset is loaded only changes that preset's own copy — switching to a different preset shows its own separately-saved version, or plain baseline if that preset never touched it. The merge (`applySoundOverride(entry, override)` in `src/shared/constants.js`) is the single source of truth for this, shared by `library.js` (bake-eligibility) and `tabs/mixer/index.js` (the live resolution layer); `plugins/editor/index.js` and `plugins/export/index.js` each keep their own duplicated copy per the plugin sandbox's can't-import-outside-its-directory rule. `Fluctuation` is deliberately excluded from the override system — it's architecturally separate (own debounce, excluded from Remix's undo/snapshot system) and isn't a Save-button-driven field.

The app always has at least one preset loaded — `presets.js`'s `ensureDefaultPreset` creates a "Default" preset (seeded from whatever's currently included, if migrating from an older version with no presets at all) if none exists, called from `src/main/index.js`'s startup bootstrap. Deleting the last remaining preset auto-creates a replacement seeded from the deleted preset's own sounds/overrides, so a preset is always active.

## Plugin ecosystem note

`plugins/export/` (mix export/rendering to a file) and other first-party plugins follow the same self-contained, `plugin://`-loaded pattern described above. See each plugin's own `manifest.json` and `index.js` for specifics — the patterns described for the Remix plugin (self-contained copies of shared logic, live-preview-vs-bake split, staleness checks reusing the `filters` object) generalize to any plugin doing similar work.

## Freesound import

Search/preview/import sounds from [Freesound.org](https://freesound.org) directly into the library, from the same "+" add-sound menu as every other import path (`src/renderer/core/FreesoundDialog.js`).

**Auth**: a single app-wide API token (`FREESOUND_API_KEY`, requested once at freesound.org/apiv2/apply), baked in at build time exactly like `NOCTIVAGO_UPDATE_TOKEN` (`electron.vite.config.js`'s `__FREESOUND_API_KEY__`, main process only). This is Freesound's simplest auth shape and covers everything this feature needs — text search and downloading a sound's **preview** (compressed mp3, not the original file). OAuth2 (a per-user login flow) is only required for write actions (upload/rate) or for downloading a sound's full original-quality file, neither of which this feature does — importing a preview is plenty for a looping ambient sound and keeps the whole feature to one token instead of a login flow. Unlike the update token, this one is deliberately baked into **both** the GitHub release and the itch.io build (`.github/workflows/release.yml`) — it's a free, re-issuable, read-only key rather than a real credential, so the owner accepted it being extractable from a public binary rather than losing the feature on itch.io.

**Main process** (`src/main/freesound/`): `client.js` does the search call and builds an authorized (token-appended) preview URL; `download.js` reuses the bundled ffmpeg (`runFfmpegToFile`, same shape as `library.js`'s own direct-link download) to pull a preview down to a scratch wav; `protocol.js` registers a `freesound-preview://` privileged scheme (alongside `sound://`/`plugin://` in `src/main/index.js`) that proxies live preview *auditioning* through an authorized fetch — the renderer only ever sees the plain, unauthenticated preview URL Freesound's search response returned, and the API token never crosses into the sandboxed renderer. `authorizedPreviewUrl`'s hostname check doubles as an SSRF guard against a URL that isn't actually pointing at Freesound.

**Import** (`library.js`'s `addSoundFromFreesound`) downloads the preview and funnels it through the exact same `addSound(keepCopy: true)` path every other import already uses, plus one new field: `source: { type: 'freesound', freesoundId, username, license, pageUrl, importedAt }`, carrying the attribution a CC-BY (or similar) sound legally needs — surfaced as a small "Freesound" badge in the Mixer (`SoundRow.js`, reusing the Composite badge's styling) whose tooltip shows the author/license.

## Releasing and auto-update

`npm run release:win` (`electron-vite build && electron-builder --win --publish always`) builds the Windows installer and publishes it as a GitHub Release, via `electron-builder.yml`'s `publish` config. A GitHub Actions workflow can run this automatically on any pushed tag matching `v*`, using GitHub Actions' own auto-provided `GITHUB_TOKEN` to create the release and upload the installer.

**In-app update checking** (`src/main/autoUpdate.js`, `electron-updater`) checks GitHub Releases on every startup of a *packaged* build (`app.isPackaged` gate — never runs under `npm run dev`), and only ever prompts before acting: a "Download?" dialog on `update-available`, then a separate "Restart now?" dialog on `update-downloaded`. `autoUpdater.autoDownload`/`autoInstallOnAppQuit` are both `false` for exactly this reason — nothing happens silently.

If this repository is public, `electron-updater`'s GitHub provider can read releases with no authentication at all — no token needed. (If forking this project to a private repository, `electron-updater`'s GitHub provider needs a token to read releases; see its own documentation for the `GH_TOKEN` environment variable it reads at runtime — avoid baking a broad-access token into a shipped binary, use a narrowly-scoped, read-only token instead.)
