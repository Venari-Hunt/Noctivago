# Noctívago

Windows desktop ambient sound mixer, inspired by the Linux app [Blanket](https://github.com/rafaelmardojai/blanket) (not a port — Blanket is GTK/Linux-only). Electron + vanilla JS/DOM (no UI framework). Original MVP spec: `C:\Users\jluca\.claude\plans\ok-i-m-fine-with-hidden-lemur.md`.

The user (owner of this project) is not a developer — explain setup steps explicitly, don't assume familiarity with the toolchain.

## Running it

```
npm install
npm run dev
```

Two environment quirks that show up in fresh shells on this machine (both needed before `npm`/`node`/Electron will work):
- `node`/`npm` aren't reliably on `PATH` in every shell — `$env:Path += ";C:\Program Files\nodejs"` if `node -v` fails.
- If launching Electron produces `Cannot read properties of undefined (reading 'whenReady')`, an inherited `ELECTRON_RUN_AS_NODE=1` env var is forcing Electron to run as plain Node. Clear it: `Remove-Item Env:\ELECTRON_RUN_AS_NODE`.

`ffmpeg-static`'s postinstall (which downloads the actual ffmpeg binary) sometimes gets skipped by npm's script-allowlist prompt — if ffmpeg-dependent features (waveform, loop clips) fail, check `node_modules/ffmpeg-static/ffmpeg.exe` exists; if not, run `node node_modules/ffmpeg-static/install.js`.

Under `npm run dev` with more than one display connected, `src/main/index.js`'s `devWindowPosition()` opens the window directly on the highest-numbered display rather than the default (primary, centered) position — the owner keeps working there (gaming, etc.) while a dev session runs and doesn't want a window popping up over whatever's already on screen. Computed *before* window creation (passed as `x`/`y` to the `BrowserWindow` constructor), not moved after the fact — an after-the-fact move still means the window visibly flashes on the primary display first. Gated on `!app.isPackaged`, so a real installed build is never affected.

## Architecture

- `src/main/` — Electron main process.
  - `index.js` — window creation, custom `sound://` protocol (serves either the original file or a rendered loop clip, see below) and `plugin://` protocol (serves plugin files, see Plugins below).
  - `ipc.js` — IPC handlers.
  - `library.js` — registered sound files, persisted via `electron-store`.
  - `presets.js` — saved mixes.
  - `ffmpeg/` — ffmpeg integration (see below). `runFfmpeg.js` is the reusable spawn wrapper; `ffmpegPath.js` resolves the bundled binary; `loopClip.js` and `waveformPeaks.js` are its two current consumers.
  - `plugins/` — `registry.js` (scans + caches bundled/user plugin manifests), `protocol.js` (`plugin://` handler + path-traversal guard), `invoke.js` (dispatches `plugin:invoke` IPC to a plugin's own main-process module).
- `src/preload/index.js` — contextBridge API exposed to the renderer as `window.noctivago` (namespaces: `library`, `presets`, `audio`, `plugins`).
- `src/shared/constants.js` — plain constants imported by both main and renderer (e.g. `MAX_BUFFER_CLIP_SECONDS`).
- `src/renderer/` — plain JS/DOM UI, no framework.
  - `core/TabHost.js` — tab bar + lazily-mounted `<section>` per tab.
  - `core/PluginLoader.js` — discovers plugins via IPC, dynamically `import()`s each one, registers its tab(s).
  - `tabs/mixer/index.js` — the entire sound mixer (was `main.js` before the plugin-architecture rework), registered as the first tab via `mount(container)`.
  - `audio/AudioEngine.js`, `audio/SoundSource.js` (streaming playback), `audio/BufferSoundSource.js` (buffer/gapless playback).
  - `ui/*.js` — SoundList, SoundRow, PresetsModal (mixer-specific, used only by `tabs/mixer/`). Trimming/filtering UI (`LoopEditor.js`, waveform drawing) used to live here but moved to the Remix plugin — see below.
  - `main.js` — now a tiny bootstrap: creates the `TabHost`, registers the Mixer tab synchronously, then calls `loadPlugins()`.

### Playback: two modes, chosen automatically per sound

**Stream mode** (`LocalFileSoundSource`, the default): each sound plays through an `<audio>` element (`src="sound://<id>"`) piped into `MediaElementAudioSourceNode → highpass BiquadFilterNode → lowpass BiquadFilterNode → filter GainNode → per-sound GainNode → master GainNode`. The filter nodes apply the sound's saved highpass/lowpass/gain settings (same chain shape as the Remix plugin's live preview) — this is what makes filters audible even for sounds that never qualify for a baked buffer clip (see below). The `sound://` protocol hand-rolls HTTP Range support via `fs.createReadStream` (Electron's `net.fetch` on `file://` URLs was found to silently ignore Range headers in this Electron version — don't assume it works, verify). Looping is a `requestAnimationFrame` boundary-check + seek-back — not sample-accurate, can have an audible click/gap at the seam. This is what makes arbitrarily long files (hours) playable at all without loading them into memory.

**Buffer mode** (`BufferSoundSource`): whenever the user trims + sets filters and hits Save in the Remix plugin (see below), ffmpeg renders *just that loop region*, with any highpass/lowpass/gain filters baked in via `-af`, out to a small WAV (`src/main/ffmpeg/loopClip.js`, `getUserData()/clips/<id>.wav`) — but only if the region is ≤ `MAX_BUFFER_CLIP_SECONDS` (600s/10min, in `src/shared/constants.js`). Since the clip is now short regardless of how long the source file was, it's fully decoded client-side (`decodeAudioData`) into a native `AudioBufferSourceNode` with true `loop=true`/`loopStart`/`loopEnd` — sample-accurate, click-free. `tabs/mixer/index.js`'s `loopClipEligible(entry)` checks `entry.loopClipReady` + that the clip's recorded loop points *and* filters still match the entry's live ones (4-way staleness check, since either changing without re-saving should fall back to streaming) before trying buffer mode, and falls back to stream mode on *any* failure (missing ffmpeg, corrupt clip, decode error) — buffer mode is strictly additive and only ever affects loop-seam smoothness, never whether filters apply, never required for the app to work.

`BufferSoundSource.pause()` tracks elapsed offset manually (`AudioBufferSourceNode` is one-shot — can't be pause/resumed like `<audio>` can) so resuming continues from the same position rather than restarting, matching stream mode's behavior.

**Getting a sound into buffer mode**: the default is lazy — `tabs/mixer/index.js`'s `maybeAutoBake` bakes a full-file clip the first time an eligible, never-baked sound actually plays. A Settings toggle (`eagerlyBakeOnImport`, off by default) makes this eager instead: `library.js`'s `maybeEagerBakeOnImport`, fired fire-and-forget from `addSound()` — the single choke point every import path (single file, folder-as-preset, folder-as-tag, watch-folder) already funnels through — probes the file's real duration via ffmpeg directly (`loopClip.js`'s `probeDurationSeconds`, since a fresh import has no `durationSeconds` yet; that's normally only learned lazily via the `<audio>` element's own `loadedmetadata`) and bakes immediately, before the sound is ever played. Same `MAX_BUFFER_CLIP_SECONDS` cap and bake call as the lazy path — this only changes *when* the first bake happens, not how.

### Playback mode: Loop vs. Random Interval ("scatter")

Every sound's `playMode` (`'loop'` default, or `'scatter'`, in `library.js`) picks between the two source families above (continuous loop) and a second pair — `BufferScatterSource`/`StreamScatterSource` (`src/renderer/audio/ScatterSoundSource.js`) — that instead replay the trimmed clip as one-shots on a randomized gap (`entry.scatter.minGapSeconds`/`maxGapSeconds`) with a randomized pitch each time (`entry.scatter.minPitchSemitones`/`maxPitchSemitones`; both left at 0 means *fully* random pitch per replay, not "no shift" — an explicit, deliberate special case). This is the game-engine "scattered ambience emitter" pattern (Wwise Random Container, FMOD's Scatterer Instrument, Unity's Audio Random Container) — researched before implementing, per the standing instruction in [[feedback_research_before_complex_tasks]] — for a short, event-like sound (a creak, a bird call) inside a longer ambient mix, rather than looping it back-to-back. `tabs/mixer/index.js`'s `desiredSourceKind(entry)` crosses `playMode` with buffer eligibility into four kinds (`loop-buffer`/`loop-stream`/`scatter-buffer`/`scatter-stream`); `reconcileSource` swaps the live source whenever the desired kind or the bake itself changes, same pattern the original loop/stream swap already used.

`BufferScatterSource` uses the decoded clip's native `AudioBufferSourceNode.detune` (cents) for pitch — true independent pitch shift with zero effect on shot duration or the gap timer, a nicer primitive than the playbackRate-linked pitch/tempo coupling most non-web engines settle for. `StreamScatterSource` (the fallback for a trim too long to bake) has no such primitive on `<audio>`, so it reuses `playbackRate` the same way Speed does elsewhere in this app — a pitch shift there also changes shot tempo, a documented, accepted limitation.

Scatter-mode clips reuse `renderLoopClip` unchanged rather than a second bake pipeline: both `library.js` and `tabs/mixer/index.js` have an `effectiveCrossfadeSeconds(entry)` helper that forces the crossfade to `0` whenever `playMode === 'scatter'` (crossfade+rotation, which permanently reorders the clip's own audio to hide a *looping* wrap point, would be actively wrong for a clip that's never looped back-to-back) — `0` already means "plain trim, no rotation" in `loopClip.js`'s `doRender`, so this is a pure input-shaping trick, not new ffmpeg logic. Switching a sound between Loop and Random Interval in the Remix plugin (which owns this control, alongside trim/filters/crossfade/speed-pitch — the same "shape a sound" editor as everything else that affects the bake) naturally invalidates the old bake via the same staleness check every other trim/filter edit already goes through.

### Waveform

`src/main/ffmpeg/waveformPeaks.js` streams the *whole* original file through ffmpeg as downsampled mono float32 PCM and reduces it into `[min,max]` peaks per pixel column with O(1) memory (never buffers the decoded audio) — works for files of any length/format. This replaced an earlier renderer-side `decodeAudioData`-based approach that was capped at 30 minutes and fell back to a bare time-ruler beyond that.

**BUG FIX (canvas stretch/blur)**: the Remix trim waveform (`#editor-canvas`, drawn by `plugins/editor/audio/waveform.js`) had its internal bitmap resolution (fixed `640x160` HTML attributes) out of sync with its actual rendered CSS size (styled `width: 100%`, so it stretches to fill the panel on any normal window width) — the browser scaled the smaller bitmap up non-uniformly to fill the box, which is exactly what a user-reported "totally stretched and blurry" waveform looks like. Same root cause and same fix as the Remix EQ graph's own identical bug (see below) — `waveform.js` gained its own `resizeCanvasForDisplay()`, resizing the canvas's real bitmap resolution to its rendered CSS size × `devicePixelRatio` before every draw and scaling the context so the rest of the drawing code keeps working in plain CSS-pixel coordinates. `LoopEditor.js`'s own interaction math (drag, wheel, hit-testing) was never affected — it already worked in `rect.width`/`rect.height` (CSS-pixel space) throughout, only the *drawing* function had the bug.

**Live spectrum analyzer**: `PreviewSource.js` taps an `AnalyserNode` (never connected onward — a pure read tap) off `outputGainNode`, the single point both crossfading voices' signals combine into, so it reflects whichever voice is actually audible regardless of crossfade state. `EqEditor.js`'s `tickSpectrum(analyserNode)` is called once per frame from the same `tickPreviewPlayhead()` rAF loop that already drives the waveform playhead and sticky progress bar (no separate loop) — reads `getByteFrequencyData()` (already dB-scaled 0-255 by the Web Audio API itself, no extra scaling needed) and redraws a filled area in pink (`rgba(247, 118, 142, ...)`, matching the FL Studio "Fruity Parametric EQ 2" reference this was modeled on) connecting each linearly-spaced FFT bin's point via the graph's own log-frequency `freqToX`. Takes over from the static band-energy backdrop (above) whenever playing; `clearSpectrum()` (called on pause/stop/dispose) falls back to the static backdrop rather than freezing on the last live frame.

**Per-band filter types**: 7 bands (matches the real FL Studio reference, researched directly rather than assumed — see `noctivago_task_list` memory for the full research and the deliberate cut-list of reference features judged not worth cloning, e.g. Mid/Side processing, Linear Phase mode, phase rotation display, none of which map onto Noctívago's single-independent-sound signal flow). Each band independently one of 8 types via a `type` field on the band object (`'off' | 'lowpass' | 'highpass' | 'bandpass' | 'notch' | 'lowshelf' | 'highshelf' | 'peaking'`), selected via a `<select>` next to the Freq/Gain/Q precision fields. A lucky architecture fit: Web Audio's native `BiquadFilterNode.type` already covers 7 of the 8 shapes directly — only `'off'` is a pseudo-type (not a real biquad shape), mapped to `'allpass'` at the node level (`eqNodeType()` in both `SoundSource.js` and `PreviewSource.js`) since allpass leaves the amplitude spectrum completely unchanged, a true no-op without needing to dynamically rewire the fixed per-band node chain. `.type` isn't an AudioParam (a plain property, can't be smoothed like frequency/Q/gain) — only reassigned when it actually changes, to avoid resetting the filter's internal state on every unrelated update. Baking dispatches per band to the matching ffmpeg filter (`loopClip.js`'s `buildEqBandFilter`: `lowpass`/`highpass`/`bandpass`/`bandreject`(notch)/`bass`(lowshelf)/`treble`(highshelf)/`equalizer`(peaking), `'off'` simply omitted from the chain) — all six real filter names verified chained together in one real ffmpeg invocation before writing any app code. Only peaking/lowshelf/highshelf are true no-ops at `gainDb: 0` (their whole effect is proportional to gain); lowpass/highpass/bandpass/notch have no gain parameter at all and always shape the signal whenever selected, so they're never skipped just for looking "neutral."

### Why ffmpeg, not more JS

Both the loop-seam click and the waveform-for-long-files problems trace back to the same root cause: `decodeAudioData` on a whole multi-hour file either throws `EncodingError` or uses gigabytes of RAM (this is *why* stream mode exists at all — see git history around the original long-file rewrite). ffmpeg (bundled via `ffmpeg-static`, spawned via `child_process`, never a shell) processes files without holding them fully in memory, sidestepping that limit entirely. `runFfmpeg.js` is deliberately generic/domain-agnostic so ffmpeg-based features reuse it rather than each rolling their own spawn logic — the Remix plugin's filter baking (see below) is the first consumer beyond loop clips/waveforms.

**Packaging note:** `electron-builder.yml` has `asarUnpack: [node_modules/ffmpeg-static/**]` — required because binaries can't execute from inside an asar archive. Verified working since `v0.1.0` (real install, see Status) and re-confirmed structurally on every local `npm run build:win` run since.

### App icon

`resources/icon.ico` is not a plain PNG electron-builder auto-converts — it's hand-built by `resources/icon-src/build-ico.mjs` (run `node resources/icon-src/build-ico.mjs` from the repo root to regenerate after editing `resources/icon-src/render.html`'s SVG and re-rendering `icon-master.png`). **Why this matters**: electron-builder's own PNG→ICO conversion PNG-compresses every embedded size, but Windows only honors PNG compression for the 256px entry — sizes below that (16/24/32/48/64, exactly what the taskbar and Windows Search use) silently fall back to a generic icon if they're PNG-compressed instead of classic uncompressed BMP/DIB data. Discovered the hard way: `v0.1.13` shipped with an auto-converted icon that looked fine in most places but showed a generic icon on the taskbar and in Windows Search; confirmed via low-level PE resource inspection (`LoadLibraryEx`/`EnumResourceNames`/`FindResource` on the built `.exe`) that every size, not just 256, had been PNG-compressed. The build script now generates real BMP/DIB data (with a proper 1bpp AND mask derived from the alpha channel) for every size below 256, PNG-compressing only the 256 entry — verified by loading the result back through .NET's `System.Drawing.Icon` (Windows' own icon parser), not just by trusting the script's own logic. `src/main/tray.js` (system tray) and `src/main/index.js` (`BrowserWindow`'s `icon` option) both read the same design; the tray one stays a plain PNG since `nativeImage`-based tray icons don't have this multi-size ICO requirement.

## Plugins

The app is meant to be open-sourced with outside contributors adding functionality as plugins rather than editing core — modeled on Obsidian's plugin architecture, but **deliberately not** copying its trust model (Obsidian plugins get raw Node/Electron access; here that's split by process, see below), since this codebase has been consistently more sandboxed (`contextIsolation: true`, no `nodeIntegration`, everything served through custom protocols rather than raw file access).

**A plugin is a folder** containing `manifest.json` (`id`, `name`, `version`, `main` required; `mainProcess` optional) + a `main` entry file exporting a default class:
```js
export default class MyPlugin {
  constructor(app, manifest) { this.app = app }
  async onload() { this.unregister = this.app.tabs.register({ id, title, mount: (container) => {...} }) }
  async onunload() { this.unregister?.() }
}
```
Two real examples exist in `plugins/`: `hello-world/` (minimal working plugin) and `broken-plugin-example/` (deliberately throws in `onload()` — a regression-test fixture proving one broken plugin can't take down the app or other plugins).

`register()` also accepts an optional `mountSticky: (container) => {...}` alongside `mount` — its own section in the shared sticky bar directly under the tab bar (`#tab-sticky-bar` in `index.html`, wired in `TabHost.js`), always visible regardless of how far the tab's own content is scrolled. This is a fixed-height flex sibling of `main` in `#app`'s layout, not `position: sticky` — deliberately simpler, no scroll-container edge cases to get wrong. Distinct from the toolbar above the tab bar (global mix Play all/master volume, app-wide): the sticky bar is per-tab, for controlling whatever's local to that specific tab (e.g. the Remix plugin's own trim preview, see below) — only the active tab's sticky section is shown, and the shared bar itself hides entirely for a tab that doesn't provide one (like the Mixer, which has no single "current preview" the way Remix does). Same lazy-mount-once-then-show/hide lifecycle `mount` already has, not remounted on every tab switch.

**Where plugins live**: `plugins/<id>/` at the repo root for bundled/official plugins (packaged into the app via `electron-builder.yml`'s `extraResources`), and `<userData>/plugins/<id>/` for user-installed ones (parallel to Obsidian's `.obsidian/plugins/`). `src/main/plugins/registry.js` scans both and merges them; on an id collision, bundled wins. Presence in either directory *is* enabled — there's no enable/disable toggle UI in v1 (disable by moving the folder out).

**How loading actually works**: `plugin://<id>/<path>` is a privileged `standard` Electron scheme (registered in `main/index.js`, handled in `src/main/plugins/protocol.js`) serving a plugin's own files as real ES modules — `PluginLoader.js` in the renderer does `await import(\`plugin://${id}/${manifest.main}\`)`, which resolves relative imports between a plugin's own files correctly and shows real filenames/breakpoints in DevTools. This directly extends the same pattern `sound://` already established for serving local files into the sandboxed renderer. Verified working (including relative cross-file imports) via a throwaway spike before any of the rest was built.

**Security posture — split by process**:
- Renderer-side plugin code (`manifest.main`) is exactly as sandboxed as core code — no `require`, no `ipcRenderer`, only the curated `app` object (`{ tabs, noctivago, plugin }`) it's constructed with. `app.noctivago` is `window.noctivago` handed through wholesale (already curated/whitelisted) — no per-plugin capability scoping in v1, any enabled plugin can call any core API, matching Obsidian's own trust model closely enough not to need more yet.
- Main-process plugin code (`manifest.mainProcess`, opt-in) is ordinary trusted Node — same trust level `src/main/*.js` already has — loaded via `src/main/plugins/invoke.js`. This is the only place a plugin gets real power (spawn ffmpeg, touch disk), reached from the renderer via one generic `api.plugins.invoke(pluginId, method, ...args)` rather than each plugin needing its own hand-written IPC channel in `ipc.js`.
- This is not real code sandboxing — a `mainProcess` plugin still has full Node power once opted into, same as Obsidian's actual model. Trust boundary remains "the user reads/trusts plugin source before installing," just scoped to a smaller, more visible manifest field than "the whole plugin."

**Explicit non-goals for v1** (deferred, not designed): plugin marketplace/browser, hot-reload dev tooling, settings-tab API, command palette, ribbon icons, enable/disable UI, per-plugin capability scoping, persistent per-plugin data storage.

**Full design rationale** (alternatives considered and rejected, e.g. `executeJavaScript` injection vs. dynamic `import()`, why core doesn't route through the plugin loader itself) is in the plan file this was built from: `C:\Users\jluca\.claude\plans\snoopy-booping-sky.md`.

### The Remix plugin (`plugins/editor/`, tab titled "Remix")

The first real (non-toy) plugin, and the one that validated the plugin API against an actual feature. All per-sound editing — trim points *and* filters (highpass, lowpass, gain) — lives here now; it moved out of the core Mixer tab entirely (the old in-mixer Loop Editor modal, its canvas/waveform code, and the "Trim" button are gone from `src/renderer/` — deleted, not just unused, once nothing else referenced them).

- **Live preview without touching ffmpeg**: `audio/PreviewSource.js` streams the sound the same way `LocalFileSoundSource` does (`sound://<id>`, works for any file length) but inserts a `BiquadFilterNode` (highpass) → `BiquadFilterNode` (lowpass) → `GainNode` chain before the output gain. Dragging a filter slider calls `setTargetAtTime` on these nodes directly — instant, click-free, audible feedback with zero ffmpeg round-trips. ffmpeg only runs once, on Save.
- **Save bakes trim + filters in one ffmpeg pass**: reuses `loopClip.js`'s renderer (extended to accept a `filters` object and insert `-af highpass=f=…,lowpass=f=…,volume=…dB` into the ffmpeg args), rather than building a second, parallel baking pipeline. The Mixer's buffer-mode eligibility check compares filters as well as loop points, so changing either without re-saving correctly falls back to streaming (still filtered — see Playback above — just with a small loop seam) instead of playing a stale baked clip.
- **Save never touches the original file**: trim points and filters are persisted as metadata (`library.js`, via `electron-store`) and applied live by both playback modes; the ffmpeg render is a disposable derived cache (`getUserData()/clips/<id>.wav`), regenerated on every Save, not an edit to the source audio. The Remix plugin's Save button surfaces this outcome directly (baked / bake failed / skipped because the trim exceeds the buffer-mode cap) via a status line under the button — added after user feedback that a silent Save was confusing.
- **Self-contained by design, not by accident**: a plugin can't import files outside its own directory (enforced by the `plugin://` path-traversal guard), so `plugins/editor/` has its own copies of `AudioEngine.js`, the waveform-drawing code, `LoopEditor.js` (the drag/scrub/snap canvas controller), and `util/time.js` — duplicated from core rather than shared. This is a deliberate tradeoff matching Obsidian's "bundle your own dependencies" plugin model, not an oversight; keep it in mind if core's copies of these change and the plugin's need the same fix.
- `MAX_BUFFER_CLIP_SECONDS` (600s) is duplicated as a local constant in `plugins/editor/index.js` for the same cross-directory-import reason — keep it in sync with `src/shared/constants.js` if that value ever changes.
- **Parametric EQ**: a fixed 6-band peaking EQ, folded into the *existing* `filters` object as `filters.eq: [{freqHz, gainDb, q}, ...]` (`library.js`'s `defaultEqBands()`) rather than a new top-level field — reuses every bit of existing filters plumbing (staleness comparison, `updateFilters`, live-update paths) with zero new schema/IPC code. A scoped-down take on FL Studio's "Fruity Parametric EQ 2" (the reference screenshot this was designed from, see `noctivago_remix_eq_future` memory): fixed band count, no add/remove-node UI, and the connecting line drawn between nodes is a straight polyline through each band's own point, not the true composite biquad response curve — both deliberate cuts to keep it buildable in one pass. `plugins/editor/ui/EqEditor.js` is the draggable-node canvas (X = log-frequency, Y = gain, mouse wheel over a node = Q — no third drag axis available); `index.js` also exposes precision numeric fields (Freq/Gain/Q) for the selected band, mirroring the Start/End/Length text-input pattern next to the trim handles. Presets (Muffled/Phone/etc.) deliberately never touch `.eq` — only "Reset filters" (via `NEUTRAL_FILTERS.eq`) or a per-sound "Reset EQ" button do. Live preview inserts a chain of 6 `BiquadFilterNode`s (`type: 'peaking'`) between the lowpass and filter-gain nodes in both `PreviewSource.js` and core's `LocalFileSoundSource` (`src/renderer/audio/SoundSource.js`), same position ffmpeg's bake applies them (`equalizer=f=…:width_type=q:w=…:g=…` in `loopClip.js`'s `buildFilterChain`, verified against the real bundled binary before shipping) so preview and the real Mixer agree. **Real bug caught during verification**: the canvas's interaction math (hit-testing, drag) initially used `canvas.width`/`canvas.height` (the internal 640×140 bitmap resolution) instead of `canvas.getBoundingClientRect()` (the actual rendered CSS size, ~1319px wide here since the canvas is styled `width: 100%`) — this silently broke all dragging, since mouse coordinates and node positions were computed in two different, mismatched coordinate spaces. Fixed by following `LoopEditor.js`'s already-established split exactly: interaction math uses `rect.width`/`rect.height`, drawing uses `canvas.width`/`canvas.height` — caught by an actual CDP drag test coming back with no-op results, not by code review.
- **Sticky playback bar**: Play/Pause, a loop toggle, a progress bar/time readout, and a preview-volume slider live in `mountSticky()` (see the Plugins section above), not the scrollable panel body — always visible under the tab bar regardless of scroll position. Progress is relative to the *trimmed loop region* (`loopStart`..`loopEnd`), not the whole original file, matching what's actually being previewed/looped. The loop toggle is an icon button (`.editor-loop-icon-btn`/`-active`, an inline SVG repeat glyph recolored via `currentColor`), not the checkbox it used to be — same underlying `this.looping` boolean and `previewSource.setLooping()` call, purely a restyle plus relocation. The volume slider drives `PreviewSource.setVolume()` directly (that method already existed — nothing previously exposed it in the UI, the preview was always hardcoded to 0.7); `this.previewVolume` persists across sound switches within the tab session, same pattern `this.looping` already established, distinct from the Mixer's own per-sound saved volume. `mount()` and `mountSticky()` populate the same shared `this.els` object; ordering matters (`mount` then `mountSticky`, both synchronous, see `TabHost.js`) since `wireControls()` (called from `mount()`) no longer wires the Play/Pause or loop-toggle listeners itself — those move to `mountSticky()`'s own wiring, run immediately after.
- **EQ graph backdrop**: translucent bars behind the EQ curve showing roughly how much energy the sound actually has around six fixed reference frequencies (`library.js`'s `defaultEqBands()` frequencies, independent of wherever the user later drags a node) — a deliberately scoped-down alternative to a literal live spectrum analyzer (which would need real-time `AnalyserNode` playback + a continuous rAF redraw loop, meaningfully more scope) or a literal waveform (which wouldn't make sense on this graph's *frequency*-domain X-axis — a time-domain plot doesn't belong there, an early framing mistake caught before implementing). `src/main/ffmpeg/bandEnergy.js`'s `computeBandEnergy` runs one `bandpass`-filtered ffmpeg pass per frequency (in parallel — wall-clock cost is roughly the slowest single pass, not the sum), computing RMS in JS from the piped PCM, verified against the real bundled binary before writing any app code. Static, load-time-only analysis (`plugins/editor/index.js`'s `loadSound()`, fire-and-forget) — not tied to playback, not recomputed as the user drags EQ nodes. **Two real bugs caught during verification, not by code review**: (1) the output PCM sample rate was originally 11025Hz (Nyquist 5512.5Hz) — comfortably below the 6000Hz and 14000Hz bands, so ffmpeg's own anti-aliasing filter during the final resample was silently discarding real signal at those frequencies for *every* file, not just an edge case (confirmed: a genuinely loud real 14kHz tone measured as near-silence at 11025Hz output vs. correctly strong at 32000Hz); (2) a bandpass filter centered at or above the *source* file's own Nyquist is a degenerate configuration, not just imprecise — confirmed a low-sample-rate (22050Hz) test file spuriously reported its 14000Hz band as the *loudest* of all six for a pure 100Hz tone. Fixed by raising the output rate to 32000Hz and probing the source's real sample rate first (parsed straight out of ffmpeg's own stderr stream-info line), skipping any band at or past that file's Nyquist entirely rather than trusting a degenerate filter's output.

## Releasing and auto-update

`npm run release:win` (`electron-vite build && electron-builder --win --publish always`) builds the Windows installer and publishes it as a GitHub Release, via `electron-builder.yml`'s `publish: {provider: github, owner: joaovenari, repo: Noctivago, private: true}`. `.github/workflows/release.yml` runs this automatically on any pushed tag matching `v*` (or manually via workflow_dispatch), on `windows-latest`, using GitHub Actions' own auto-provided `GITHUB_TOKEN` (scoped read/write to just this repo via the workflow's `permissions: contents: write`) to create the release and upload the installer — no manual setup needed for this half.

**In-app update checking** (`src/main/autoUpdate.js`, `electron-updater`) checks GitHub Releases on every startup of a *packaged* build (`app.isPackaged` gate — never runs under `npm run dev`), and only ever prompts before acting: a "Download?" dialog on `update-available`, then a separate "Restart now?" dialog on `update-downloaded`. `autoUpdater.autoDownload`/`autoInstallOnAppQuit` are both `false` for exactly this reason — nothing happens silently.

**The one piece of manual setup this needs, because the repo is private:** `electron-updater`'s GitHub provider has to authenticate to read releases, and there's no config field for a token — it reads it from the `GH_TOKEN` environment variable at runtime. Baking the CI-publish token (`secrets.GITHUB_TOKEN`, broad repo-write access) into the *shipped app* would be a real credential-leak risk, so a **second, separate, narrowly-scoped token** is used instead: create a fine-grained PAT at github.com/settings/personal-access-tokens/new, scoped to only the `Noctivago` repo with read-only `Contents` permission, and add it as a repo secret named `NOCTIVAGO_UPDATE_TOKEN` (Settings → Secrets and variables → Actions). The release workflow passes it through as a build-time env var, and `electron.vite.config.js`'s `define: { __UPDATE_TOKEN__: ... }` bakes it into the compiled main-process bundle (empty string for any local/dev build, so nothing leaks into a build the user runs themselves). **Accepted risk, explicitly discussed:** this token still ships inside every installed copy of the app and could in principle be extracted by anyone who has it — acceptable per the user for now since distribution is limited to trusted people while the repo stays private ahead of a future public release.

**EQ bands gained a Gentle/Steep slope control** — the last item from the FL Studio parametric EQ clone's own research backlog (feasibility confirmed weeks earlier: ffmpeg's `highpass`/`lowpass` have a real `poles` parameter but `bandpass`/`bandreject` don't, and `BiquadFilterNode` has no slope parameter at all — cascading N identical filter instances in series was verified, on both sides, to be the one technique that works consistently across all four filter-*shaped* types). Only `lowpass`/`highpass`/`bandpass`/`notch` have a real slope concept (`SLOPE_CAPABLE_EQ_TYPES`, duplicated per the usual cross-file/cross-directory pattern in `EqEditor.js`, `SoundSource.js`, `PreviewSource.js`, and `loopClip.js`) — peaking/shelf bands are gain-shaped, not rolloff-shaped, and `'off'` does nothing, so the new Slope `<select>` next to Type hides/disables itself for those. `'steep'` means 4 identical cascaded stages (`STEEP_STAGE_COUNT`) instead of 1, each stage multiplying the rolloff by another ~12dB/octave (verified directly against the real bundled ffmpeg binary: four cascaded `highpass=f=1000:poles=2` instances measured ~34dB more attenuation than one).

**This meant a real architectural change**, similar in shape to the dynamic-node rework above but one level deeper: a "band" used to map to exactly one live `BiquadFilterNode`; now it maps to a *group* of 1–4 identical nodes chained internally. `SoundSource.js`/`PreviewSource.js` both gained an `eqNodeGroups` array (nodes re-grouped per band, for per-band parameter updates) alongside the existing flat `eqNodes` (still used for connect/disconnect bookkeeping), and their rebuild trigger changed from a plain band-count comparison to a per-band *topology fingerprint* (`eq.map(eqBandStageCount).join(',')`) — a plain length check can't tell a same-length type/slope change (which alters one band's own stage count) apart from a genuine no-op. `loopClip.js`'s `buildFilterChain` cascades the same single-band ffmpeg filter string `eqBandStageCount(band)` times in the `-af` chain rather than teaching `buildEqBandFilter` itself about repetition, keeping that function's per-type mapping unchanged. The EQ graph's composite response curve (`computeResponseCurve`) also folds stage count in — a steep band's own `getFrequencyResponse()` magnitude is summed in dB `stages` times rather than once, so the drawn curve honestly reflects the real cascaded rolloff, not just a single stage's shape.

**BUG FIX: an uncaught exception during waveform-peak extraction could crash-loop the entire app with an unstoppable "JavaScript error occurred in the main process" dialog** — found by the agent's own testing (a malformed IPC call, `getWaveformPeaks(id)` with no `targetWidth`), then confirmed to be a real architectural gap, not just a testing artifact, before fixing it. Root cause: `runFfmpeg.js`'s shared `runFfmpegPipe` (the reusable ffmpeg-stdout-streaming wrapper `waveformPeaks.js`, `bandEnergy.js`, and `loopClip.js` all build on) wired the caller's per-chunk callback directly into the raw Node stream's own `'data'` event (`child.stdout.on('data', onChunk)`) with no try/catch - a synchronous throw inside `onChunk` (here: `extractWaveformPeaks`'s bucket-accumulation loop indexing into a zero-length `peaks` array, since `Array.from({length: undefined})` silently produces `[]`) propagates straight up through Node's stream internals as an uncaught main-process exception, completely bypassing every caller's own try/catch around the awaited promise (the throw happens well after that executor already returned). ### The Export plugin (`plugins/export/`)

**Bakes a whole preset down to one audio file of a chosen length and format** - explicitly owner-prioritized ahead of everything else in the backlog ("I like this feature more than the others"), jumping past its own already-high ranked score. Started from an owner design question ("what about choosing a length and exporting an audio? is it hard?") that turned into the owner proposing the actual architecture themselves, live: "use the data inputted on the preset as grounds for a 'simulation'... run a 'simulation' of the events that will transpire within this [duration]... use the simulation output to create a single ffmpeg command." Confirmed sound and built essentially as proposed, with one caveat surfaced back and accepted (see below).

**Simulate first, render second.** `plugins/export/simulate.js` reuses the *exact* randomization/scheduling functions each playMode's real playback source already uses - `randomGapSeconds`/`randomPitchSemitones`/`randomVolumeScale` (mirroring `ScatterSoundSource.js`) rolled repeatedly until cumulative time exceeds the chosen export duration produces a scatter sound's shot list; `secondsUntilNextTrigger` (mirroring `ScheduledSoundSource.js`) rolled the same way produces a scheduled sound's trigger list. This is a dry run of the exact same process a live source uses to schedule its next event, just without any actual audio scheduling - zero new randomization logic, all duplicated per the plugin's own established "bundle your own dependencies" convention (a plugin can't import outside its own directory). **`simulateEvents({ entry, durationSeconds, now })` is the extensibility contract the owner explicitly asked for** ("it needs to work not only with what already exists but the features that will be added too"): dispatches by `playMode` to a per-mode simulator, so a future playMode only needs to add a case here (or, if the list grows, a lookup table) rather than the export pipeline hardcoding scatter/scheduled-specific logic inline. `'loop'` mode returns `null` deliberately - a looped sound has no discrete events, it just tiles.

**A `'times'`-type scheduled sound (real daily HH:MM triggers) is handled exactly per the owner's own explicit instruction**: "treat it as a sound with timed intervals. If the event of it playing falls out of the time scope just exclude it from the export." The simulator starts from the real current wall-clock time and rolls `secondsUntilNextTrigger` forward, including whatever real trigger moments happen to land within the export window and naturally excluding (not specially handling - the loop already stops the instant an offset would exceed the duration) any that wouldn't recur until after it ends. This means running the same export at different times of day can produce a different number of `'times'`-triggered events - an accepted, explicitly-instructed trade-off, not an oversight.

**Rendering (`src/main/ffmpeg/exportMix.js`), the one place the owner's "single ffmpeg command" framing needed a caveat** - surfaced directly and accepted before building: placing hundreds of shots (a scatter sound firing every ~30s across a multi-hour export easily reaches 500+) each with their own delay/pitch/volume in one giant `adelay`+`amix`+per-shot-`rubberband` graph would risk Windows command-line length limits and unwieldy filter-graph parsing. Practical shape instead: one ffmpeg pass **per included sound** - a `'loop'` sound bakes one crossfaded iteration (reusing `loopClip.js`'s existing bake logic completely unchanged, via a new `renderClipToPath` export that takes an explicit output path instead of the sound's own id-keyed managed clip slot, so export renders never disturb a sound's real cached buffer-mode clip) and tiles it via ffmpeg's own `-stream_loop`; a `'scatter'`/`'scheduled'` sound bakes one one-shot "shot" clip (crossfade forced to 0, matching `effectiveCrossfadeSeconds`'s existing reasoning) then places a copy at each simulated event's own offset via `asplit` (splitting the single input into N identical branches inside the filter graph, rather than opening the same short file hundreds of times) + per-branch `rubberband`+`volume`+`afade`+`adelay` + a final `amix`. **The graph is written to a script file and referenced via `-filter_complex_script`** rather than inlined on the command line, specifically so a dense export can't hit a command-line length limit regardless of shot count. Every per-sound track renders to the *exact* export duration (`apad=whole_dur=`); the final mixdown just `amix`es those together, then applies the **whole-mix EQ/gain and fade in/out last** - the owner's own explicit ordering ("should be applied on the whole mix after everything") - before encoding to the chosen format (wav/mp3/opus/flac/ogg).

**Verified directly against the real bundled ffmpeg binary before any of this was wired into the app**, per the project's own established discipline: a synthetic spike test placing 40 then 150 pitch/volume-varied one-shot clips via `asplit`+`adelay`+`amix` first caught a real bug in the *test methodology itself* (`amix`'s default `duration=first` stopped the output at the first branch's own short length, not the intended target - fixed with `duration=longest`+`apad`) before confirming the technique renders correctly and fast (150 shots across 5 minutes in ~4s, ~77x realtime). **Verified end-to-end against the real dev app**: a genuine 3-sound preset (one of each playMode - loop/scatter/scheduled) exported to a real 90-second file in ~1.8s; the output's actual measured duration was exactly 90.00s; RMS-sampling the real decoded audio across the whole file confirmed continuous non-silent content from all three sources, and precise sampling at the very start/end confirmed the fade-in/fade-out ramps land exactly where expected (near-silent at the true start/end, full level by ~1s in); a separate MP3-format export was independently verified to produce a valid, correctly-durationed MP3 stream. New UI: its own tab (not just a Presets-modal button, per the owner's explicit "I think this should be a new plugin... a new tab is the best approach") with preset/length/format pickers, a whole-mix Highpass/Lowpass/Gain+fade section (deliberately a simpler 3-control set for v1, not the full 7-band parametric EQ the per-sound Remix editor has - noted directly as a scope call, not silently reduced), and an Export button that opens a native save-location picker before running.

**Scheduled playback gained the exact same pitch/volume randomization and fade in/out controls Random Interval already has** - direct owner request, flagged explicit priority ("this takes precedence over anything"), reversing `v0.1.77`'s original deliberate scope cut (its own doc comment used to say "no pitch/volume randomization or fade envelope, since the whole point here is a *deterministic* cue at a known time"). Only the *timing* stays deterministic clock math; each trigger's own character is now randomized identically to a scatter shot. Implemented by exporting `randomPitchSemitones`/`randomVolumeScale`/`fadeSeconds`/`scheduleShotEnvelope` from `ScatterSoundSource.js` and importing them into `ScheduledSoundSource.js` (same directory, no cross-plugin restriction, so no third copy needed) - both `BufferScheduledSource` (gained a per-shot `shotGain` node, mirroring `BufferScatterSource`) and `StreamScheduledSource` (gained a persistent `shotGainNode` spliced into its filter chain) now apply the identical detune/playbackRate-pitch + shot-gain-envelope treatment on every trigger. New Remix UI fields (Pitch min/max, Volume min/max, Fade in/out) in the schedule section, threaded through `snapshotOf`'s explicit field list from the start this time. **Also updated the Export plugin's `simulateScheduledEvents`** (a real missed-duplication-site risk caught proactively during this same change, not after shipping) - it previously hardcoded neutral pitch/volume/fade for every scheduled event, which would have silently ignored the new randomization in exported files; now rolls the same `randomPitchSemitones`/`randomVolumeScale` and reads the real `fadeInMs`/`fadeOutMs`/computed shot duration, matching how it already simulates scatter events. **Verified via CDP against the real dev app**: configured a scheduled sound with a real pitch/volume/fade range, fired it via the Mixer's test-fire button (confirmed already wired for scheduled sounds from `v0.1.75`), and read the live `shotGainNode.gain.value` directly - landed at 0.656, correctly inside the configured 0.5-1.0 range and past the 200ms fade-in's settling point.

### The Composite plugin (`plugins/composite/`)

**Composite multi-sound "effect" groups** (e.g. a door: knob turn + creak + bell) - the item that had been gated on the owner confirming a design direction, resolved via a live conversation right after the Scheduled-randomization fix shipped. The owner's own framing superseded Claude's earlier Tags-based recommendation entirely: pick multiple existing sounds, arrange them with their own relative delay, and **bake** them into one new real audio file ("it is in fact a new audio file... so the existing infrastructure is still valid for it") - not a live multi-source playback rig. The result is created via the exact same `library.addSound` every plain import already goes through, so it's a completely normal entry from that point on: Loop/Random Interval/Scheduled, filters, EQ, Export, Save as copy all already work on it with **zero new playback code anywhere else in the app**. A `compositeSource: { members, createdAt }` field marks it purely for display (a gold "Composite" badge on its Mixer row, `SoundRow.js`) and so the Composite tab can find and re-edit it later - it plays no role in playback/eligibility/staleness at all.

**Rendering** (`src/main/ffmpeg/composite.js`): reuses `loopClip.js`'s `renderClipToPath` (built for the Export plugin) to bake each member's own [loopStart,loopEnd] with its own real filters/speedPitch (crossfade forced to 0, same one-shot reasoning Scatter/Scheduled/Doppler already use) into a temp clip, then combines with plain `adelay`+`amix` - a handful of genuinely *different* files, not the same file split N ways like Export's per-shot placement, so no `asplit` needed here. `library.js` gained `markAsComposite`/`updateComposite` for the metadata half; `ipc.js`'s `composite:create`/`composite:rebake` orchestrate resolving member sound IDs to real filter/trim/speedPitch data (mirroring `export:run`'s own id→data boundary) and calling the render.

**Re-editing an existing composite** re-bakes to the *same* file path in place (same id, same `storedFileName`) rather than creating a new entry - resets the same "not yet baked" loop-clip fields a fresh import would have, since the underlying audio content just changed out from under any existing Remix trim.

**Real bug caught during verification, not code review**: the first real bake attempt failed with ffmpeg's "Unable to choose an output format" - traced to the `.tmp`-then-rename atomic-write pattern (borrowed from `loopClip.js`'s own convention) meaning ffmpeg's actual output path ended in `.wav.tmp`, not `.wav` - its format auto-detection reads the *last* extension and found an unrecognized one. Fixed by adding an explicit `-f wav`, which the codebase's other `.tmp`-writing call sites either already had or never needed (writing straight to a real extension with no rename step). **Verified via CDP against the real dev app**: baked two real sounds (one at delay 0, one at delay 1000ms) into a new composite, confirmed the resulting entry has the exact same field shape a plain import produces (`storageMode: 'copied'`, all default playback fields present) plus `compositeSource`; measured the actual baked file's real duration (3.80s, exactly matching `max(3.0, 1.0+2.8)`) and RMS-sampled real audio content at multiple points confirming both members present at their correct offsets (level measurably increasing once the second member's overlap begins); re-opened it in the Composite tab, changed a delay, re-baked, and confirmed the *same* entry (not a duplicate) was updated in place with a new, correctly-changed duration (3.30s).
