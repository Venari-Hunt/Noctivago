Since the above was written: Remix gained Speed/Pitch/Reverse controls (ffmpeg `rubberband`/`areverse`, Speed also live on streamed sounds via `playbackRate`), a two-pass bake ordering fix so those don't reintroduce a loop seam, faster/reversible auto-zoom while dragging a trim handle, and — per explicit owner prioritization over the rest of the backlog — the Loop vs. Random Interval ("scatter") playback mode described above.

**The parametric EQ was substantially deepened after direct research into FL Studio's "Fruity Parametric EQ 2"** (the app's own stated reference, not an assumption — WebSearch + the official Image-Line manual), triggered by the user repeatedly asking "do you actually know how this works?" rather than letting scope drift on assumption. What shipped from that research: **7 bands** (was 6; `defaultEqBands()` in both `library.js` and `plugins/editor/index.js`), each independently one of **8 filter types** via a `type` field (`off/lowpass/highpass/bandpass/notch/lowshelf/highshelf/peaking`, a `<select>` next to the Freq/Gain/Q fields) — Web Audio's native `BiquadFilterNode.type` covers 7 of these directly; `'off'` maps to `'allpass'` at the node level (a true no-op on the amplitude spectrum) via an `eqNodeType(type)` helper duplicated in `SoundSource.js` and `PreviewSource.js`. Baking dispatches per band to the matching real ffmpeg filter (`loopClip.js`'s `buildEqBandFilter`: `lowpass`/`highpass`/`bandpass`/`bandreject`/`bass`/`treble`/`equalizer`, all verified chained together against the real bundled binary first). A **real-time spectrum analyzer** replaced the static band-energy backdrop as the graph's primary visualization: `PreviewSource.js` taps an `AnalyserNode` off `outputGainNode` (the point both crossfade voices combine into), and `EqEditor.js`'s `tickSpectrum()` reads `getByteFrequencyData()` once per frame from the *same* rAF loop that already drives the playhead — drawn as a pink fill (`rgba(247,118,142,...)`, matching the reference) through the graph's own log-frequency mapping. The static backdrop (`bandEnergy.js`) wasn't removed — it's now the fallback shown via `drawBandEnergyBackdrop()` whenever nothing is playing (`clearSpectrum()` on pause/stop). Deliberately *not* cloned, with reasoning tied to Noctívago's own signal architecture rather than just scope-cutting: Mid/Side/L/R monitoring, Linear Phase (FFT) mode, phase rotation display, and the HQ+/HQL/HQE quality tiers all exist to manage phase/latency problems that only arise when a filtered signal is later recombined with a correlated copy of itself (parallel processing, live DAW monitoring) — Noctívago's sounds each play back independently and are never recombined with anything correlated to themselves, so these simply don't apply here. **A/B Compare** was kept in scope (initially miscategorized with the dropped DAW-specific features, then reconsidered) since it's generic workflow utility, not mixing-console-specific: two buttons (`editor-eq-compare-a`/`-b`) next to Reset EQ snapshot the live 7-band config into an in-memory slot (`this.eqCompare.slots.A`/`.B`, `switchEqCompareSlot()`) and toggle between them — the first switch into an untouched slot seeds it as a copy of the current bands (so it doesn't jar into something different), each slot then diverges independently as the user edits. Per-editing-session only (reset on every `loadSound()`, not persisted) — a comparison aid, not a saved setting. Also shipped in this stretch: **double-click a node to reset just that band** to its own default (`EqEditor.js`'s `onDoubleClick`, mirrors the app-wide slider-reset convention for these canvas-drawn nodes it can't otherwise reach), **Alt+click as a faster alternative to double-click for the same reset** (checked in `pointerDown` before starting a drag, fires the identical `onDoubleClick` callback since both are just different triggers for the same reset action), **Ctrl+click fine-tune drag** (holding Ctrl while dragging a node shrinks mouse movement into parameter movement by `FINE_TUNE_SCALE` (0.2), applied to the per-frame delta rather than re-deriving an absolute position from the cursor every frame — so toggling Ctrl mid-drag never causes a jump, only the scale of movement going forward changes; verified via CDP by comparing the gain delta from an identical raw mouse movement with and without Ctrl held, and by toggling Ctrl mid-drag and confirming a smooth, proportional transition), **per-band Mute/Solo** (two buttons next to the Freq/Gain/Q fields, scoped to the currently-selected band like those fields already are. Mute is a real, persisted `band.muted` boolean — non-destructive on purpose, unlike switching a band's `type` to `'off'`, it never touches freq/gain/Q/type, so re-enabling a band restores exactly what it was tuned to; `eqNodeType(band)` in both `SoundSource.js` and `PreviewSource.js` now takes the whole band object and bypasses to `'allpass'` on `band.muted || band.type === 'off'`, and `loopClip.js`'s `buildEqBandFilter` skips a muted band entirely from the baked ffmpeg chain. Solo is the opposite: preview-only, per-editing-session state that lives on the `EqEditor.js` controller (`soloIndex`, reset on every `load()`) and is deliberately never part of the saved `filters.eq` — `index.js`'s `previewFilters()` builds an audition-only copy of the current filters (every band except the soloed one forced to `muted: true`, the soloed band force-unmuted so soloing overrides its own real mute) and that's what actually gets sent to `previewSource.setFilters()`, while `currentFilters()` — the real, saved state — stays untouched; bypassed nodes also render dimmed on the EQ graph itself so it's obvious at a glance which bands are actually contributing. Verified via CDP: toggling Mute correctly flagged the sound as having unsaved changes and bypassed the live `BiquadFilterNode` to `allpass`; toggling Solo did neither of the first two (no dirty flag, since it's not part of what saves) but did correctly bypass every *other* band's live node while leaving a separately-muted band's real `.muted` flag untouched underneath), and the **dev-only window-positioning fix** — `src/main/index.js`'s `devWindowPosition()` now computes the target display's centered coordinates *before* `BrowserWindow` construction (passed straight into the constructor) instead of moving the window after launch, eliminating a visible flash on the primary display that a post-hoc move couldn't avoid.

**The Mixer's sound list auto-groups currently-playing sounds to the top, loudest first** (`src/renderer/ui/SoundList.js`'s `splitNowPlaying`) — restores behavior the owner wanted back ("what's actually making noise right now" at a glance), framed as an automatic group rather than a manual toggle so there's nothing to remember to turn on. Only kicks in with no explicit `groupMode` chosen (defers to an explicit alphabetical/date/tags grouping exactly like drag-reorder already does) and only when something's actually playing — an idle mixer, or one with an explicit group mode selected, renders exactly as before. "Loudest" is each sound's own per-sound volume (`state.volumes`, 0-1) — global/master volume applies uniformly so it can't affect *relative* loudness ranking. Ties fall back to whatever order the chosen `sortMode` already produced (name/date/custom), since `Array.prototype.sort` is stable. Drag-reorder (`custom` sort mode) is disabled while this auto-split is active, same reasoning as the existing grouped-mode guard: a row could land in a different section on the very next render (e.g. it stops playing), which would make "which row did you actually drag" ambiguous.

**BUG FIX: the Remix EQ's live spectrum analyzer shrank/faded whenever the preview volume slider was turned down**, reported directly by the user ("it's just a control of volume for the tab and shouldn't tamper with tools for editing the audio") — correct: `PreviewSource.js`'s `analyserNode` used to tap `outputGainNode` directly, which carries both the preview volume slider's own level *and* the play/pause fade-in/out ramp (both animate `outputGainNode.gain`), so the spectrum display was reflecting listening level, not the actual filtered signal. Fixed by adding a second, parallel connection from both crossfade voices into a dedicated `analyserFeedNode` (a plain `GainNode` fixed at `1`, never touched by `setVolume`/`play`/`pause`) and tapping the analyser from that instead — still correctly reflects whichever voice is audible (crossfade state) and any EQ/filter changes (both happen upstream, in each voice's own filter chain), just decoupled from the volume slider. Verified via CDP: sampled the analyser's real `getByteFrequencyData()` output at full preview volume, then again after dropping `setVolume(0.05)` (confirmed via `outputGainNode.gain.value` reading `0.05`) — the analyser's byte-sum stayed within normal frame-to-frame variance (806 → 893) instead of collapsing proportionally the way it did with the old tap.

**A sound name truncated by window width now marquee-scrolls on hover** (`SoundRow.js`'s `wireMarquee`) to reveal the full text — `.sound-row-name` is already `white-space:nowrap` + `overflow:hidden` + `text-overflow:ellipsis`, so `scrollWidth > clientWidth` is exactly "this name is truncated," nothing extra to check. Verified via CDP: renamed a test sound to a name overflowing its row, confirmed real `scrollWidth`/`clientWidth` measurements agreed there was truncation, dispatched a synthetic `mouseenter` and confirmed the class/custom-properties applied and a mid-animation screenshot showed the text genuinely scrolled off to one side; confirmed a short, non-truncated name's `mouseenter` never adds the class at all (an exact `scrollWidth === clientWidth` no-op); confirmed `mouseleave` fully resets `transform` to `none`.

**App-wide number-box stepper** (`src/renderer/core/numberBoxStepper.js`, installed once in `main.js` alongside `sliderReset.js`, same delegated-listener pattern — any current or future `<input type="number">`, core or any plugin's, gets it for free): hover a number field and scroll, or use Arrow Up/Down while it's focused, to step its value — plain ±1, Ctrl ±0.1 (finer), Shift jumps to the next/previous multiple of 10, Alt to the next/previous multiple of 100 (exact rules given directly by the user, with worked examples: 3 + Shift → 10, 13 + Alt → 100). Verified via CDP against the real EQ Freq/Gain/Q fields: every modifier combination (plain/Ctrl/Shift/Alt, both directions) for both wheel and arrow-key input produced the exact expected value, including the user's own two worked examples; confirmed a value clamps correctly against a field's real `min`/`max` (Alt from 13 on Gain, whose max is 24, landed at 24, not the unclamped 100); confirmed a wheel event dispatched at an *unfocused* input while a different one has focus is a complete no-op (value unchanged, `preventDefault()` never called) — proving normal page/panel scrolling stays untouched.

**BUG FIX: adjusting the EQ's Freq/Gain/Q number fields via hover+scroll or arrow keys silently did nothing** — reported directly ("raising the frequency by the number doesn't change the node's position and doesn't affect the audio"). Root cause: a real regression from this session's own app-wide number-box stepper (`numberBoxStepper.js`, `v0.1.53`), which dispatches a synthetic `'input'` event on scroll/arrow-key adjustment - but the EQ's Freq/Gain/Q fields were the one place in the whole app still wired to `'change'` (fires only on blur/Enter) instead of `'input'` (fires live, matching every other numeric field: Scatter gap min/max, the core filter sliders). The stepper's `'input'` dispatch simply never reached `applyEqFieldsToSelectedBand()`, so scroll/arrow-key edits updated the field's own displayed value but never touched the actual band, the node's position on the graph, or the live audio. Fixed by switching `eqFreq`/`eqGain`/`eqQ` to `'input'` listeners (the Type `<select>` correctly stays on `'change'`, the only sensible event for a dropdown). Verified via CDP: dispatched a synthetic `input` event on the Freq field (matching the stepper's real trigger), confirmed the band data, the graph controller's own state, and the live `BiquadFilterNode.frequency` (after letting its `setTargetAtTime` smoothing ramp settle) all agreed at the new value; separately confirmed manual typing + blur still works correctly, ruling out a regression from the fix itself.

**The parametric EQ was reworked from a fixed 7-band set into a fully user-managed, dynamic node system** — reversing an earlier deliberate scope cut, after direct feedback that the fixed set felt "too crowded" ("It should be blank with nodes and you would click a + button to add a node and a trash can button to delete a selected node/drag the node into the trash can button to delete it too. This should take precedence over anything"). `defaultEqBands()` (in both `library.js` and `plugins/editor/index.js`) now returns `[]` — a fresh or reset EQ starts genuinely blank, with a "Click + to add a band" hint drawn directly on the canvas. `EqEditor.js` gained `addBand()` (pushes a neutral peaking band at 1000Hz, selects it) and `removeSelectedBand()` (deletes whichever band is selected — the one shared path for both the trash button's click and dragging a node onto it, hit-tested via a registered `setTrashDropTarget(el)` element in `pointerUp`), plus careful `soloIndex` bookkeeping across deletion (cleared if the soloed band was removed, decremented if it pointed past the removed index — since `soloIndex` is a raw array index into a now-mutable-length array).

**This forced a real architectural change to the live audio chain**, not just the UI: `PreviewSource.js`'s per-voice `eqNodes` and `SoundSource.js`'s equivalent used to be built *once*, at construction, assuming a fixed band count forever. Both gained a `_rebuildEqChain`/`rebuildEqChain` method that tears down and reconnects the chain (`lowpassNode → eqNodes[0..N] → filterGainNode`, or `lowpassNode → filterGainNode` directly when N=0) whenever `setFilters()` sees the band count actually change — `.disconnect()` with no arguments removes every outgoing connection from a node, so this is safe regardless of the old or new count. An unchanged band count still takes the cheap in-place `setTargetAtTime` path, same as before. Verified via CDP against both audio paths independently: `PreviewSource`'s live voice correctly rebuilt from 3 nodes down to 2 after a drag-to-trash deletion; `SoundSource`'s core Mixer playback correctly rebuilt from 6 real saved bands down to 1, and separately down to 0 (confirmed playback stayed unpaused throughout, matching the always-additive "buffer mode only affects seam smoothness" ethos this app already has for the rest of the filter chain) — and a sound saved with the old 7-band data still loads and plays correctly today, no migration needed (only the *default* changed, not the schema).

**Double-click and Alt+click, previously identical (both fired a full reset), were split apart** after a direct follow-up: "double clicking shouldn't reset the node completely just position. Alt clicking should be the full reset." With no more canonical per-index default to reset *back to* (bands are user-added now), both were redefined: double-click resets just `gainDb` to 0 (the node's vertical "position"); Alt+click is the fuller reset (`gainDb:0, q:1, type:'peaking'`) while still preserving the node's own frequency — its horizontal identity, not something a reset should relocate. Verified via CDP: a distinctive band (freq 3000, gain 10, Q 4, type peaking) double-clicked came back with only gain zeroed, freq/Q/type untouched; the same setup with type `highshelf` Alt+clicked came back fully neutralized except frequency.

**The EQ graph's connecting line is now the real composite frequency-response curve**, not a straight polyline through node points — also requested directly, twice, with a clarifying follow-up ("the line should start at the left edge of the box... and end at the right edge... when the nodes affect it"). Rather than hand-deriving the RBJ cookbook biquad transfer-function math (real risk of a subtle formula bug), `EqEditor.js` creates a real (never-rendered) `BiquadFilterNode` per active band on a dedicated lazy `OfflineAudioContext` and reads its own native `getFrequencyResponse()` — guaranteed to match what the browser's actual audio graph will do, since it *is* the same implementation. Each active band's magnitude response (one sample per horizontal pixel, spanning the full 20Hz–20kHz width) is summed in dB across bands — correct because the real chain connects bands in series, and a series chain's combined transfer function is the product of each stage's own response (log-domain sum). Bypassed bands (muted, or a different band is soloed) and `'off'`-type bands are excluded, matching the same "honest reflection of what's audible" the existing node-dimming already does. **Performance**: computing this on every single `redraw()` call would be wasteful, since `tickSpectrum()` alone already triggers one every animation frame during playback purely to refresh the live spectrum overlay, with the bands themselves usually unchanged frame to frame — the controller caches the last computed curve, keyed on a cheap `JSON.stringify(bands)` fingerprint plus `soloIndex` and canvas width, and only recomputes when that key actually changes. Verified visually via screenshots: a peaking band showed a real bell curve with the correct Q-shaped width; a highpass band showed a genuine rolloff (flat above the cutoff, dropping to the graph's floor below it) — not a straight line to a point.

**A "Current Mix" group now sits between Now Playing and Everything Else** in the Mixer's sound list (`SoundList.js`'s `splitNowPlaying`) — requested directly via the Obsidian inbox: "Now playing > Current Mix > Everything Else." Same activation rule as before (only kicks in with no explicit `groupMode` chosen, and now also activates whenever anything is *included*, not just when something's *playing*, since a fully-paused-but-loaded mix should still show its Current Mix tier). Verified via CDP: included two real sounds (both landed in Now Playing while playing), clicked global pause (both correctly moved to Current Mix, header count dropped to two groups), then re-added one individually (correctly split across all three tiers simultaneously — Now Playing/Current Mix/Everything Else all present and correctly populated in one render).

**Number-field hover+scroll no longer requires a click first** (`numberBoxStepper.js`) — a direct, explicit reversal of the focus-gated design shipped in `v0.1.53`: "Just hovering a text box with a number should be grounds for scrolling with mouse wheel and changing it. ### The Export plugin (`plugins/export/`)

**Bakes a whole preset down to one audio file of a chosen length and format** - explicitly owner-prioritized ahead of everything else in the backlog ("I like this feature more than the others"), jumping past its own already-high ranked score. Started from an owner design question ("what about choosing a length and exporting an audio? is it hard?") that turned into the owner proposing the actual architecture themselves, live: "use the data inputted on the preset as grounds for a 'simulation'... run a 'simulation' of the events that will transpire within this [duration]... use the simulation output to create a single ffmpeg command." Confirmed sound and built essentially as proposed, with one caveat surfaced back and accepted (see below).

**Simulate first, render second.** `plugins/export/simulate.js` reuses the *exact* randomization/scheduling functions each playMode's real playback source already uses - `randomGapSeconds`/`randomPitchSemitones`/`randomVolumeScale` (mirroring `ScatterSoundSource.js`) rolled repeatedly until cumulative time exceeds the chosen export duration produces a scatter sound's shot list; `secondsUntilNextTrigger` (mirroring `ScheduledSoundSource.js`) rolled the same way produces a scheduled sound's trigger list. This is a dry run of the exact same process a live source uses to schedule its next event, just without any actual audio scheduling - zero new randomization logic, all duplicated per the plugin's own established "bundle your own dependencies" convention (a plugin can't import outside its own directory). **`simulateEvents({ entry, durationSeconds, now })` is the extensibility contract the owner explicitly asked for** ("it needs to work not only with what already exists but the features that will be added too"): dispatches by `playMode` to a per-mode simulator, so a future playMode only needs to add a case here (or, if the list grows, a lookup table) rather than the export pipeline hardcoding scatter/scheduled-specific logic inline. `'loop'` mode returns `null` deliberately - a looped sound has no discrete events, it just tiles.

**A `'times'`-type scheduled sound (real daily HH:MM triggers) is handled exactly per the owner's own explicit instruction**: "treat it as a sound with timed intervals. If the event of it playing falls out of the time scope just exclude it from the export." The simulator starts from the real current wall-clock time and rolls `secondsUntilNextTrigger` forward, including whatever real trigger moments happen to land within the export window and naturally excluding (not specially handling - the loop already stops the instant an offset would exceed the duration) any that wouldn't recur until after it ends. This means running the same export at different times of day can produce a different number of `'times'`-triggered events - an accepted, explicitly-instructed trade-off, not an oversight.

**Rendering (`src/main/ffmpeg/exportMix.js`), the one place the owner's "single ffmpeg command" framing needed a caveat** - surfaced directly and accepted before building: placing hundreds of shots (a scatter sound firing every ~30s across a multi-hour export easily reaches 500+) each with their own delay/pitch/volume in one giant `adelay`+`amix`+per-shot-`rubberband` graph would risk Windows command-line length limits and unwieldy filter-graph parsing. Practical shape instead: one ffmpeg pass **per included sound** - a `'loop'` sound bakes one crossfaded iteration (reusing `loopClip.js`'s existing bake logic completely unchanged, via a new `renderClipToPath` export that takes an explicit output path instead of the sound's own id-keyed managed clip slot, so export renders never disturb a sound's real cached buffer-mode clip) and tiles it via ffmpeg's own `-stream_loop`; a `'scatter'`/`'scheduled'` sound bakes one one-shot "shot" clip (crossfade forced to 0, matching `effectiveCrossfadeSeconds`'s existing reasoning) then places a copy at each simulated event's own offset via `asplit` (splitting the single input into N identical branches inside the filter graph, rather than opening the same short file hundreds of times) + per-branch `rubberband`+`volume`+`afade`+`adelay` + a final `amix`. **The graph is written to a script file and referenced via `-filter_complex_script`** rather than inlined on the command line, specifically so a dense export can't hit a command-line length limit regardless of shot count. Every per-sound track renders to the *exact* export duration (`apad=whole_dur=`); the final mixdown just `amix`es those together, then applies the **whole-mix EQ/gain and fade in/out last** - the owner's own explicit ordering ("should be applied on the whole mix after everything") - before encoding to the chosen format (wav/mp3/opus/flac/ogg).

**Verified directly against the real bundled ffmpeg binary before any of this was wired into the app**, per the project's own established discipline: a synthetic spike test placing 40 then 150 pitch/volume-varied one-shot clips via `asplit`+`adelay`+`amix` first caught a real bug in the *test methodology itself* (`amix`'s default `duration=first` stopped the output at the first branch's own short length, not the intended target - fixed with `duration=longest`+`apad`) before confirming the technique renders correctly and fast (150 shots across 5 minutes in ~4s, ~77x realtime). **Verified end-to-end against the real dev app**: a genuine 3-sound preset (one of each playMode - loop/scatter/scheduled) exported to a real 90-second file in ~1.8s; the output's actual measured duration was exactly 90.00s; RMS-sampling the real decoded audio across the whole file confirmed continuous non-silent content from all three sources, and precise sampling at the very start/end confirmed the fade-in/fade-out ramps land exactly where expected (near-silent at the true start/end, full level by ~1s in); a separate MP3-format export was independently verified to produce a valid, correctly-durationed MP3 stream. New UI: its own tab (not just a Presets-modal button, per the owner's explicit "I think this should be a new plugin... a new tab is the best approach") with preset/length/format pickers, a whole-mix Highpass/Lowpass/Gain+fade section (deliberately a simpler 3-control set for v1, not the full 7-band parametric EQ the per-sound Remix editor has - noted directly as a scope call, not silently reduced), and an Export button that opens a native save-location picker before running.

**Scheduled playback gained the exact same pitch/volume randomization and fade in/out controls Random Interval already has** - direct owner request, flagged explicit priority ("this takes precedence over anything"), reversing `v0.1.77`'s original deliberate scope cut (its own doc comment used to say "no pitch/volume randomization or fade envelope, since the whole point here is a *deterministic* cue at a known time"). Only the *timing* stays deterministic clock math; each trigger's own character is now randomized identically to a scatter shot. Implemented by exporting `randomPitchSemitones`/`randomVolumeScale`/`fadeSeconds`/`scheduleShotEnvelope` from `ScatterSoundSource.js` and importing them into `ScheduledSoundSource.js` (same directory, no cross-plugin restriction, so no third copy needed) - both `BufferScheduledSource` (gained a per-shot `shotGain` node, mirroring `BufferScatterSource`) and `StreamScheduledSource` (gained a persistent `shotGainNode` spliced into its filter chain) now apply the identical detune/playbackRate-pitch + shot-gain-envelope treatment on every trigger. **"Suggest a loop point" — automatic loop-region detection in Remix (v0.1.94)** — picked via the ranking system (7.33, but the one tied-lowest item that was fully de-risked: research already done, concrete design ready). `src/main/ffmpeg/loopSuggest.js`: `suggestLoopPoints(inputPath, durationSeconds, options)` → `{ ok, wholeFile, loopStart, loopEnd }`. **Analysis-only** — it just populates the Start/End fields (through the exact same path a manual edit takes, so Save + undo pick it up); it never bakes or renders anything, the existing crossfade-rotation bake (`loopClip.js`) still does the actual seam-smoothing on whatever region gets saved. **Why it doesn't reuse PyMusicLooper/LoopAuditioneer's approach**: those target *musical* content and lean on beat/pitch periodicity; Noctívago's sounds (rain/wind/forest/crowd) are non-tonal textures with no periodic structure to phase-align, so the perceptually relevant cue at a loop seam is *energy-envelope continuity*, not sample phase. So this works on a cheap per-frame energy envelope — full-band RMS + a low/high split from a one-pole 500Hz filter, computed as it streams (flat memory regardless of file length, same reason `waveformPeaks.js` reduces to peaks instead of buffering). **Search**: one ffmpeg decode to 22050 mono → 20ms-frame envelope, normalized per-feature by its own median (scale-invariant across files, still preserves *within*-file level jumps as a real cost). Two-stage: a coarse pass over an envelope downsampled to ~2000 frames (cost bounded no matter the length; adaptive stride if the loop-length range × frame count would exceed ~800K candidate pairs), then a full-resolution refine within a window of the coarse winner (capped at 250 frames / 5s so a multi-hour file's wide coarse cell can't blow up stage 2 — past a few seconds of precision the difference isn't audible for looping ambience anyway). Seam score = triangular-weighted sum of per-frame `|Δfull| + |Δlow| + |Δhigh|` over a ±0.5s window around each candidate seam, minus a mild length bonus (`LENGTH_WEIGHT = 0.02`) so a longer region is preferred when the seam matches equally well (more material = less obviously repetitive) — but only mildly, never enough to pick a much worse seam for length. Loop-length constrained to `[12s, 75s]` (both clamped to the file); files ≤5s return `wholeFile: true`. New `audio:suggestLoopPoints` IPC + `api.audio.suggestLoopPoints`, called from a new "Suggest a loop point" button in the Remix `.editor-times` area (with an inline status line: "Analyzing…" → "Suggested 0:17 loop — adjust if needed, then Save."). **Verified via CDP against the real dev app** with synthetic test files built to exercise each behavior: a 40s stationary-texture file → a near-max-length loop (correct — stationary content loops fine anywhere, longer is less repetitive); a 50s wind bed with a loud 2s gust at t=32 → seam correctly *avoids* landing on the gust (it plays once per loop cycle); a 40s file that's calm for 20s then agitated → loop region stays entirely within the calm half, not straddling the loudness jump (the key discriminating case, confirmed both in the returned numbers and visually in a screenshot of the waveform's loop overlay); a 12-minute file → 630ms total, bounded. Full UI flow verified: button disables + "Analyzing…" during, Start/End/Length update, Save enables, undo history commits, and a real Save after suggesting bakes the suggested region correctly (`loopClipReady`, clip points match). **Un-feel-tested tunables flagged to the owner**: `LENGTH_WEIGHT` (0.02) and the `[12s, 75s]` preferred-length range — a `## Questions` inbox note asks whether the suggested loops feel right.

**Seamless looping for long stream-mode sounds (v0.1.101)** — the ranked backlog's "hybrid bridge-clip seamless loop" item. **Time-preserving per-shot pitch for Random Interval / Scheduled (v0.1.111)** — the Board `#next`, from the owner's v0.1.102 Question answer: "i would prefer if the sounds kept the length i set it to. If it's getting faster or slower on pitch changes it should be fixed... both on the mixer tab and on exports. Unless it would be the most resource draining thing ever." Before this, a scatter/scheduled shot's random pitch was applied by `AudioBufferSourceNode.detune` alone, which the Web Audio spec folds into `computedPlaybackRate` — so a pitched-up shot genuinely played *faster and shorter*. New `src/renderer/audio/pitchStretch.js`: a self-contained **WSOLA** (waveform-similarity overlap-add) time-stretch — overlapping input frames placed at a scaled synthesis hop, each nudged within ±256 samples to the offset that best cross-correlates with the previous frame's natural continuation (biased toward the natural hop by `0.05·|delta|/radius` so a pure tone, the pathological many-equal-matches case, doesn't drift into a pitch change). 50% Hann overlap ⇒ exact constant-overlap-add ⇒ amplitude preserved with zero normalization and no edge blow-up. Chosen over a phase vocoder: no FFT (a hand-rolled one hit real amplitude/edge bugs first), holds up on the broadband/noisy textures this app mostly plays, and cheap — coarse-step-4 search + fine refine + a 256-sample correlation window ⇒ ~30 ms for a 2 s stereo clip, ~55 ms for 4 s (off the audio thread, on the shot-scheduling `setTimeout`). `pitchShiftBuffer(context, buffer, semitones)` stretches the clip by the pitch ratio; the caller still sets `detune` to that ratio, so playback resamples the stretched clip back to the original length while shifting pitch — net: pitch moves, duration doesn't. Returns the buffer unchanged for a sub-`IDENTITY_PITCH_EPSILON_SEMITONES` (0.02) shift, and **null** past `MAX_STRETCH_SECONDS` (12 s) so the caller falls back to the old resample-coupled behavior for an unusually long shot clip. Wired into `BufferScatterSource._playOneShot` and `BufferScheduledSource._playOneShot` (both: `node.buffer = shifted ?? this.audioBuffer`, and `durationSeconds` = nominal when stretched, pitch-adjusted when it fell back — the fade-out envelope needs the real end). **Stream mode is the one place per-shot pitch still couples to length** — `StreamScatterSource`/`StreamScheduledSource` have no in-memory samples to pre-stretch and only ever run for a scatter/scheduled trim too long to ever bake (unusual for an event sound); left as a documented accepted limitation, same as Speed elsewhere. **Export** (`plugins/export/simulate.js`): dropped the `/effectiveRate` divisions on `shotDurationSeconds` in both `simulateScatterEvents` and `simulateScheduledEvents` — exports already pitch shots with `rubberband` (duration-preserving), so the shot length is just `loopEnd − loopStart` now, which fixes the v0.1.102-flagged bug where the fade-out landed early and batch spans (`planBatches`) were planned short. `exportMix.js` itself unchanged (it was already duration-correct, just fed wrong metadata). Live (WSOLA) and export (rubberband) now agree on the property that matters — length + pitch — though timbre differs slightly between the two algorithms (acceptable, and far better than differing durations). Static Remix Pitch (loop mode) was already fine: it bakes into the clip via rubberband, duration-neutral. Doppler untouched (its own contour, out of scope). **Verified**: a Node harness on `timeStretch`/`pitchShiftBuffer` (31 assertions — length scales exactly, pitch held on tones, amplitude preserved on tones + noise, transient survives and stays in place, wrapper thresholds/fallback); CDP against the real dev app (temp `NOCTIVAGO_CDP` switch, removed) — imported both source classes and drove `_playOneShot` at ±semitones: the buffer swaps to a pre-stretched one, real playback length stays nominal (2.5 s → 2.5 s at +4/−5/+7 st), an `OfflineAudioContext` render confirmed the frequency actually shifts (−7 st → 200 Hz, +12 st → 600 Hz), the >12 s buffer returns null; 3 real scatter shots via the Mixer's test-fire button with a −4..+6 st range, no console errors; `npm run build` clean.

**Small fixes from a self-review pass (v0.1.112)** — no inbox items and the Board had no autonomously-pickable `#next` after v0.1.111, so a read-only `/code-review` of the v0.1.103–111 diffs stood in for a task (same as v0.1.102). Six findings; the four safe ones shipped here, the other two flagged. Shipped:
- **`pitchStretch.js` amplitude spike near the end of a pitched shot.** The WSOLA render marked a frame as "last" (→ its trailing half written at unity gain instead of the Hann taper, to not fade a decaying tail) using a *prediction* from the worst-case search offset — but the loop often placed one more frame overlapping it, stacking unity + a rising taper ≈ +6 dB ~10 ms before the shot's nominal end. Default `fadeOutMs` is 0, so nothing masked it: an audible click/level jump on a large fraction of pitched one-shots. Fixed by splitting `timeStretch` into `planStretch` (builds the whole frame-offset list) + `renderStretch` (overlap-adds) — the genuine last frame is now known exactly (`k === frameStarts.length - 1`), so unity-trailing-half applies only where nothing follows.
- **`pitchStretch.js` stereo decorrelation.** `pitchShiftBuffer` ran `timeStretch` per channel, each doing its own similarity search → L and R picking different frame offsets → inter-channel phase differences that weren't in the source (stereo smear / comb filtering summed to mono). Now `planStretch` runs once on a mono downmix and every channel renders against that shared plan.

Live playback's own copy isn't a hang (a `setTimeout(0)` between `onended`s → back-to-back shots) so it's left alone — noted in inbox Questions.
- **`ipc.js` `audio:getWaveformPeaks` persisting a bogus 0 duration.** `probeDurationSeconds` returns `0` (not `null`) if ffmpeg decodes no samples; the `!= null` guard passed that through to `library.updateMeta`, permanently suppressing the Mixer's own null-guarded re-probe and feeding 0 into loop-clip eligibility. Now guards on `> 0`, matching `library.js`'s eager-bake `<= 0` check.
- **Composite tab re-extracting every clip waveform on every window resize and on unrelated app-wide library mutations** (each `getWaveformPeaks` is a fresh ffmpeg spawn, no cache). Now: the `library.onChanged` handler and the `resize` handler both no-op unless the tab is actually visible (new `this.shown` flag via `onShow`/`onHide`; `onShow` catches up); `resize` is debounced 120 ms; and a per-`(soundId, width, in, out)` peaks cache (cleared on `refresh()`) means repeated identical renders (selection, resize back) don't re-spawn ffmpeg.

### The Preset Remix plugin (`plugins/preset-remix/`, tab titled "Preset Remix")

**Whole-mix processing saved on a preset and heard live whenever that preset is loaded** — the long-standing `#future` "Preset Remix / whole-mix editing tab" item, built after the owner picked its shape from a two-question fork: processing set = "HP/LP/Gain now, EQ same session" (both shipped here in one release), and when-applied = "per-preset, applied on load" (not an always-on master bus). It's the *live-playback* counterpart of the Export plugin's "Whole-mix processing" section — Export bakes HP/LP/Gain+fade into a file; this applies HP/LP/Gain+fade-in **+ a parametric EQ** to everything playing.

**Data model**: a new `wholeMix` field on a preset (`presets.js`), `{ highpassHz, lowpassHz, gainDb, fadeInSeconds, eq: [...] }` or `null` when fully neutral (`normalizeWholeMix` collapses a neutral config to `null` so the "does this preset have whole-mix settings" check stays a truthiness test). `eq` is a variable-length band array in the *exact* same shape as a sound's own `filters.eq` (`{ freqHz, gainDb, q, type, slope, muted }`). New `presets.updatePresetWholeMix(id, wholeMix)` + `presets:updateWholeMix` IPC + `api.presets.updateWholeMix` preload. The portable preset export (`presetPortable.js`) does **not** carry `wholeMix` yet — deferred, noted in the inbox.

**Live chain** (`src/renderer/audio/WholeMixChain.js`): a master chain `masterGain → input → highpass → lowpass → [eq bands…] → gain → fadeGain → destination`, owned by `AudioEngine` (`engine.wholeMix`), sitting between `masterGain` (the global volume slider) and `context.destination`. The one structural change to `AudioEngine` is `masterGain.connect(this.wholeMix.input)` instead of `masterGain.connect(destination)`. The EQ sub-chain is built by the *same* `eqNodeType` / `eqBandStageCount` helpers a sound's own chain uses — now `export`ed from `SoundSource.js` (core-to-core, unlike the plugin-side duplicates) — with the identical "rebuild only when the per-band topology fingerprint changes, in-place param updates otherwise" logic copied from `SoundSource.setFilters`. `fadeGain` handles the on-load fade-in (kept separate from the user's `gain` dB node so a fade never fights a gain change). Neutral by default: nodes exist but pass audio through, `set(null)` resets them.

**How it takes effect**: `tabs/mixer/index.js`'s `loadPreset` sets `state.activePresetId = preset.id` and calls `engine.wholeMix.set(preset.wholeMix ?? null, { fadeInSeconds })` — the fade-in only ever runs on an actual load. Loading another preset swaps the chain (or resets it to neutral). `state.activePresetId` is *not* cleared when the user then deviates from the preset by hand — it just tracks "what did we last load."

**Live preview** across the plugin/core boundary: the plugin only has the curated `window.noctivago` IPC surface, no line to the engine — so it dispatches a `noctivago:whole-mix-preview` window `CustomEvent` `{ presetId, wholeMix }` on every control/EQ change (and once more with the *saved* values on `onHide`, reverting any unsaved preview). The Mixer listens and applies it **only if `e.detail.presetId === state.activePresetId`** — editing preset A while preset B is the live mix changes nothing audible. Same window-CustomEvent bridge the Solo button (`noctivago:solo`) and sleep timer (`noctivago:stop-all-playback`) already use.

**The plugin UI** (`plugins/preset-remix/index.js` + `ui/EqEditor.js`): a preset `<select>`, HP/LP/Gain sliders + a fade-in field (mirroring the Export tab's controls), then a scoped-down draggable-node EQ canvas — `WholeMixEqEditor`, a fresh ~280-line editor, *not* a copy of the core Remix `EqEditor` (which is 800+ lines of spectrum analyzer / A-B / mute-solo / cut-overlay that don't apply to a whole mix with no single preview source). Kept: draggable nodes, the real composite response curve (`OfflineAudioContext` `BiquadFilterNode.getFrequencyResponse` summed in dB, same technique as core), click-empty-to-add, wheel-for-Q, right-click-to-remove, double-click-to-flatten, per-band Freq/Gain/Q precision fields + a type `<select>`. No slope UI (bands are always `gentle`). Save via `api.presets.updateWholeMix`; a `canonicalMix()` order-insensitive compare drives the dirty check (the editor and the store build band objects with different key orders). `plugins/preset-remix/` uses only `app.noctivago` + its own tiny EQ math — no copies of `AudioEngine.js` etc. needed.

**Verified via CDP against the real dev app** (temp `NOCTIVAGO_CDP` remote-debugging switch in `main/index.js` + a temp `window.__mixerDebug` engine hook, both removed after; note: plugin JS is served by the `plugin://` protocol which HTTP-caches, so a `Page.reload({ignoreCache:true})` is needed after editing a plugin file): saved HP 500 / Gain −6 / fade 3 on a preset → `presets.list()` shows the normalized `wholeMix`; loading that preset in the Mixer built `engine.wholeMix` with `highpass.frequency` 500, `gain` −6 dB, `fadeGain` mid-ramp at 0.2; a live edit while that preset was active moved the engine's `lowpass` to ~4000; leaving the tab unsaved reverted it to 20000; editing a *different* preset left the active chain untouched; loading a no-`wholeMix` preset reset the chain to neutral (`config: null`). EQ: click-to-add populated the precision fields (112 Hz / +7.2 dB / peaking), wheel changed Q 1→1.08, the type `<select>` set `highshelf`, Save persisted both bands, right-click removed one and Save persisted the remainder; loading the preset built the matching `eqNodeGroups` (topology `"1"`, highshelf node @ 2518 Hz / −7.2 dB), a live-preview add rebuilt to topology `"1,1"`, leaving unsaved reverted to `"1"`.
