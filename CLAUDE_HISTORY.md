Since the above was written: Remix gained Speed/Pitch/Reverse controls (ffmpeg `rubberband`/`areverse`, Speed also live on streamed sounds via `playbackRate`), a two-pass bake ordering fix so those don't reintroduce a loop seam, faster/reversible auto-zoom while dragging a trim handle, and — per explicit owner prioritization over the rest of the backlog — the Loop vs. Random Interval ("scatter") playback mode described above.

**The parametric EQ was substantially deepened after direct research into FL Studio's "Fruity Parametric EQ 2"** (the app's own stated reference, not an assumption — WebSearch + the official Image-Line manual), triggered by the user repeatedly asking "do you actually know how this works?" rather than letting scope drift on assumption. What shipped from that research: **7 bands** (was 6; `defaultEqBands()` in both `library.js` and `plugins/editor/index.js`), each independently one of **8 filter types** via a `type` field (`off/lowpass/highpass/bandpass/notch/lowshelf/highshelf/peaking`, a `<select>` next to the Freq/Gain/Q fields) — Web Audio's native `BiquadFilterNode.type` covers 7 of these directly; `'off'` maps to `'allpass'` at the node level (a true no-op on the amplitude spectrum) via an `eqNodeType(type)` helper duplicated in `SoundSource.js` and `PreviewSource.js`. Baking dispatches per band to the matching real ffmpeg filter (`loopClip.js`'s `buildEqBandFilter`: `lowpass`/`highpass`/`bandpass`/`bandreject`/`bass`/`treble`/`equalizer`, all verified chained together against the real bundled binary first). A **real-time spectrum analyzer** replaced the static band-energy backdrop as the graph's primary visualization: `PreviewSource.js` taps an `AnalyserNode` off `outputGainNode` (the point both crossfade voices combine into), and `EqEditor.js`'s `tickSpectrum()` reads `getByteFrequencyData()` once per frame from the *same* rAF loop that already drives the playhead — drawn as a pink fill (`rgba(247,118,142,...)`, matching the reference) through the graph's own log-frequency mapping. The static backdrop (`bandEnergy.js`) wasn't removed — it's now the fallback shown via `drawBandEnergyBackdrop()` whenever nothing is playing (`clearSpectrum()` on pause/stop). Deliberately *not* cloned, with reasoning tied to Noctívago's own signal architecture rather than just scope-cutting: Mid/Side/L/R monitoring, Linear Phase (FFT) mode, phase rotation display, and the HQ+/HQL/HQE quality tiers all exist to manage phase/latency problems that only arise when a filtered signal is later recombined with a correlated copy of itself (parallel processing, live DAW monitoring) — Noctívago's sounds each play back independently and are never recombined with anything correlated to themselves, so these simply don't apply here. **A/B Compare** was kept in scope (initially miscategorized with the dropped DAW-specific features, then reconsidered) since it's generic workflow utility, not mixing-console-specific: two buttons (`editor-eq-compare-a`/`-b`) next to Reset EQ snapshot the live 7-band config into an in-memory slot (`this.eqCompare.slots.A`/`.B`, `switchEqCompareSlot()`) and toggle between them — the first switch into an untouched slot seeds it as a copy of the current bands (so it doesn't jar into something different), each slot then diverges independently as the user edits. Per-editing-session only (reset on every `loadSound()`, not persisted) — a comparison aid, not a saved setting. Also shipped in this stretch: **double-click a node to reset just that band** to its own default (`EqEditor.js`'s `onDoubleClick`, mirrors the app-wide slider-reset convention for these canvas-drawn nodes it can't otherwise reach), **Alt+click as a faster alternative to double-click for the same reset** (checked in `pointerDown` before starting a drag, fires the identical `onDoubleClick` callback since both are just different triggers for the same reset action), **Ctrl+click fine-tune drag** (holding Ctrl while dragging a node shrinks mouse movement into parameter movement by `FINE_TUNE_SCALE` (0.2), applied to the per-frame delta rather than re-deriving an absolute position from the cursor every frame — so toggling Ctrl mid-drag never causes a jump, only the scale of movement going forward changes; verified via CDP by comparing the gain delta from an identical raw mouse movement with and without Ctrl held, and by toggling Ctrl mid-drag and confirming a smooth, proportional transition), **per-band Mute/Solo** (two buttons next to the Freq/Gain/Q fields, scoped to the currently-selected band like those fields already are. Mute is a real, persisted `band.muted` boolean — non-destructive on purpose, unlike switching a band's `type` to `'off'`, it never touches freq/gain/Q/type, so re-enabling a band restores exactly what it was tuned to; `eqNodeType(band)` in both `SoundSource.js` and `PreviewSource.js` now takes the whole band object and bypasses to `'allpass'` on `band.muted || band.type === 'off'`, and `loopClip.js`'s `buildEqBandFilter` skips a muted band entirely from the baked ffmpeg chain. Solo is the opposite: preview-only, per-editing-session state that lives on the `EqEditor.js` controller (`soloIndex`, reset on every `load()`) and is deliberately never part of the saved `filters.eq` — `index.js`'s `previewFilters()` builds an audition-only copy of the current filters (every band except the soloed one forced to `muted: true`, the soloed band force-unmuted so soloing overrides its own real mute) and that's what actually gets sent to `previewSource.setFilters()`, while `currentFilters()` — the real, saved state — stays untouched; bypassed nodes also render dimmed on the EQ graph itself so it's obvious at a glance which bands are actually contributing. Verified via CDP: toggling Mute correctly flagged the sound as having unsaved changes and bypassed the live `BiquadFilterNode` to `allpass`; toggling Solo did neither of the first two (no dirty flag, since it's not part of what saves) but did correctly bypass every *other* band's live node while leaving a separately-muted band's real `.muted` flag untouched underneath), and the **dev-only window-positioning fix** — `src/main/index.js`'s `devWindowPosition()` now computes the target display's centered coordinates *before* `BrowserWindow` construction (passed straight into the constructor) instead of moving the window after launch, eliminating a visible flash on the primary display that a post-hoc move couldn't avoid.

**The Mixer's sound list auto-groups currently-playing sounds to the top, loudest first** (`src/renderer/ui/SoundList.js`'s `splitNowPlaying`) — restores behavior the owner wanted back ("what's actually making noise right now" at a glance), framed as an automatic group rather than a manual toggle so there's nothing to remember to turn on. Only kicks in with no explicit `groupMode` chosen (defers to an explicit alphabetical/date/tags grouping exactly like drag-reorder already does) and only when something's actually playing — an idle mixer, or one with an explicit group mode selected, renders exactly as before. "Loudest" is each sound's own per-sound volume (`state.volumes`, 0-1) — global/master volume applies uniformly so it can't affect *relative* loudness ranking. Ties fall back to whatever order the chosen `sortMode` already produced (name/date/custom), since `Array.prototype.sort` is stable. Drag-reorder (`custom` sort mode) is disabled while this auto-split is active, same reasoning as the existing grouped-mode guard: a row could land in a different section on the very next render (e.g. it stops playing), which would make "which row did you actually drag" ambiguous.

**BUG FIX: the Remix EQ's live spectrum analyzer shrank/faded whenever the preview volume slider was turned down**, reported directly by the user ("it's just a control of volume for the tab and shouldn't tamper with tools for editing the audio") — correct: `PreviewSource.js`'s `analyserNode` used to tap `outputGainNode` directly, which carries both the preview volume slider's own level *and* the play/pause fade-in/out ramp (both animate `outputGainNode.gain`), so the spectrum display was reflecting listening level, not the actual filtered signal. Fixed by adding a second, parallel connection from both crossfade voices into a dedicated `analyserFeedNode` (a plain `GainNode` fixed at `1`, never touched by `setVolume`/`play`/`pause`) and tapping the analyser from that instead — still correctly reflects whichever voice is audible (crossfade state) and any EQ/filter changes (both happen upstream, in each voice's own filter chain), just decoupled from the volume slider. Verified via CDP: sampled the analyser's real `getByteFrequencyData()` output at full preview volume, then again after dropping `setVolume(0.05)` (confirmed via `outputGainNode.gain.value` reading `0.05`) — the analyser's byte-sum stayed within normal frame-to-frame variance (806 → 893) instead of collapsing proportionally the way it did with the old tap.

**App-wide number-box stepper** (`src/renderer/core/numberBoxStepper.js`, installed once in `main.js` alongside `sliderReset.js`, same delegated-listener pattern — any current or future `<input type="number">`, core or any plugin's, gets it for free): hover a number field and scroll, or use Arrow Up/Down while it's focused, to step its value — plain ±1, Ctrl ±0.1 (finer), Shift jumps to the next/previous multiple of 10, Alt to the next/previous multiple of 100 (exact rules given directly by the user, with worked examples: 3 + Shift → 10, 13 + Alt → 100). **BUG FIX: adjusting the EQ's Freq/Gain/Q number fields via hover+scroll or arrow keys silently did nothing** — reported directly ("raising the frequency by the number doesn't change the node's position and doesn't affect the audio"). Root cause: a real regression from this session's own app-wide number-box stepper (`numberBoxStepper.js`, `v0.1.53`), which dispatches a synthetic `'input'` event on scroll/arrow-key adjustment - but the EQ's Freq/Gain/Q fields were the one place in the whole app still wired to `'change'` (fires only on blur/Enter) instead of `'input'` (fires live, matching every other numeric field: Scatter gap min/max, the core filter sliders). The stepper's `'input'` dispatch simply never reached `applyEqFieldsToSelectedBand()`, so scroll/arrow-key edits updated the field's own displayed value but never touched the actual band, the node's position on the graph, or the live audio. Fixed by switching `eqFreq`/`eqGain`/`eqQ` to `'input'` listeners (the Type `<select>` correctly stays on `'change'`, the only sensible event for a dropdown). Verified via CDP: dispatched a synthetic `input` event on the Freq field (matching the stepper's real trigger), confirmed the band data, the graph controller's own state, and the live `BiquadFilterNode.frequency` (after letting its `setTargetAtTime` smoothing ramp settle) all agreed at the new value; separately confirmed manual typing + blur still works correctly, ruling out a regression from the fix itself.

**The parametric EQ was reworked from a fixed 7-band set into a fully user-managed, dynamic node system** — reversing an earlier deliberate scope cut, after direct feedback that the fixed set felt "too crowded" ("It should be blank with nodes and you would click a + button to add a node and a trash can button to delete a selected node/drag the node into the trash can button to delete it too. This should take precedence over anything"). `defaultEqBands()` (in both `library.js` and `plugins/editor/index.js`) now returns `[]` — a fresh or reset EQ starts genuinely blank, with a "Click + to add a band" hint drawn directly on the canvas. `EqEditor.js` gained `addBand()` (pushes a neutral peaking band at 1000Hz, selects it) and `removeSelectedBand()` (deletes whichever band is selected — the one shared path for both the trash button's click and dragging a node onto it, hit-tested via a registered `setTrashDropTarget(el)` element in `pointerUp`), plus careful `soloIndex` bookkeeping across deletion (cleared if the soloed band was removed, decremented if it pointed past the removed index — since `soloIndex` is a raw array index into a now-mutable-length array).

**This forced a real architectural change to the live audio chain**, not just the UI: `PreviewSource.js`'s per-voice `eqNodes` and `SoundSource.js`'s equivalent used to be built *once*, at construction, assuming a fixed band count forever. Both gained a `_rebuildEqChain`/`rebuildEqChain` method that tears down and reconnects the chain (`lowpassNode → eqNodes[0..N] → filterGainNode`, or `lowpassNode → filterGainNode` directly when N=0) whenever `setFilters()` sees the band count actually change — `.disconnect()` with no arguments removes every outgoing connection from a node, so this is safe regardless of the old or new count. An unchanged band count still takes the cheap in-place `setTargetAtTime` path, same as before. Verified via CDP against both audio paths independently: `PreviewSource`'s live voice correctly rebuilt from 3 nodes down to 2 after a drag-to-trash deletion; `SoundSource`'s core Mixer playback correctly rebuilt from 6 real saved bands down to 1, and separately down to 0 (confirmed playback stayed unpaused throughout, matching the always-additive "buffer mode only affects seam smoothness" ethos this app already has for the rest of the filter chain) — and a sound saved with the old 7-band data still loads and plays correctly today, no migration needed (only the *default* changed, not the schema).

**Double-click and Alt+click, previously identical (both fired a full reset), were split apart** after a direct follow-up: "double clicking shouldn't reset the node completely just position. Alt clicking should be the full reset." With no more canonical per-index default to reset *back to* (bands are user-added now), both were redefined: double-click resets just `gainDb` to 0 (the node's vertical "position"); Alt+click is the fuller reset (`gainDb:0, q:1, type:'peaking'`) while still preserving the node's own frequency — its horizontal identity, not something a reset should relocate. Verified via CDP: a distinctive band (freq 3000, gain 10, Q 4, type peaking) double-clicked came back with only gain zeroed, freq/Q/type untouched; the same setup with type `highshelf` Alt+clicked came back fully neutralized except frequency.

**The EQ graph's connecting line is now the real composite frequency-response curve**, not a straight polyline through node points — also requested directly, twice, with a clarifying follow-up ("the line should start at the left edge of the box... and end at the right edge... when the nodes affect it"). Rather than hand-deriving the RBJ cookbook biquad transfer-function math (real risk of a subtle formula bug), `EqEditor.js` creates a real (never-rendered) `BiquadFilterNode` per active band on a dedicated lazy `OfflineAudioContext` and reads its own native `getFrequencyResponse()` — guaranteed to match what the browser's actual audio graph will do, since it *is* the same implementation. Each active band's magnitude response (one sample per horizontal pixel, spanning the full 20Hz–20kHz width) is summed in dB across bands — correct because the real chain connects bands in series, and a series chain's combined transfer function is the product of each stage's own response (log-domain sum). Bypassed bands (muted, or a different band is soloed) and `'off'`-type bands are excluded, matching the same "honest reflection of what's audible" the existing node-dimming already does. **Performance**: computing this on every single `redraw()` call would be wasteful, since `tickSpectrum()` alone already triggers one every animation frame during playback purely to refresh the live spectrum overlay, with the bands themselves usually unchanged frame to frame — the controller caches the last computed curve, keyed on a cheap `JSON.stringify(bands)` fingerprint plus `soloIndex` and canvas width, and only recomputes when that key actually changes. Verified visually via screenshots: a peaking band showed a real bell curve with the correct Q-shaped width; a highpass band showed a genuine rolloff (flat above the cutoff, dropping to the graph's floor below it) — not a straight line to a point.

Verified via CDP: included two real sounds (both landed in Now Playing while playing), clicked global pause (both correctly moved to Current Mix, header count dropped to two groups), then re-added one individually (correctly split across all three tiers simultaneously — Now Playing/Current Mix/Everything Else all present and correctly populated in one render).

**Number-field hover+scroll no longer requires a click first** (`numberBoxStepper.js`) — a direct, explicit reversal of the focus-gated design shipped in `v0.1.53`: "Just hovering a text box with a number should be grounds for scrolling with mouse wheel and changing it. Not selecting then hovering." **EQ bands gained a Gentle/Steep slope control** — the last item from the FL Studio parametric EQ clone's own research backlog (feasibility confirmed weeks earlier: ffmpeg's `highpass`/`lowpass` have a real `poles` parameter but `bandpass`/`bandreject` don't, and `BiquadFilterNode` has no slope parameter at all — cascading N identical filter instances in series was verified, on both sides, to be the one technique that works consistently across all four filter-*shaped* types). Only `lowpass`/`highpass`/`bandpass`/`notch` have a real slope concept (`SLOPE_CAPABLE_EQ_TYPES`, duplicated per the usual cross-file/cross-directory pattern in `EqEditor.js`, `SoundSource.js`, `PreviewSource.js`, and `loopClip.js`) — peaking/shelf bands are gain-shaped, not rolloff-shaped, and `'off'` does nothing, so the new Slope `<select>` next to Type hides/disables itself for those. `'steep'` means 4 identical cascaded stages (`STEEP_STAGE_COUNT`) instead of 1, each stage multiplying the rolloff by another ~12dB/octave (verified directly against the real bundled ffmpeg binary: four cascaded `highpass=f=1000:poles=2` instances measured ~34dB more attenuation than one).

**Remix trim waveform: rendering-only smoothing pass to reduce blockiness at high zoom** — next-lowest-scored ranked backlog item, following a research pass (per [[feedback_research_before_complex_tasks]]) into how DAWs/waveform libraries actually render at arbitrary zoom levels: real tools combine a multi-resolution peak pyramid (real finer detail fetched as you zoom) with smooth interpolated rendering rather than nearest-neighbor stepping. **BUG FIX: an uncaught exception during waveform-peak extraction could crash-loop the entire app with an unstoppable "JavaScript error occurred in the main process" dialog** — found by the agent's own testing (a malformed IPC call, `getWaveformPeaks(id)` with no `targetWidth`), then confirmed to be a real architectural gap, not just a testing artifact, before fixing it. Root cause: `runFfmpeg.js`'s shared `runFfmpegPipe` (the reusable ffmpeg-stdout-streaming wrapper `waveformPeaks.js`, `bandEnergy.js`, and `loopClip.js` all build on) wired the caller's per-chunk callback directly into the raw Node stream's own `'data'` event (`child.stdout.on('data', onChunk)`) with no try/catch - a synchronous throw inside `onChunk` (here: `extractWaveformPeaks`'s bucket-accumulation loop indexing into a zero-length `peaks` array, since `Array.from({length: undefined})` silently produces `[]`) propagates straight up through Node's stream internals as an uncaught main-process exception, completely bypassing every caller's own try/catch around the awaited promise (the throw happens well after that executor already returned). Electron's default handler shows a blocking dialog for this - and since the ffmpeg child process is never killed when its stdout handler throws, it keeps streaming and re-triggering the identical exception on every subsequent chunk, producing exactly the "won't stop popping up no matter how many times I click OK" symptom reported live, mid-session. **Fixed at the shared wrapper**, benefiting all four call sites at once (the project's own stated reason `runFfmpeg.js` is kept generic/domain-agnostic rather than each feature rolling its own spawn logic): `onChunk` is now called inside its own try/catch, killing the child and rejecting the promise on error instead of letting the throw escape - converting a fatal, unrecoverable crash into a normal, already-expected rejection (`ipc.js`'s `audio:getWaveformPeaks` handler already had a try/catch around this exact call, written assuming failures would surface as rejections - it just turned out that assumption didn't hold for a synchronous throw inside a raw stream callback). Also added a defensive guard directly in `extractWaveformPeaks` (`waveformPeaks.js`) rejecting immediately if `targetWidth` isn't a positive integer, since this function is reached over IPC - a real trust boundary where a bad argument should fail cleanly rather than silently corrupt internal state. **Verified via CDP against the real dev app**: repeated the exact malformed call that previously crashed the app and confirmed it now returns `null` with the app still fully alive and responsive afterward; confirmed a correctly-shaped call still returns real peak data unchanged; confirmed Remix's waveform still loads and renders correctly (including the smoothing fix above) after a full dev-app restart.

**Remix trim waveform: real finer-grained detail past the original resolution, closing out the other half of the blocky-waveform item** — `waveformPeaks.js`'s `extractWaveformPeaks` gained optional `windowStart`/`windowEnd` params: when present, ffmpeg seeks (`-ss`/`-t` as *input* options, before `-i`, for a fast seek rather than decoding from the start of a long file every time) and decodes just that narrower time range instead of the whole file, so the same `targetWidth` bucket count now spans a much smaller span - genuinely finer real detail, not a resample of the same coarse array. `LoopEditor.js` gained a second `detailPeaks`/`detailPeaksStart`/`detailPeaksEnd` slot alongside the existing full-file `peaks` - `redraw()` uses the detail array only while the current viewport is fully covered by it, falling back to the base array the instant the view moves past its edges (so there's never a moment showing stale detail for the wrong range). `waveform.js`'s `drawWaveform` now takes the peaks array's own `peaksStart`/`peaksEnd` time range as parameters (defaulting to `[0, duration]` for the base array) instead of always assuming `peaks` spans the whole file, so the same draw code works unchanged for either array. `plugins/editor/index.js`'s `maybeFetchDetailPeaks` (wired off the same `onViewportChange` the scrollbar already listens to) triggers only once the current view's seconds-per-pixel drops below the base array's own seconds-per-bucket - i.e., only once the user has actually zoomed in past what the existing resolution can show - debounced 250ms so a zoom gesture (many wheel ticks in quick succession) fires one ffmpeg pass for the settled end state, not one per tick.
